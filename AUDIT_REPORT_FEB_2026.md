## 2. Архитектурный обзор

### 2.1. Соблюдение слоистой структуры
Проект демонстрирует эталонное следование слоистой архитектуре:
*   **Domain:** Чистая бизнес-логика (`src/bioetl/domain`), изолированная от внешнего мира. Используются `Protocol` для портов и `frozen dataclass` для сущностей.
*   **Application:** Оркестрация бизнес-процессов (`src/bioetl/application`), зависящая только от абстракций домена.
*   **Infrastructure:** Реализация адаптеров (`src/bioetl/infrastructure`), зависящая от внешних библиотек.
*   **Composition:** Явный корень композиции (`bootstrap.py` и фабрики), связывающий слои.

### 2.2. Принципы Ports & Adapters и DDD
*   Все внешние системы (БД, API, файловая система) скрыты за портами (`DataSourcePort`, `StoragePort`).
*   Доменные сущности (Activity, Molecule) богаты поведением (валидация инвариантов в `__post_init__`).
*   Используются Value Objects (например, `Watermark`, `BatchID`) для типизации.

### 2.3. Границы модулей и зависимости
*   Зависимости строго контролируются тестами (`test_layer_dependencies.py`).
*   Отсутствуют циклические зависимости.
*   Использование `TYPE_CHECKING` блоков предотвращает runtime-импорты для типизации.

## 3. Выявленные проблемы и области для улучшения

Несмотря на высокую оценку, выявлены следующие точки роста (Phase 5 Refactoring):

1.  **Complexity of Composition Root:** Модуль `bootstrap.py` начинает накапливать логику инициализации (метрики, трейсинг, конфиги), что нарушает SRP.
2.  **Async/Sync Interface Consistency:** Метод `should_write_gold` в `BasePipeline` является синхронным, что может ограничить реализацию сложных фильтров, требующих I/O (например, lookup в кэше).
3.  **Strict Typing:** В некоторых местах отсутствует явное указание `@override`, что снижает читаемость и безопасность при рефакторинге иерархий классов.

## 4. План рефакторинга

Ниже приведен приоритизированный план улучшений для перехода к фазе "Architecture Refinement".

### Приоритет 1: Усиление типизации и безопасности (High)
**Цель:** Повысить надежность кода при изменениях в базовых классах и протоколах.
*   **Действие:** Добавить декоратор `@override` (из `typing_extensions`) ко всем методам, реализующим протоколы или переопределяющим методы базовых классов.
*   **Область:** `src/bioetl/infrastructure/adapters/`, `src/bioetl/application/pipelines/`.
*   **Риски:** Минимальные. Требует добавления зависимости `typing-extensions` (если Python < 3.12).

### Приоритет 2: Рефакторинг Composition Root (Medium)
**Цель:** Разгрузить `bootstrap.py` и выделить логику сборки графа объектов.
*   **Действие:** Выделить класс `PipelineAssembler` в `src/bioetl/composition/assemblers/`, который инкапсулирует логику создания `RuntimeConfig`, настройки метрик и создания раннера.
*   **Область:** `src/bioetl/composition/`.
*   **Риски:** Нарушение инициализации пайплайна. Требует тщательного тестирования `bootstrap_pipeline`.

### Приоритет 3: Асинхронные фильтры Gold слоя (Low)
**Цель:** Обеспечить возможность использования I/O в фильтрах Gold слоя.
*   **Действие:** Изменить сигнатуру `should_write_gold` в `BasePipeline` на `async def`. Обновить вызовы в `RecordProcessor` (добавить `await`).
*   **Область:** `src/bioetl/application/core/base.py`, `src/bioetl/application/core/record_processor.py`.
*   **Риски:** Breaking change для всех реализаций пайплайнов. Требует одновременного обновления всех наследников.

## 5. Метрики и контроль качества

Для контроля архитектуры рекомендуется добавить следующие метрики и проверки:

1.  **Strict Override Check:** Включить правило линтера (или mypy strict), требующее `@override` при переопределении.
2.  **Complexity Metrics:** Мониторить цикломатическую сложность (Cyclomatic Complexity) для `bootstrap.py`. Если превышает порог (например, 10), блокировать PR.
3.  **Dependency Graph Check:** В CI добавить шаг проверки графа зависимостей (`pydeps` или `import-linter`) на соответствие матрице импортов, описанной в `AGENT.md`.
