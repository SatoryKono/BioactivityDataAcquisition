### S2.1-001 — HIGH — Composite checkpoint bytes depend on `PYTHONHASHSEED`

- **Local severity:** HIGH (replay/checkpoint reproducibility risk).
- **Rules:** RULES.md §4.3 and §6.1; Qodo `718014`, `717993`
  (`QG-DET-001`, Qodo severity `UNSPECIFIED`).
- **Evidence:**
  `src/bioetl/application/composite/checkpoint/state.py:45`,
  `state.py:47`, `state.py:149`, `state.py:151`,
  `state_serialization.py:26`, `state_serialization.py:44`, and
  `persistence_service.py:57`.
- **Current behavior:** checkpoint state stores completed names as
  `frozenset[str]`, converts them with unsorted `list(...)`, serializes result
  dictionaries in insertion order, and writes `json.dumps(..., indent=2)`
  without `sort_keys=True` or the canonical serializer.
- **Impact:** the same logical checkpoint produces different artifact bytes in
  different Python processes. Byte comparison, exact replay evidence, and
  checkpoint artifact reproducibility can report drift even when runtime state
  is semantically identical.
- **Verification 1 — code trace:** `CompositeCheckpointState.to_dict()` emits
  `list(self.completed_enrichers)`/`list(self.completed_dependencies)`;
  `CompositeCheckpointPersistenceService.save()` writes that payload unchanged.
- **Verification 2 — runtime reproduction:** identical state emitted
  `['beta', 'delta', 'gamma', 'alpha']` with `PYTHONHASHSEED=1` and
  `['delta', 'gamma', 'alpha', 'beta']` with `PYTHONHASHSEED=2`.
- **Verification command:**

  ```bash
  for seed in 1 2; do
    env PYTHONHASHSEED="$seed" .venv/bin/python -c \
      'from bioetl.application.composite.checkpoint.state import CompositeCheckpointState; import json; s=CompositeCheckpointState(composite_name="c", run_id="r", completed_enrichers=frozenset({"alpha","beta","gamma","delta"})); print(json.dumps(s.to_dict(), indent=2))'
  done
  ```

- **Remediation direction:** sort set-derived collections and keyed result maps,
  then serialize through the project canonical JSON seam before the existing
  atomic storage port write.

### S2.1-002 — HIGH — `_cv_details` JSON is not canonical and changes with equivalent map order

- **Local severity:** HIGH (exact-output determinism and JSON-field contract risk).
- **Rules:** RULES.md §2.6 Schema Typing Policy and §4.3; Qodo `718014`,
  `717993` (`QG-DET-001`, Qodo severity `UNSPECIFIED`).
- **Evidence:**
  `src/bioetl/application/composite/cross_validator_helpers.py:106`,
  `cross_validator_helpers.py:120`, `cross_validator_helpers.py:148`, and
  `src/bioetl/application/composite/cross_validator.py:226`.
- **Current behavior:** `_build_enricher_detail()` preserves incidental dict
  insertion order for mismatch fields and calls `json.dumps(...,
  ensure_ascii=False)` without sorted keys or compact canonical separators.
  `_combine_cv_details()` repeats the non-canonical serialization and
  `_finalize()` places the bytes in the `_cv_details` DataFrame column.
- **Impact:** semantically identical mismatch sets can yield different row
  bytes. This violates the canonical JSON contract and weakens reproducible
  composite outputs and byte-level evidence.
- **Verification 1 — code/data-flow trace:** helper output flows directly to
  `cv_details.alias("_cv_details")` in the returned validation DataFrame.
- **Verification 2 — runtime reproduction:** the same two mismatch fields
  supplied in opposite mapping insertion order produced different JSON strings:
  `{"enricher": "e", "field_mismatches": ["b", "a"]}` versus
  `{"enricher": "e", "field_mismatches": ["a", "b"]}`.
- **Verification command:**

  ```bash
  .venv/bin/python -c 'import polars as pl; from bioetl.application.composite.cross_validator_helpers import _build_enricher_detail; a=_build_enricher_detail("e", {"b":pl.Series([True]),"a":pl.Series([True])}, pl.Series([2])); b=_build_enricher_detail("e", {"a":pl.Series([True]),"b":pl.Series([True])}, pl.Series([2])); print(a[0]); print(b[0]); print(a[0] == b[0])'
  ```

- **Remediation direction:** sort mismatch fields/enricher detail entries and
  use the canonical JSON serializer (stable keys, compact separators, project
  ASCII policy); add byte-equality regression tests, not only `json.loads()`
  semantic assertions.

### S2.1-003 — MEDIUM — Exported workflow executor builders lack return annotations

- **Local severity:** MEDIUM (public type-contract gap with bounded blast radius).
- **Rules:** RULES.md §4.4.2; Qodo `718001`, `717987`, `717867`
  (`QG-TYPE-001`, Qodo severity `UNSPECIFIED`).
- **Evidence:**
  `src/bioetl/application/workflow/transforms/reconcile_foreign_keys.py:18`,
  `reconcile_foreign_keys.py:21`,
  `src/bioetl/application/workflow/transforms/reconcile_rows.py:15`, and
  `reconcile_rows.py:18`.
- **Current behavior:** both functions are exported through `__all__` and
  return executor closures registered as `WorkflowTransformCallable`, but
  neither public builder declares its return type.
- **Impact:** the public workflow extension seam is not fully
  `mypy --strict`-described; incompatible executor signature changes can escape
  checking at the builder boundary.
- **Verification 1 — AST/usage trace:** the full-scope AST census found exactly
  these two public missing-return annotations; `builtins.py:31` and
  `builtins.py:36` pass their results to
  `WorkflowTransformRegistry.register(..., executor: WorkflowTransformCallable)`.
- **Verification 2 — independent lint:** Ruff `ANN201` reports both functions.
- **Verification command:**

  ```bash
  .venv/bin/ruff check --select ANN201 \
    src/bioetl/application/workflow/transforms/reconcile_foreign_keys.py \
    src/bioetl/application/workflow/transforms/reconcile_rows.py
  ```

- **Remediation direction:** annotate both builders as returning
  `WorkflowTransformCallable` (or introduce a narrower callable alias matching
  the explicit closure signature).
