## Findings

### PASS -- No Violations Found

#### ARCH-005: Factory Isolation (CRITICAL) -- PASS
All factory and assembly logic resides exclusively in `composition/`. No factory instantiations found in `domain/` or `application/`.

- `GenericPipelineFactory` in `composition/factories/pipeline_factory.py`
- `DataSourceFactory` in `composition/factories/data_source_factory.py`
- `DQServicesFactory` in `composition/factories/dq_factory.py`
- `StorageFactory` in `composition/factories/storage.py`
- `BaseServicesFactory` in `composition/factories/services_factory.py`

All correct locations per ARCH-005.

#### DI Wiring -- PASS
Bootstrap functions consistently use constructor injection. Dependencies flow from composition root downward:

```python
# runtime/observability.py -- correct DI pattern
def bootstrap_logger_port(pipeline: str, run_id: UUID | None = None, ...) -> LoggerPort:
    return UnifiedLogger(pipeline=pipeline, run_id=effective_run_id, ...)

def bootstrap_observability_bundle(pipeline: str, run_id: UUID, settings: Settings, ...) -> ObservabilityBundle:
    logger = bootstrap_logger_port(...)
    tracer = bootstrap_tracer_port(settings)
    metrics = bootstrap_metrics_port(settings)
    ...
```

```python
# runtime/pipeline.py -- proper injectable parameters
def bootstrap_pipeline_runner(ctx: PipelineRunContext, registry: PipelineRegistry | None = None) -> PipelineRunner:
    return build_pipeline_runner(
        ctx=ctx, registry=registry,
        get_default_registry_fn=get_default_registry,  # Injectable for testing
        ...
    )
```

#### No Module-level Side Effects -- PASS
No module-level instantiation of services, clients, or I/O operations found.

- `runtime/observability.py` -- pure function definitions, no module-level state
- `runtime/pipeline.py` -- pure function definitions
- All factory files -- class/function definitions only

`maybe_start_metrics_server()` correctly separates server startup from bootstrap, keeping the composition layer side-effect free.

### Observations (Non-blocking)

#### OBS-001: Deprecated Aliases (INFO)
Multiple deprecated aliases maintained for backward compatibility:
- `bootstrap_logger` -> `bootstrap_logger_port`
- `bootstrap_tracer` -> `bootstrap_tracer_port`
- `bootstrap_metrics` -> `bootstrap_metrics_port`
- `bootstrap_dq_monitor` -> `bootstrap_dq_monitor_port`
- `bootstrap_observability` -> `bootstrap_observability_bundle`
- `bootstrap_pipeline` -> `bootstrap_pipeline_runner`
- `bootstrap_checkpoint` -> `bootstrap_checkpoint_port`
- `bootstrap_storage` -> `bootstrap_storage_adapter`

**Recommendation:** Consider adding `@deprecated` decorators (Python 3.13+) or `warnings.warn()` to guide migration. These are not violations per EXC-004.

#### OBS-002: Injectable Function Parameters Pattern (INFO)
`runtime/pipeline.py` uses an excellent testability pattern where bootstrap functions accept injectable function parameters:

```python
def build_pipeline_runner(
    ctx, registry,
    get_default_registry_fn=get_default_registry,
    register_all_providers_fn=register_all_providers,
    ...
)
```

This enables pure unit testing without mocking module-level imports. Good practice.

#### OBS-003: NoOp Implementations (INFO)
CLI bootstrap correctly uses NoOp implementations (NoOpLogger, NoOpMetrics, NoOpTracing) for commands that do not require full observability. This follows the Null Object Pattern (EXC-003).
