**Дата аудита:** Март 2026
**Версия архитектуры:** 5.4
**Общий статус:** Проект демонстрирует высокий уровень зрелости архитектуры (Hexagonal + DDD), строгое соблюдение границ слоёв и наличие развитой инфраструктуры тестирования. ## 3. Детальный анализ архитектуры

### 3.1. Соблюдение слоистой структуры и Hexagonal Architecture
*   **Domain:** Идеально. Сущности (`BaseEntity`) чистые, frozen dataclasses, используют `datetime.UTC`. Порты определены через `Protocol`. Тесты (`test_layer_dependencies.py`) строго запрещают импорт инфраструктуры.
*   **Application:** Хорошо. `BasePipeline` использует внедрение зависимостей (DI) для сервисов и трансформеров. Однако, логика фильтрации Gold-слоя (`should_write_gold`) всё еще находится в базовом классе, что нарушает SRP.
*   **Infrastructure:** Есть замечания. Модуль `src/bioetl/infrastructure/config.py` перегружен ответственностью: он загружает YAML, валидирует Pydantic-схемы и выполняет маппинг в доменные объекты (`yaml_config_to_domain`).
*   **Interfaces:** Четко отделены (CLI, Orchestration).

### 3.2. Основные выявленные проблемы
1.  **Нарушение границ в Config:** Документация (`AGENT.md`) утверждает, что логика маппинга вынесена в `src/bioetl/composition/mappers/config_mapper.py`. По факту этот файл отсутствует, а логика осталась в инфраструктуре.
2.  **God-Object тенденции в BasePipeline:** Методы `transform_for_gold` и `should_write_gold` являются hardcoded логикой в абстрактном классе, хотя должны быть вынесены в `GoldTransformer` по аналогии с `SilverTransformer`.
3.  **Остаточный Tech Debt:** Присутствуют закомментированные импорты или неиспользуемые переменные (выявлено статическим анализом `vulture` в тестах), хотя общий уровень чистоты кода высокий.

## 4. План рефакторинга (Phase 5: Refinement)

Предлагается провести рефакторинг в два этапа с приоритетом на устранение архитектурных несоответствий.

### Приоритет 1 (Критично): Выделение слоя маппинга конфигурации
**Цель:** Привести код в соответствие с документацией и принципом разделения ответственности (Infrastructure не должен знать о деталях конструирования Domain объектов).

*   **Шаг 1.1:** Создать модуль `src/bioetl/composition/mappers/config_mapper.py`.
*   **Шаг 1.2:** Перенести функцию `yaml_config_to_domain` и вспомогательные функции (`_extract_source_fields`, `_build_gold_filters`) из `infrastructure/config.py` в новый модуль.
*   **Шаг 1.3:** Обновить `infrastructure/config.py`, оставив там только `load_pipeline_config` (возвращает `PipelineYamlConfig`) и `Settings`.
*   **Шаг 1.4:** Обновить `bootstrap.py` для использования нового маппера.

*   **Риски и минимизация:**
    *   *Риск:* Циклические импорты (Circular Dependency) между `infrastructure` и `composition`, если типы определены не там.
    *   *Минимизация:* Строго использовать `TYPE_CHECKING` и убедиться, что Pydantic-схемы остаются в `infrastructure`, а Domain-конфиги в `domain`.
    *   *Риск:* Поломка динамического разрешения путей конфигурации.
    *   *Минимизация:* Прогон тестов `test_config_golden_master.py` перед и после изменений.

*   **Критерий готово:** `test_config_golden_master.py` проходит без изменений входных/выходных данных; в `infrastructure` нет импортов доменных сущностей конфига.

### Приоритет 2 (Важно): Декомпозиция BasePipeline (Gold Transformer)
**Цель:** Убрать логику трансформации из базового класса пайплайна, завершив переход на полную композицию.

*   **Шаг 2.1:** Определить протокол `GoldTransformerPort` в `domain/ports`.
*   **Шаг 2.2:** Реализовать `DefaultGoldTransformer` в `application/core/transformers/`.
*   **Шаг 2.3:** Перенести логику `should_write_gold` и `transform_for_gold` в этот трансформер.
*   **Шаг 2.4:** Внедрить `GoldTransformer` через конструктор `BasePipeline` (обновить фабрики).

*   **Риски и минимизация:**
    *   *Риск:* Регрессия в логике фильтрации Gold-слоя (например, потеря данных при записи).
    *   *Минимизация:* Добавить unit-тест для `DefaultGoldTransformer`, проверяющий эквивалентность логики текущей реализации `BasePipeline`.
    *   *Риск:* Усложнение фабрик пайплайнов (`GenericPipelineFactory`).
    *   *Минимизация:* Использовать значения по умолчанию (Default implementation) в фабрике, чтобы не ломать существующие пайплайны.

*   **Критерий готово:** `BasePipeline` не содержит методов с бизнес-логикой Gold-слоя; тесты пайплайнов проходят.

### Приоритет 3 (Желательно): Чистка технического долга
*   **Шаг 3.1:** Удалить неиспользуемые методы, выявленные `vulture`.
*   **Шаг 3.2:** Провести ревизию `TODO` комментариев.

*   **Риски и минимизация:**
    *   *Риск:* Удаление кода, который используется неявно (через рефлексию или динамические импорты).
    *   *Минимизация:* Тщательная проверка через `grep` по строкам перед удалением.

## 5. Метрики и контроль качества

Для предотвращения регресса рекомендуется:

1.  **Architecture Tests:** Добавить тест `test_infrastructure_no_domain_mapping`, запрещающий функции маппинга (возвращающие доменные объекты) внутри `infrastructure/config.py`.
2.  **Line Count Metrics:** Отслеживать размер файла `BasePipeline`. Цель — снижение LOC на 10-15% после выноса Gold-логики.
3.  **Config Cohesion:** Контролировать, что `infrastructure` импортирует `domain` только для определений типов (Protocol/ABC), но не конструирует сложные агрегаты.

**Прогноз изменения балла:** После реализации плана оценка по категории "Качество документации" поднимется до 9/10, а "Технический долг" до 9/10. Общий балл вырастет до **~8.9**.
