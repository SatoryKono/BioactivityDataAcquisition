## 2. Архитектурный анализ

### Оценка текущей архитектуры
*   **Слоистая структура:** Идеально соблюдается. Тесты `tests/test_architecture.py` гарантируют отсутствие утечек инфраструктуры в домен.
*   **Ports & Adapters (Hexagonal) и DDD:** Домен полностью изолирован и оперирует только бизнес-сущностями. Инфраструктура зависит от портов.
*   **Границы модулей:** В целом четкие, но `bootstrap.py` начинает брать на себя слишком много ответственности (нарушение SRP).
*   **Соглашения:** Единообразный стиль кодирования, типизации и структуры файлов.

### Выявленные проблемы
1.  **Нарушение границ слоёв (SRP в Bootstrap):**
    *   Файл `src/bioetl/bootstrap.py` выполняет две несовместимые функции: инициализация глобальных синглтонов (Redis, S3) и роль конкретной Фабрики для пайплайнов (`ChEMBLActivityPipelineFactory`).
    *   Класс `ChEMBLActivityPipelineFactory` находится внутри `bootstrap.py`. При добавлении 5-10 новых пайплайнов этот файл станет "God Object".
2.  **Смешение конфигурации и логики:**
    *   В `ChEMBLActivityPipelineFactory` параметры Rate Limiter (`rate=10.0`, `capacity=20`) захардкожены.
    *   Для изменения лимитов (например, при получении платного ключа API) придется править код и деплоить релиз.
3.  **Дублирование логики маппинга:**
    *   Метод `transform_bronze_to_silver` в классе пайплайна содержит низкоуровневую логику перекладывания полей из JSON в словарь. Это загрязняет оркестратор пайплайна деталями реализации.

## 3. План рефакторинга

### Шаг 1: Декомпозиция Composition Root (Bootstrap)
*   **Приоритет:** Критичный
*   **Цель:** Разделить инициализацию инфраструктуры и фабрики пайплайнов.
*   **Правки:**
    *   Создать пакет `src/bioetl/infrastructure/factories/`.
    *   Перенести `ChEMBLActivityPipelineFactory` в `src/bioetl/infrastructure/factories/chembl.py`.
    *   В `bootstrap.py` оставить только функцию `bootstrap()`, возвращающую контейнер с общими сервисами.
*   **Риски:** Циклические импорты (минимальны при правильной структуре).
*   **Критерий готово:** `bootstrap.py` содержит только инициализацию общих адаптеров.

### Шаг 2: Конфигурируемые Фабрики
*   **Приоритет:** Высокий
*   **Цель:** Вынести параметры провайдеров (rate limits, timeouts) в конфигурацию.
*   **Правки:**
    *   В `src/bioetl/config.py` добавить настройки для провайдеров (например, `ChEMBLSettings`, `PubChemSettings`).
    *   Обновить фабрики, чтобы они читали эти настройки из объекта `Settings`.
*   **Риски:** Необходимость обновления `.env.example`.
*   **Критерий готово:** Лимиты API можно менять через переменную окружения `BIOETL_CHEMBL_RATE_LIMIT`.

### Шаг 3: Выделение слоя Мапперов
*   **Приоритет:** Средний
*   **Цель:** Очистить Application слой от логики преобразования данных.
*   **Правки:**
    *   Создать абстракцию `Mapper` или протокол в Application слое.
    *   Вынести логику `transform_bronze_to_silver` из `ChEMBLActivityPipeline` в `ChEMBLActivityMapper`.
*   **Риски:** Увеличение количества классов.
*   **Критерий готово:** Пайплайн делегирует трансформацию отдельному компоненту.

## 4. Контроль качества

Для контроля архитектуры предлагается добавить/обновить следующие метрики:

1.  **Complexity Check (Xenon):** Продолжать использовать. После рефакторинга сложность `bootstrap.py` и `ChEMBLActivityPipeline` должна снизиться.
2.  **Import Linter:** Настроить правила, запрещающие импорт конкретных фабрик в `bootstrap.py` (кроме тех случаев, когда это необходимо для DI контейнера, но лучше использовать ленивую загрузку или реестр).
3.  **Тесты:**
    *   Добавить юнит-тест для новой фабрики, проверяющий, что она корректно считывает настройки из конфига.
    *   Добавить тест маппера (Snapshot testing): `input_bronze.json` -> `Mapper` -> `expected_silver.json`.

**Прогноз изменения балла:**
Реализация плана позволит поднять оценку "Модульность" до 10 и "Технический долг" до 9, увеличив общий балл до **9.25**.
