# BioETL: Project Rules
*Version: 1.0 (Optimized), 2025-05-20*

## 1. Scope и Философия
Данный документ устанавливает стандарты разработки проекта BioETL.
**Цель проекта**: Эффективный ETL-инструмент для сбора и унификации научных данных (PubMed, ChEMBL, PubChem и др.).
**Главный принцип**: "Pragmatic Engineering". Мы избегаем преждевременной сложности (Over-engineering). Архитектура должна ускорять добавление новых источников, а не блокировать их бюрократией.

## 2. Архитектура: Ports & Adapters (Lite)
Мы используем упрощенную Гексагональную архитектуру, чтобы изолировать логику обработки данных от внешних API и баз данных.

- **Infrastructure (Adapters)**: Весь код, который "трогает" внешний мир. Клиенты HTTP (PubChemClient), драйверы БД (PostgresAdapter), файловая система.
- **Application (Pipelines)**: Оркестрация. Здесь определяется *поток* данных. Этот слой вызывает адаптеры и применяет трансформации.
- **Domain (Pure Logic)**: Чистые функции трансформации данных и Pydantic/Pandera схемы. Здесь нет ввода-вывода.
    - *Отличие от строгого DDD*: Мы **не** используем тяжелые DDD-паттерны (Aggregates, Repositories для каждой сущности). Данные — это потоки (Dataframes/Streams), а не объекты с поведением.

## 3. Организация Пайплайнов (DAGs)
Вместо жесткой структуры (E->T->V->E), мы рассматриваем пайплайны как направленные графы (DAG).
- **Гибкость**: Этапы могут идти в любом порядке (например, Extract -> Validate (Raw) -> Transform -> Enrich -> Export).
- **Оркестрация**: Для управления зависимостями и ретраями рекомендуется использовать легковесные инструменты (Prefect, Dagster) или простой собственный Runner, если зависимостей мало.
- **Fail Fast**: Валидация критичных ошибок должна происходить как можно раньше.

## 4. Стратегия Данных (Medallion Architecture)
Учитывая нестабильность внешних научных источников, мы делим данные на уровни качества:

1.  **Bronze (Raw)**: "Сырые" данные, сохраненные как есть (JSON/CSV).
    - *Валидация*: Минимальная или отсутствует. Цель — не потерять данные, если источник добавил поле.
2.  **Silver (Normalized)**: Очищенные данные, приведенные к плоскому формату.
    - *Валидация*: Pydantic/Pandera (Soft). Отсеиваем битые записи, логируем ошибки, но не роняем весь пайплайн.
3.  **Gold (Curated)**: Финальные, строгие контракты для потребителей.
    - *Валидация*: Строгая (`strict=True`). Гарантирует качество для аналитики.

## 5. Документация (Automation First)
Принцип "Docs-as-Code" реализуется через автоматизацию, а не ручной труд.

- **Автогенерация**: Карты модулей, схемы данных (ER-диаграммы) и описания полей должны генерироваться из кода (Pydantic/Pandera models) автоматически скриптами в CI.
- **Ручная документация**: Только архитектурные решения (ADR) и высокоуровневые гайды (`docs/guides/`).
- **Синхронизация**: Запрещено требовать ручного обновления `00-map.md` в PR. Это задача роботов.

## 6. Политика Именования и Структура
Мы унифицируем структуру вокруг **Провайдера** данных, так как это основной источник сложности (API limits, auth).

**Структура папок:**
```text
src/bioetl/
  ├── infrastructure/
  │   └── adapters/
  │       ├── chembl/        # ChEMBL (chembl_webresource_client)
  │       ├── pubchem/       # PubChem (pubchempy)
  │       ├── uniprot/       # UniProt (unipressed)
  │       ├── gtop/          # Guide to Pharmacology (pyGtoP или requests)
  │       ├── openalex/      # OpenAlex (pyalex)
  │       ├── crossref/      # Crossref (habanero)
  │       ├── semantic/      # Semantic Scholar (semanticscholar)
  │       └── pubmed/        # PubMed (Bio.Entrez / metapub)
  ├── application/
  │   └── pipelines/
  │       ├── pubchem/       # Пайплайны PubChem
  │       └── common/        # Общие шаги
  └── domain/
      └── schemas/           # Pydantic/Pandera схемы
```

**Именование файлов и доков:**
- Всегда: `Provider` -> `Entity`.
- Код: `pubchem/compounds.py`
- Доки: `docs/providers/pubchem/compounds.md`
- *Цель*: Файлы документации и кода лежат в предсказуемых, зеркальных местах.

## 7. Рекомендованные библиотеки
Для взаимодействия с внешними API используем готовые клиенты (avoid reinventing the wheel).

| Источник            | Библиотека (Package)        | Комментарий |
|---------------------|-----------------------------|-------------|
| **ChEMBL**          | `chembl_webresource_client` | Официальный клиент. |
| **PubChem**         | `pubchempy`                 | Стандарт де-факто для Python. |
| **UniProt**         | `unipressed`                | Эффективный клиент для UniProt REST API. |
| **Guide to Pharm.** | `pyGtoP`                    | *Warning*: Не поддерживается активно. Если сбоит — писать прямой адаптер на `httpx`. |
| **OpenAlex**        | `pyalex`                    | Удобная обертка с типизацией. |
| **Crossref**        | `habanero`                  | Предпочтительнее устаревшего `crossrefapi` (поддержка rOpenSci). |
| **Semantic Scholar**| `semanticscholar`           | Официальная библиотека. |
| **PubMed**          | `biopython` (`Bio.Entrez`)  | Низкоуровневый стандарт. Для удобства поиска можно рассмотреть `metapub`. |

## 8. Стандарты Кода и CI
- **Линтеры**: Ruff (объединяет flake8/isort).
- **Типизация**: MyPy (обязательна для Core логики, желательна для скриптов).
- **Тесты**:
    - Unit: для трансформаций (Domain). Быстрые, без IO.
    - Integration: для Адаптеров (Infrastructure). Используют VCR.py или моки.
    - E2E: Запуск полного пайплайна на сэмпле данных.

## 9. Change Management
- **Schema Evolution**: Изменения в Bronze-схемах не считаются Breaking. Изменения в Gold-схемах требуют версионирования.
- **ADR**: Для важных решений (выбор базы данных, смена оркестратора) создаем ADR в `docs/architecture/decisions/`.
