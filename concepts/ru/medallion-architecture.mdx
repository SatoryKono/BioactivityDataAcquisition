Каждый запуск конвейера в BioETL записывает данные через три отдельных слоя. Этот подход — называемый медальонной архитектурой — отделяет сырые ответы API от нормализованных записей и готовых к анализу агрегатов, давая вам чёткую родословную данных от источника до запроса. Поскольку каждый слой сохраняется независимо, вы можете повторно обработать любой этап без повторной выгрузки данных из API, изучить, что именно пришло из вышестоящего источника, и вернуться к любой предыдущей версии таблицы.

## Три слоя

<CardGroup cols={3}>
  <Card title="Bronze" icon="1">
    Сырые записи в точности в том виде, в каком они получены из API, сжатые zstd. Ничего не изменяется и не фильтруется.
  </Card>

  <Card title="Silver" icon="2">
    Нормализованные, провалидированные записи, записанные в Delta Lake. Применяется схема и используется хэш контента для дедупликации.

  <Card title="Gold" icon="3">
    Развёрнутые, готовые к аналитике записи, производные от Silver. Вложенные поля раскрыты, а исключённые поля удалены.

### Bronze: сырые данные в том виде, в каком они получены

Bronze хранит каждый пакет ответов API в виде файла JSONL, сжатого zstd. Ничего не преобразуется — если API возвращает некорректную запись, она попадает в Bronze без изменений. Эта неизменяемость и делает возможным точное воспроизведение: вы можете повторно прогнать обработку Silver и Gold по тем же файлам Bronze и получить идентичные результаты.

Каждый файл пакета Bronze содержит sidecar-отчёт о качестве данных и необязательный YAML с метаданными:

```text
data/output/bronze/chembl/activity/2025-01-15/
├── batch-2025-01-15-a1b2c3d4.jsonl.zst       # Сжатый пакет
├── batch-2025-01-15-a1b2c3d4.jsonl           # Необязательная несжатая копия
├── chembl-activity-metadata.yaml             # Количество записей, временные метки
└── batch-2025-01-15-chembl-activity-dq-report.json
```

Файлы Bronze хранятся на диске до тех пор, пока вы не решите их удалить. Используйте стандартные средства файловой системы, чтобы удалить старые пакеты Bronze, или настройте параметры vacuum конвейера, чтобы автоматически освобождать место.

### Silver: нормализованный и провалидированный

Silver — это таблица [Delta Lake](https://delta.io). Записи из Bronze проходят через многоступенчатый конвейер **нормализации** и **валидации** перед записью.

#### Нормализация

Нормализация преобразует сырые ответы API в согласованную, соответствующую схеме форму:

- **Переименование полей** — специфичные для поставщика имена полей (например, `standard_value` в ChEMBL, `CanonicalSMILES` в PubChem) сопоставляются с единой схемой, общей для всех конвейеров.
- **Приведение типов** — числа в строковом представлении приводятся к корректным числовым типам (`float64`, `int32` и т. д.); строки дат разбираются в столбцы `datetime`.
- **Стандартизация единиц измерения** — числовые значения активности приводятся к каноническим единицам там, где это применимо (например, значения IC50, указанные в µM, сохраняются в nM для сопоставимости между поставщиками).
- **Гармонизация null-значений** — специфичные для поставщика маркерные значения (`"None"`, `"-"`, пустые строки) заменяются на корректные null-значения, чтобы запросы в нижних слоях вели себя согласованно.
- **Извлечение вложенных полей** — выбранные вложенные поля или поля-массивы API разворачиваются в столбцы верхнего уровня, чтобы запросы к Silver оставались простыми.

#### Валидация

Валидация выполняется сразу после нормализации с помощью [Pandera](https://pandera.readthedocs.io/) и правил уровня поля, определённых в вашем YAML сущности:

- **Проверки схемы** — каждый столбец сверяется с объявленным типом данных. Несоответствие типа вызывает ошибку валидации для затронутой записи.
- **Проверки обязательных полей** — поля, помеченные `required: true`, не должны быть null; отсутствующие значения направляют запись в карантин.
- **Проверки диапазона** — числовые поля, настроенные с границами `min` / `max`, проверяются на соответствие. Значения вне диапазона помечаются кодом ошибки `DQ-RANGE`.
- **Проверки перечислений** — категориальные поля, настроенные с `allowed_values`, отклоняют любую запись, содержащую неперечисленное значение.
- **Проверки шаблонов** — строковые поля с правилом `pattern` сопоставляются с заданным регулярным выражением; несоответствующие значения помещаются в карантин.
- **Дедупликация** — для каждой записи вычисляется хэш контента (SHA-256 по бизнес-ключу \+ полезному грузу). Совпадающие хэши пропускаются при слиянии Delta Lake, что делает повторные запуски по одним и тем же данным Bronze полностью идемпотентными.

Записи, прошедшие все проверки, объединяются в таблицу Silver с помощью семантики upsert (сопоставление по бизнес-первичным ключам, обновление при изменении хэша полезного груза). Записи, не прошедшие хотя бы одну проверку, записываются в карантинную таблицу вместо того, чтобы загрязнять чистые данные.

Таблицу Silver можно читать напрямую с помощью Polars:

```python
import polars as pl

# Текущая версия
df = pl.read_delta("data/output/silver/chembl/activity")

# Более ранняя версия — Delta Lake сохраняет полную историю
df = pl.read_delta("data/output/silver/chembl/activity", version=5)
```

### Gold: развёрнутый и готовый к аналитике

Gold строится из Silver путём разворачивания вложенных структур JSON, удаления внутренних полей и применения специфичных для поставщика агрегаций. Таблицы Gold оптимизированы для прямых запросов — распаковка JSON не требуется.

<Note>
  Gold записывается как таблица Delta Lake с теми же гарантиями путешествия во времени, что и Silver. Вы можете запрашивать любую историческую версию таблицы Gold так же, как и Silver.
</Note>

## Структура каталогов

После запуска конвейера вы увидите следующее расположение под `data/output/`:

```text
data/output/
├── bronze/{provider}/{entity}/{date}/
│   └── batch-*.jsonl.zst
├── silver/{provider}/{entity}/           # Таблица Delta Lake
│   ├── _delta_log/
│   └── part-00000-*.parquet
├── gold/{provider}/{entity}/             # Таблица Delta Lake (развёрнутая)
│   ├── _delta_log/
│   └── part-00000-*.parquet
├── checkpoints/                          # Состояние возобновления конвейера
├── quarantine/                           # Записи, не прошедшие валидацию
│   └── common.quarantine/
│       ├── _delta_log/
│       └── part-00000-*.parquet
└── control/run_manifest/                 # Неизменяемые записи запусков
```

Сегменты `{provider}` и `{entity}` соответствуют имени конвейера. Например, конвейер `chembl_activity` записывает в `bronze/chembl/activity/`, `silver/chembl/activity/` и `gold/chembl/activity/`.

## Как движутся данные

```text
Внешний API
     │
     ▼
Bronze (JSONL + zstd)
  сырые записи, без изменений, только дозапись
     │
     ▼ переименование полей, приведение типов, гармонизация null
     ▼ проверка схемы, проверки диапазона/перечислений/шаблонов, дедупликация
Silver (Delta Lake)
  нормализованный, с хэшем контента, путешествие во времени включено
     │
     ▼ разворачивание, агрегация, исключение внутренних полей
Gold (Delta Lake)
  готовый к аналитике, без вложенного JSON
```

Записи, не прошедшие проверки DQ на этапе Silver, записываются в карантинную таблицу вместо того, чтобы безмолвно отбрасываться. Вы можете в любое время изучить, повторно обработать или очистить карантинные записи с помощью команд `bioetl quarantine`.

## Что вам даёт Delta Lake

BioETL использует [delta-rs](https://github.com/delta-io/delta-rs) для записи слоёв Silver и Gold. Это означает, что каждая запись атомарна, изменения схемы обнаруживаются и отклоняются, если они явно не разрешены, а каждая версия таблицы доступна по номеру.

<AccordionGroup>
  <Accordion title="ACID-транзакции">
    Каждая пакетная запись либо полностью фиксируется, либо откатывается. Вы никогда не прочитаете частично записанную таблицу, даже если запуск конвейера будет прерван в середине пакета.
  </Accordion>

  <Accordion title="Путешествие во времени">
    Delta Lake сохраняет полный журнал транзакций. Вы можете запросить любую прошлую версию таблицы Silver или Gold, передав параметр `version` в `pl.read_delta()`. По умолчанию журнал транзакций хранится 7 дней (настраивается через `BIOETL_DELTA_VACUUM_RETENTION`).
  </Accordion>

  <Accordion title="Применение схемы">
    Поступающие записи проверяются по объявленной схеме перед каждой записью. Если в ответе API появляются новые поля, BioETL обнаруживает расхождение и записывает предупреждение в журнал вместо того, чтобы молча изменить схему таблицы.
  </Accordion>

  <Accordion title="Аудиторский след">
    Каждая запись фиксируется в журнале Delta с временной меткой, типом операции и количеством записей. В сочетании с манифестом запуска, хранящимся в `data/output/control/run_manifest/`, у вас есть полная неизменяемая история каждого выполнения конвейера.
  </Accordion>
</AccordionGroup>

## Почему это важно для вашего рабочего процесса

Поскольку Bronze неизменяем, а Silver/Gold производны, вы можете:

- **Воспроизвести любой результат** — повторно прогнать обработку Silver и Gold по кэшированным файлам Bronze, чтобы получить побайтово идентичные результаты.
- **Восстановиться после ошибок схемы** — исправить правило преобразования и перестроить Silver и Gold из Bronze без повторной выгрузки из API.
- **Провести аудит любой записи** — проследить строку Gold через Silver до исходного пакета Bronze, содержавшего её, с помощью `manifest_id`, связывающего запись с конкретным запуском конвейера.
- **Сравнить запуски** — использовать `bioetl run-manifest diff`, чтобы увидеть, чем именно отличались два запуска по конфигурации, количеству записей или результатам DQ.

<Tip>
  Используйте `bioetl run --run-type rebuild`, чтобы стереть и перестроить Silver и Gold из существующих файлов Bronze. Это быстрее, чем полная повторная выгрузка, и гарантирует те же исходные данные.
</Tip>
