BioETL применяет проверки качества данных (DQ) на каждом этапе конвейера. Прежде чем запись попадёт в слой Silver, она должна пройти нормализацию и проверку схемы, а также любые настроенные вами правила уровня поля. Записи, не прошедшие проверки, записываются в карантинную таблицу, а не отбрасываются без предупреждения и не пропускаются дальше. Вы можете в любой момент изучить, повторно обработать или очистить карантинные записи, а отчёты DQ записываются рядом с данными каждого слоя, чтобы у вас всегда был аудиторский след.

## Как работает нормализация

Прежде чем сможет запуститься валидация, исходные записи проходят **нормализацию** — преобразование из специфичного для поставщика формата в каноническую схему, используемую во всех конвейерах. Нормализация выполняется на переходе Bronze → Silver и включает:

<AccordionGroup>
  <Accordion title="Переименование полей">
    Специфичные для поставщика имена полей сопоставляются с единой, независимой от конвейера схемой. Например, `standard_value` и `standard_units` в ChEMBL становятся `activity_value` и `activity_unit`; `CanonicalSMILES` в PubChem становится `smiles`. Таблицы сопоставления находятся в конфигурации каждого поставщика по пути `configs/providers/{provider}.yaml`.
  </Accordion>

  <Accordion title="Приведение типов">
    Ответы API представлены в JSON, поэтому все значения приходят в виде строк или слабо типизированных числовых значений. BioETL приводит каждое поле к объявленному типу: числа в строковом представлении становятся `float64` или `int32`, строки дат ISO-8601 — столбцами `datetime[UTC]`, а булеподобные строки (`"Y"`/`"N"`) — типом `bool`. Ошибки приведения трактуются как ошибки валидации и направляют запись в карантин.
  </Accordion>

  <Accordion title="Стандартизация единиц измерения">
    Числовые значения активности приводятся к каноническим единицам там, где это допускает документация поставщика. Например, значения IC50, указанные в µM, сохраняются как nM, чтобы сравнения между поставщиками использовали единую базу. Карта единиц объявляется для каждой сущности в `configs/entities/{provider}/{entity}.yaml` в разделе `normalization.unit_map`.
  </Accordion>

  <Accordion title="Гармонизация null-значений">
    Специфичные для поставщика «маркерные» значения — `"None"`, `"-"`, `"N/A"`, пустые строки и определённые поставщиком коды отсутствующих значений — заменяются на корректные SQL-значения `null`. Это гарантирует, что проверки `is_null()` и правила обязательных полей ведут себя одинаково независимо от источника данных.
  </Accordion>

  <Accordion title="Извлечение вложенных полей">
    Некоторые поставщики возвращают глубоко вложенные поля JSON или поля-массивы. BioETL разворачивает настраиваемое подмножество таких полей в столбцы верхнего уровня при записи в Silver. Какие поля извлекаются, определяется параметром `normalization.flatten_fields` в YAML сущности. Поля, не указанные в списке, сохраняются в виде сериализованных JSON-строк для доступа на последующих этапах.
  </Accordion>
</AccordionGroup>

## Как работает валидация

Валидация выполняется **после нормализации** в двух точках конвейера:

1. **Bronze → Silver**: каждая нормализованная запись проверяется по схеме сущности и правилам уровня поля перед записью в таблицу Silver Delta Lake.
2. **Silver → Gold**: записи Silver фильтруются по любым специфичным для Gold предикатам перед записью в слой Gold.

Если запись не проходит проверку в любой из этих точек, она записывается в `data/output/quarantine/common.quarantine/` как запись таблицы Delta Lake. Запись содержит исходный полезный груз, причину ошибки, структурированный код ошибки и ссылку на запуск конвейера, который её породил.

### Типы правил валидации

| Тип правила | Ключ YAML | Что проверяется | Код ошибки |
| --- | --- | --- | --- |
| Схема / тип данных | _(неявно)_ | Столбец соответствует объявленному типу Pandera | `DQ-TYPE-ERROR` |
| Обязательное поле | `required: true` | Поле не равно null после нормализации | `DQ-MISSING-FIELD` |
| Числовой диапазон | `min` / `max` | Значение попадает в объявленные границы | `DQ-RANGE` |
| Допустимые значения | `allowed_values` | Категориальное поле соответствует одному из перечисленных значений | `DQ-ENUM` |
| Шаблон регулярного выражения | `pattern` | Строковое поле соответствует переданному регулярному выражению | `DQ-PATTERN` |
| Дедупликация | _(неявно)_ | Хэш SHA-256 от бизнес-ключа \+ полезного груза уникален | _(пропускается без сообщения)_ |

Дедупликация выполняется на этапе слияния Delta Lake: записи, чей хэш контента уже существует в Silver, пропускаются без ошибки, что делает каждый запуск конвейера полностью идемпотентным относительно одних и тех же данных Bronze.

## Трёхуровневая иерархия правил

Правила DQ организованы послойно, чтобы можно было задать разумные значения по умолчанию и переопределять их только там, где это нужно:

<Steps>
  <Step title="Глобальные значения по умолчанию">
    `configs/base/quality.yaml` определяет базовые правила, применяемые ко всем конвейерам. Они охватывают общие типы полей — проверки на null, границы диапазона, длины строк — и задают значения мягкого и жёсткого порогов по умолчанию.
  </Step>
  <Step title="Правила поставщика">
    `configs/providers/{provider}.yaml` может переопределять или расширять глобальные значения по умолчанию для конкретного поставщика. Например, записи активности ChEMBL имеют другие допустимые диапазоны значений, чем записи соединений PubChem.
  </Step>
  <Step title="Правила сущности">
    `configs/entities/{provider}/{entity}.yaml` содержит наиболее специфичные правила. Правила уровня сущности переопределяют как глобальные, так и специфичные для поставщика значения по умолчанию для этого отдельного конвейера.
  </Step>
</Steps>

Когда BioETL оценивает запись, он объединяет три уровня по порядку — глобальный → поставщик → сущность — так что наиболее специфичное правило всегда побеждает.

## Мягкие и жёсткие пороги

Две переменные окружения управляют тем, как BioETL реагирует на неуспешные записи:

| Переменная | По умолчанию | Значение |
| --- | --- | --- |
| `BIOETL_DQ_SOFT_THRESHOLD` | `0.05` | Выдать предупреждение, если в пакете не проходят более 5% записей |
| `BIOETL_DQ_HARD_THRESHOLD` | `0.20` | Прервать пакет, если не проходят более 20% записей |

Когда мягкий порог превышен, BioETL записывает предупреждение в журнал и продолжает обработку. Пакет всё равно завершается, и данные записываются.

Когда жёсткий порог превышен, BioETL прерывает пакет и завершается с **кодом выхода 83**. Для этого пакета частичные данные не записываются. Любой из порогов можно изменить без передеплоя:

```bash
# Снизить жёсткий порог, чтобы быстрее завершаться с ошибкой во время разработки
export BIOETL_DQ_HARD_THRESHOLD=0.10

bioetl run --pipeline chembl_activity
```

<Warning>
  Пакет, превысивший жёсткий порог, завершается с кодом 83. Если вы запускаете BioETL в скрипте или CI-задаче, проверяйте код выхода, чтобы обнаруживать сбои DQ: `if [ $? -eq 83 ]; then ...`.
</Warning>

## Отчёты DQ

После завершения каждого пакета BioETL записывает отчёт DQ в виде sidecar-файла JSON рядом с данными слоя:

- Bronze: `data/output/bronze/{provider}/{entity}/{date}/batch-{date}-{provider}-{entity}-dq-report.json`
- Silver: `data/output/silver/{provider}/{entity}/silver-{provider}-{entity}-dq-report.json`
- Gold: `data/output/gold/{provider}/{entity}/gold-{provider}-{entity}-dq-report.json`

Эти отчёты содержат разбивку по каждому полю с количеством успехов и неудач, применённые пороги и ссылку на запуск, который их породил.

## Карантинная таблица

Неуспешные записи попадают в единую карантинную таблицу Delta Lake по пути `data/output/quarantine/common.quarantine/`. Поскольку карантин — это таблица Delta Lake, её можно запрашивать с помощью Polars или любого Parquet-совместимого инструмента, а её история сохраняется между запусками.

Каждая карантинная запись хранит:

- Исходный полезный груз
- Причину сбоя, читаемую человеком
- Структурированные поля: `reason_code`, `rule_type`, `field`, `operator`, `expected`, `actual`
- Значения `pipeline` и `run_id`, породившие запись
- Временную метку `ingestion_ts`

## Просмотр карантинных записей

Используйте `bioetl quarantine inspect`, чтобы просматривать сбои конкретного конвейера:

```bash
# Показать первые 100 карантинных записей для chembl_activity
bioetl quarantine inspect --pipeline chembl_activity

# Фильтрация по коду ошибки
bioetl quarantine inspect --pipeline chembl_activity --error-code DQ-MISSING-FIELD

# Показать только отклонения фильтра Silver
bioetl quarantine inspect --pipeline chembl_activity --silver-filter-only

# Ограничить конкретным запуском
bioetl quarantine inspect --pipeline chembl_activity --run-id <run-id> --limit 20
```

Для агрегированных подсчётов вместо отдельных записей:

```bash
# Сводная статистика
bioetl quarantine stats --pipeline chembl_activity

# Разбивка по коду причины
bioetl quarantine stats --pipeline chembl_activity --silver-filter-only --group-by reason-code

# Разбивка по полю
bioetl quarantine stats --pipeline chembl_activity --silver-filter-only --group-by field
```

## Проверка конфигурации DQ

Перед запуском конвейера вы можете убедиться, что его правила DQ синтаксически корректны и внутренне согласованы:

```bash
# Проверить объединённую конфигурацию DQ для сущности
bioetl dq validate --entity chembl.activity

# Показать все вычисленные правила
bioetl dq validate --entity chembl.activity --show-rules

# Считать предупреждения ошибками
bioetl dq validate --entity chembl.activity --strict
```

## Повторная обработка и очистка карантинных записей

Если вы исправили правило преобразования или конфигурацию DQ, можно повторно прогнать карантинные записи через конвейер без повторной выгрузки из API:

```bash
# Показать, какие записи будут обработаны повторно
bioetl quarantine replay --pipeline chembl_activity --dry-run

# Повторно обработать записи не старше 7 дней
bioetl quarantine replay --pipeline chembl_activity --max-age-days 7
```

Чтобы удалить старые карантинные записи:

```bash
# Предпросмотр удаления
bioetl quarantine purge --pipeline chembl_activity --older-than-days 30 --dry-run

# Удалить записи старше 30 дней
bioetl quarantine purge --pipeline chembl_activity --older-than-days 30
```

По умолчанию карантинные записи хранятся 30 дней (`BIOETL_QUARANTINE_RETENTION_DAYS`).

## Коды выхода

| Код | Значение |
| --- | --- |
| `0` | Конвейер завершился успешно |
| `82` | Ошибка выполнения конвейера |
| `83` | Превышен жёсткий порог DQ — пакет прерван |
| `84` | Не удалось получить блокировку |
| `86` | Сетевая ошибка |
| `130` | Прервано (Ctrl\+C) |

<Tip>
  Используйте `bioetl diagnostics --quarantine`, чтобы получить единое представление статистики карантина вместе с метриками конвейера и проверками работоспособности.
</Tip>
