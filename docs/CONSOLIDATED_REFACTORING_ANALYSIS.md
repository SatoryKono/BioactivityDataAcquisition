## Часть 4. Консолидированный План Рефакторинга

### 4.1. Приоритет 1 (P1): КРИТИЧЕСКИЕ

#### P1.1: Исправить mypy ошибки

**Статус**: Требуется
**Влияние**: Блокирует CI, снижает уверенность в типизации.

| Параметр | Значение |
|----------|----------|
| Текущее состояние | 27 ошибок `mypy --strict` |
| Целевое состояние | 0 ошибок |
| Файлы | По результатам `mypy --strict` |
| Трудозатраты | S-M (1-2 дня) |
| Критерий готовности | `mypy --strict` проходит без ошибок |

#### P1.2: Запретить Parquet в sink config

**Статус**: Требуется
**Влияние**: Нарушает RULES.md §2.1 (Silver/Gold — только Delta).

| Параметр | Значение |
|----------|----------|
| Текущее состояние | `format: Literal["jsonl", "delta", "parquet"]` |
| Целевое состояние | `format: Literal["jsonl", "delta"]` для Silver/Gold |
| Файлы | `src/bioetl/infrastructure/schemas/pipeline_config.py:151` |
| Трудозатраты | S (0.5 дня) |
| Критерий готовности | Валидация отклоняет `format: parquet` для Silver/Gold |

#### P1.3: Добавить Safety Guard для блокировок

**Статус**: Требуется
**Влияние**: Риск split-brain при параллельных записях.

| Параметр | Значение |
|----------|----------|
| Текущее состояние | `MemoryLock` хранит `owner_id`, но Delta writers не проверяют его |
| Целевое состояние | `DeltaWriter`/`GoldWriter` проверяют owner_id перед записью |
| Файлы | `memory_lock.py`, `delta_writer.py`, `gold_writer.py` |
| Риски | Ложные отказы при некорректном wiring |
| Трудозатраты | M (2-3 дня) |
| Критерий готовности | Тест: запись без lock или с чужим owner_id → ошибка |

### 4.2. Приоритет 2 (P2): ВЫСОКИЙ

#### P2.1: Автоматизировать VACUUM (планировщик)

**Статус**: Частично реализовано
**Влияние**: Накопление мусора в Delta tables.

| Параметр | Значение |
|----------|----------|
| Текущее состояние | `MedallionLifecycleService.vacuum()` существует, но нет автоматического вызова |
| Целевое состояние | VACUUM вызывается после успешного run (настраивается в YAML) |
| Файлы | `medallion_lifecycle.py`, `runner.py`, `pipeline_config.py` |
| Риски | Удаление нужных файлов при неверной конфигурации |
| Трудозатраты | M (2 дня) |
| Критерий готовности | После run с `maintenance.auto_vacuum: true` выполняется VACUUM |

> **Примечание**: Конфиг `MaintenanceConfig` уже существует в `pipeline_config.py:92-111`.

#### P2.2: Унифицировать NoOp паттерн

**Статус**: Желательно (НЕ ошибка)
**Влияние**: Консистентность DI, упрощение тестирования.

| Параметр | Значение |
|----------|----------|
| Текущее состояние | Writers создают NoOp внутри конструктора |
| Целевое состояние | NoOp создаётся в composition layer и инжектируется |
| Файлы | `gold_writer.py:86-89`, `bronze_writer.py` |
| Риски | Ломающие изменения API |
| Трудозатраты | M (2 дня) |
| Критерий готовности | Нет `import NoOp*` в infrastructure/storage/ |

> ⚠️ **Важно**: Это **улучшение**, не исправление ошибки. Null Object Pattern — валидный паттерн.

### 4.3. Приоритет 3 (P3): СРЕДНИЙ

#### P3.1: Очистить print() из docstrings

**Статус**: Желательно
**Влияние**: Соответствие grep-проверкам в CI.

| Параметр | Значение |
|----------|----------|
| Текущее состояние | 13 вхождений print() в docstring/примерах |
| Целевое состояние | 0 вхождений или whitelist в grep |
| Файлы | `domain/resilience.py`, `composition/entrypoints.py`, `infrastructure/config.py` и др. |
| Трудозатраты | S (0.5 дня) |
| Критерий готовности | `grep -r "print(" src/bioetl` → 0 или в whitelist |

#### P3.2: Добавить Redis Lock (опционально)

**Статус**: Требуется для production с несколькими workers
**Влияние**: Распределённая блокировка для масштабирования.

| Параметр | Значение |
|----------|----------|
| Текущее состояние | Только `MemoryLock` (single-process) |
| Целевое состояние | `RedisLock` с SETNX+EXPIRE, heartbeat |
| Файлы | `infrastructure/locking/redis_lock.py` (новый) |
| Риски | Зависимость от Redis, сложность тестирования |
| Трудозатраты | M (3 дня) |
| Критерий готовности | Integration test с Redis проходит |

> **Примечание**: Для локального development `MemoryLock` достаточен.
