## 3. Детальный анализ архитектуры

### 3.1. Соблюдение слоистой структуры
Проверка кода (`src/bioetl/application` и `src/bioetl/domain`) показала строгое соблюдение Dependency Inversion Principle.
*   **Domain**: Чистый Python, использует `typing.Protocol` для определения портов (например, `DataSourcePort`). Не зависит от инфраструктуры.
*   **Application**: Содержит бизнес-логику пайплайнов (`BasePipeline`). Зависит только от `Domain`. Инфраструктурные компоненты (логгер, клиенты) инжектируются через конструктор.
*   **Infrastructure**: Реализует порты (`UnifiedHTTPClient`, `BaseSyncAdapter`).
*   **Composition**: (`bootstrap.py`, `factories/`) Корректно связывает слои, выступая в роли "Composition Root".

### 3.2. Принципы Ports & Adapters и DDD
*   Используются **Rich Domain Models** (`entities.py` с валидацией в `__post_init__`).
*   **Адаптеры** четко отделены от бизнес-логики.
*   **GenericPipelineFactory** позволяет декларативно собирать пайплайны, минимизируя дублирование кода.

### 3.3. Выявленные (незначительные) проблемы
1.  **Сложность Фабрик**: `GenericPipelineFactory` и `ServicesBuilder` берут на себя много ответственности по сборке. Это оправдано паттерном Composition Root, но требует внимательного сопровождения.
2.  **Повторное использование Config**: Логика загрузки конфигов (`load_pipeline_config`) используется в нескольких местах, хотя централизована в `bootstrap`. Стоит следить за тем, чтобы `RuntimeConfig` не разрастался.

## 4. План рефакторинга

Учитывая высокую оценку, план фокусируется на **Governance** (управление правилами) и **Optimization**, а не на исправлении критических ошибок.

### Приоритет 1: Усиление архитектурного контроля (Governance)
**Цель:** Автоматически предотвращать регрессию архитектуры при добавлении новых пайплайнов.

1.  **Расширение архитектурных тестов (`tests/architecture/`)**
    *   *Действие*: Добавить тесты на базе `import-linter` или анализа AST, запрещающие импорт `infrastructure` в `application` (сейчас это правило "на бумаге", нужен жесткий тест в CI).
    *   *Критерий*: CI падает, если в PR добавлен неверный импорт.

2.  **Заморозка API Портов**
    *   *Действие*: Проверить все Protocols в `domain/ports.py`. Убедиться, что методы имеют строгую типизацию и документацию.
    *   *Критерий*: Все публичные методы портов имеют docstrings и type hints.

### Приоритет 2: Оптимизация производительности и ресурсов
**Цель:** Улучшить эффективность обработки данных для крупных источников (ChEMBL, PubChem).

3.  **Оптимизация `BronzeWriter`**
    *   *Действие*: Проверить использование памяти при сжатии ZSTD. Убедиться, что используется потоковая запись (streaming) везде, где возможно, чтобы избежать загрузки всего батча в RAM.
    *   *Критерий*: Профилирование памяти показывает стабильное потребление при обработке батчей >100MB.

### Приоритет 3: Улучшение Developer Experience
**Цель:** Упростить создание новых пайплайнов для новых разработчиков.

4.  **Генератор шаблонов (Scaffolding)**
    *   *Действие*: Создать скрипт `src/tools/create_pipeline.py`, который генерирует файлы (конфиг, трансформер, тест) на основе шаблонов из `docs/templates/`.
    *   *Критерий*: Команда `make new-pipeline name=xyz` создает работающую заготовку.

## 5. Метрики и контроль качества

Для поддержания рейтинга >9.0 рекомендуется отслеживать следующие метрики:

1.  **Coverage**: Удерживать Line Coverage > 90% (Domain), > 80% (Infrastructure).
2.  **Architectural Violations**: 0 (контролируется линтерами).
3.  **Cyclomatic Complexity**: Не допускать функций сложнее 10 (кроме фабрик).
4.  **Build Time**: Время прогона тестов < 5 минут (использовать `pytest-xdist` при росте базы тестов).

**Связь с интегральным баллом:**
Реализация пункта 1 (Архитектурные тесты) закрепит оценку "Архитектура слоёв" на уровне 10. Реализация пункта 3 (Оптимизация Writer) может поднять оценку "Производительность" с 8 до 9.
