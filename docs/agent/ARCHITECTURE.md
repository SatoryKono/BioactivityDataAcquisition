# Навыки Архитектуры BioETL

Этот документ описывает архитектурные стандарты и паттерны, обязательные для использования в проекте BioETL.

## 1. Архитектурный Стиль: Гексагональная Архитектура (Ports & Adapters)
Проект строго следует принципам гексагональной архитектуры для обеспечения слабой связности и тестируемости.

### Основные слои:
1.  **Domain (Домен):** `src/bioetl/domain`
    *   **Ответственность:** Чистая бизнес-логика, правила, сущности, Value Objects.
    *   **Запрещено:** Любые внешние зависимости (HTTP, SQL, файловая система), импорты из `infrastructure` или `application`.
    *   **Интерфейсы:** Определяет порты (Protocol) для взаимодействия с внешним миром (например, `StoragePort`, `MetricsPort`).

2.  **Application (Приложение):** `src/bioetl/application`
    *   **Ответственность:** Оркестрация бизнес-процессов (Use Cases/Pipelines).
    *   **Компоненты:** Пайплайны (`Pipeline`), Сервисы (`ValidationService`), Обработчики команд.
    *   **Правила:** Импортирует `domain`. Не зависит от конкретных реализаций `infrastructure`. Использует внедрение зависимостей (DI).

3.  **Infrastructure (Инфраструктура):** `src/bioetl/infrastructure`
    *   **Ответственность:** Реализация портов, определенных в домене. Работа с БД, API, файловой системой.
    *   **Компоненты:** Адаптеры (`S3Checkpoint`, `PubChemClient`), Репозитории.
    *   **Правила:** Импортирует `domain` (для реализации интерфейсов). **Строго запрещено** импортировать `application`.

4.  **Interfaces (Интерфейсы ввода/вывода):** `src/bioetl/interfaces`
    *   **Ответственность:** Точки входа в приложение.
    *   **Компоненты:** CLI (`src/bioetl/interfaces/cli.py`), API, Tasks (Prefect).
    *   **Composition Root:** Здесь происходит сборка приложения и внедрение зависимостей (см. `bootstrap.py`).

## 2. Dependency Injection (DI) и Composition Root
*   **Принцип:** Компоненты не создают свои зависимости, а получают их извне.
*   **Composition Root:** Модуль `src/bioetl/interfaces/bootstrap.py` является единственным местом, где "сшиваются" слои. Здесь инициализируются адаптеры инфраструктуры и передаются в фабрики уровня приложения.
*   **Фабрики:** Используйте фабрики (`src/bioetl/interfaces/factories/`) для создания сложных объектов пайплайнов, изолируя логику создания от логики выполнения.

## 3. Принципы DDD (Domain-Driven Design)
*   **Ubiquitous Language:** Используйте терминологию предметной области (Activity, Assay, Target) во всем коде.
*   **Bounded Contexts:** Четко разделяйте контексты (например, контекст "Валидации" vs контекст "Загрузки").
*   **Value Objects:** Используйте неизменяемые объекты-значения для типизации (например, `MolWeight`, `Doi`).

## 4. Специфические Правила
*   **Логирование:** Используйте `structlog`. В доменном слое используйте `BoundLogger` (Duck Typing), не импортируйте конкретные логгеры инфраструктуры.
*   **Конфигурация:** Настройки передаются через Pydantic-модели (`PipelineConfig`), а не через глобальные переменные или прямые вызовы `get_settings()` в глубине кода.
*   **Асинхронность:** Блокирующие операции (Delta Lake, Pandera) должны выполняться в executor (`loop.run_in_executor`), чтобы не блокировать Event Loop.
*   **Обработка ошибок:** Используйте иерархию типизированных исключений из `src/bioetl/domain/exceptions.py`.

## 5. Аудит и Рефакторинг
*   При изменении архитектуры обновляйте `AUDIT_REPORT.md` и диаграммы в `docs/02-architecture/`.
*   Соблюдайте правила `import-linter` (конфигурация в `.importlinter`).
