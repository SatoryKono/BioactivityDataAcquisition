# Навыки Документации BioETL

Этот документ описывает стандарты документирования ("Docs-as-Code") в проекте BioETL.

## 1. Общие принципы
*   **Язык:** Русский. Весь код (комментарии, докстринги) и документация пишутся на русском языке.
*   **Docs-as-Code:** Документация живет в репозитории вместе с кодом. Изменения в коде **обязаны** сопровождаться изменениями в документации.
*   **Единый источник истины:** Файл `RULES.md` является главным регламентирующим документом. Все спорные моменты решаются через него.

## 2. Структура документации (`docs/`)
*   `00-project_rules/`: Глобальные правила проекта.
*   `02-architecture/`: Архитектурные решения (ADR), схемы данных, диаграммы.
*   `03-guides/`: Руководства разработчика (как добавить источник, как запустить тесты).
*   `04-reference/`: Справочная информация по пайплайнам, метрикам, конфигам.
*   `AUDIT_REPORT.md`: Отчет об аудите кодовой базы, долгах и оценке качества.
*   `IMPLEMENTATION_ROADMAP.md`: Планы развития и текущий статус задач.

## 3. Форматы и Инструменты
*   **Markdown:** Основной формат. Используйте четкую структуру заголовков.
*   **Mermaid:** Для диаграмм (классы, последовательности, компоненты) используйте синтаксис Mermaid.js.
    *   Пример: `classDiagram`, `sequenceDiagram`, `flowchart TD`.
*   **Docstrings:** Формат Google Style (на русском). Обязательно описывайте `Args`, `Returns`, `Raises`.

## 4. Процесс работы с документацией
1.  **Планирование:** Перед написанием кода, актуализируйте план в голове или в `IMPLEMENTATION_ROADMAP.md`.
2.  **Рефакторинг:** При изменении логики обновляйте соответствующие разделы в `docs/`. Если меняется схема данных, обновите контракт в `docs/contracts/`.
3.  **Аудит:** Если пользователь просит аудит, результат записывается в `AUDIT_REPORT.md` перед внесением правок в код.
4.  **Правила:** Если вы вводите новое архитектурное правило, добавьте его в `RULES.md`.

## 5. Особенности коммуникации
*   Ответы должны быть сухими, структурированными и техническими.
*   Используйте списки, заголовки и TL;DR для длинных текстов.
*   Избегайте общих фраз, пишите конкретику.

## 6. Deprecation Policy
*   При устаревании функционала используйте workflow:
    1.  Пометить как `deprecated` (Warning).
    2.  Двойная запись (старое + новое) в течение 2 недель (для полей данных).
    3.  Удаление и мажорный бамп версии.
