## 2. Оценка архитектуры по ключевым критериям

*   **Соблюдение слоёв:** Присутствуют нарушения. Хотя формально пакеты разделены (domain/application/infrastructure/interfaces), бизнес-логика и правила валидации иногда просачиваются в слой `infrastructure` (например, в парсерах), а инфраструктурные концепции (типы файлов, БД) упоминаются в `application`.
*   **Соответствие Ports & Adapters (Hexagonal) и DDD:** В целом реализовано неплохо. Паттерн ABC/Default/Impl используется активно, однако выявлено избыточное применение интерфейсов там, где существует лишь одна реализация. Выделение Value Objects (например, `ActivityConfidence`, `PublicationYear`) является сильной стороной.
*   **Явность границ модулей и зависимостей:** Использование Dependency Injection via constructors соблюдается (Service Locators запрещены), что делает зависимости явными. Однако высокая связность между модулями-трансформерами и специфичными конфигурациями `provider/entity` усложняет переиспользование.
*   **Единообразие нейминга, структуры пакетов и файлов:** В проекте применяется строгая конвенция (PascalCase для классов, snake_case для модулей), но историческое развитие привело к наличию порядка 350+ классов (сейчас в процессе сокращения до 220).

## 3. Ключевые проблемы (Technical Debt)

1.  **Утечки абстракций и нарушения границ слоев:** Часть трансформаций (DTO mapping) выполняется слишком близко к уровню извлечения (infrastructure API adapters).
2.  **Дублирование и God Objects:** Большое количество базовых трансформеров (BaseTransformer) с избыточной логикой, которая должна быть вынесена в специализированные Policy или Strategy классы. Встречаются методы с высокой цикломатической сложностью (риск нарушения C901).
3.  **Смешение конфигурации и бизнес-логики:** Некоторые пайплайны жестко связаны со структурой YAML-конфигураций (batch_size, merge strategies), усложняя тестирование логики в изоляции от парсера конфигов.
4.  **Избыточные абстракции (Over-engineering):** Множество портов и ABC классов имеют только одну реализацию, что увеличивает объем кода (boilerplate) без реальной пользы для расширяемости.

## 4. План рефакторинга

Ниже представлен детализированный план архитектурного рефакторинга (от наиболее критичных до желательных), направленный на снижение связности, упрощение структуры классов и повышение тестируемости.

### Шаг 1. Унификация и консолидация конфигурационных классов (Critical)
**Цель:** Устранить дублирование в парсинге конфигураций пайплайнов и разделить инфраструктурные параметры от доменных.
**Конкретные правки:**
*   Рефакторинг классов в `src/bioetl/domain/config/` (например, слияние `pipeline.py` и `base_provider.py`).
*   Внедрение единого `PipelineConfigReader` в инфраструктурном слое, который возвращает иммутабельные доменные структуры (dataclasses/pydantic).
**Риски:** Поломка существующих пайплайнов из-за изменения схемы конфигурации.
**Минимизация рисков:** Использование тестов `test_config_golden_master.py` (с `UPDATE_SNAPSHOTS=0`) для контроля обратной совместимости.
**Definition of Done (DoD):** Все конфигурационные классы используют единый базовый класс; архитектурные тесты проходят; количество конфиг-классов уменьшено на 30%.

### Шаг 2. Упрощение портов и избыточных интерфейсов (High)
**Цель:** Удалить интерфейсы (ABC), имеющие только одну реализацию, для упрощения навигации и снижения кодовой базы.
**Конкретные правки:**
*   Аудит `src/bioetl/domain/ports/`. Инлайнинг единственных реализаций (например, некоторых MetadataCoordinator).
*   Замена паттерна `ABC/Impl` на прямые классы для внутренних сервисов пайплайнов (оставляя порты только для внешних систем: API, Storage).
**Риски:** Ослабление слабой связанности (loose coupling).
**Минимизация рисков:** Применение `DeprecationWarning` для старых импортов на переходный период; сохранение DI через конструкторы.
**Definition of Done (DoD):** Модули `infrastructure/adapters` ссылаются на упрощенные доменные классы; удалено не менее 15 мертвых интерфейсов; тесты проходят.

### Шаг 3. Рефакторинг трансформеров и устранение God Objects (High)
**Цель:** Разбить громоздкие классы в `src/bioetl/application/core/base_transformer/` и `src/bioetl/application/pipelines/` на меньшие, фокусирующиеся на одной задаче (Single Responsibility Principle).
**Конкретные правки:**
*   Выделение логики валидации и нормализации (например, `NormalizationServiceABC`) из базовых трансформеров в отдельные Strategy классы.
*   Применение композиции (Composition) вместо глубокого наследования (Inheritance) для пайплайнов ChEMBL, PubMed и OpenAlex.
**Риски:** Нарушение работы сложных ETL-процессов, превышение лимитов памяти при батч-обработке.
**Минимизация рисков:** Покрытие старых классов Golden тестами перед расщеплением. Строгое отслеживание `batch_memory_manager`.
**Definition of Done (DoD):** Ни один метод трансформеров не имеет C901 > 10; классы разбиты; размер файлов соответствует лимитам без новых исключений в `architecture_metric_exemptions.yaml`.

### Шаг 4. Оптимизация производительности (Medium)
**Цель:** Ускорить узкие места в пайплайнах (парсинг дат, строковые операции, батчинг).
**Конкретные правки:**
*   Замена `datetime.strptime` на прямое извлечение для формата ISO-8601 во всех модулях парсинга.
*   Замена кастомных итераций строк на `str.isascii()` и regex (согласно Bolt-директивам).
*   Рефакторинг `v.as_py()` в list comprehensions с использованием walrus operator.
**Риски:** Некорректный парсинг краевых случаев (edge cases).
**Минимизация рисков:** Использование `pytest.mark.parametrize` для всестороннего тестирования утилит (например, в `title_matching.py` и `_date_helpers.py`).
**Definition of Done (DoD):** Бенчмарки показывают ускорение не менее 20% на профильных функциях; unit-тесты для краевых случаев добавлены.

### Шаг 5. Строгое выравнивание слоёв и перенос логики DTO (Medium)
**Цель:** Обеспечить строгую однонаправленную зависимость `Infrastructure -> Application -> Domain`.
**Конкретные правки:**
*   Перемещение маппинга внешних API ответов (infrastructure) из доменного слоя. Домен должен оперировать только абстрактными `BatchRecord` или Entity.
*   Очистка `application` от прямых упоминаний форматов (например, XML в PubMed).
**Риски:** Дублирование моделей на границах слоев.
**Минимизация рисков:** Использование Pandera схем для автоматической валидации на границах.
**Definition of Done (DoD):** Инструмент `importlinter` или `dependency_map_drift_check` не показывает обратных зависимостей; чистота слоёв подтверждена архитектурными тестами.

## 5. Метрики и контроль регрессий

Для контроля качества после реализации плана необходимо отслеживать следующие метрики (привязанные к 10 категориям):

1.  **C901 Violation Count (Категория 4):** Должно оставаться на уровне 0 для нового и измененного кода (скрипт `scripts/qa/check_c901_baseline.py`).
2.  **LOC per File (Категория 4):** Количество исключений в `architecture_metric_exemptions.yaml` должно уменьшиться минимум на 20%.
3.  **Test Coverage (Категория 6):** Доменная логика (Domain) стабильно `>90%`, общее покрытие системы `>85%`.
4.  **Class Count / Interfaces Count (Категория 2, 5):** Целевое сокращение общего числа классов до ~220. Метрика отслеживается через `grep -r "class " src/bioetl | wc -l`.
5.  **Architecture Drift Score (Категория 1):** Скрипт `scripts/qa/generate_architecture_dependency_map.py --update` должен показывать 0 неавторизованных связей между слоями.
6.  **Performance Check (Категория 9):** Время выполнения парсинга крупных батчей сокращено, отсутствие OOM ошибок.

**Ожидаемый результат:** После выполнения всех 5 шагов плана, интегральный балл проекта возрастет с текущих `6.60` до стабильных `8.5+` (хорошее состояние), что позволит быстрее внедрять новые источники данных (например, OpenAlex).
