# Черновик спецификации инструментирования фаз (0.3)

## 1. Выбор целевых суит
На основе результатов [CI1-01](#12828) (отчет `docs/reports/audit/phase-profile-41570319793.md`), для инструментирования выбраны топ-3 кандидата с наибольшим временем выполнения:
1. `tooling-other` (320.5s)
2. `integration` (233.2s)
3. `repo-backed-tooling` (125.6s)

Эти суиты дают наибольший потенциал для выявления узких мест на этапах setup/call/teardown.

## 2. Форма новых артефактов
- **Формат**: JSON.
- **Содержание**. Время collection, длительности setup/call/teardown по каждому тесту и отдельные измерения setup фикстур с идентификатором, областью действия и длительностью. Queue time, если доступно, записывается отдельно.
- **Источник**. Использовать пассивный pytest-плагин по образцу `.github/workflows/stage0-phase-profile.yml`. Обёртки `pytest_collection` и `pytest_fixture_setup` измеряют collection и setup фикстур монотонным таймером. `pytest_runtest_logreport` собирает `nodeid`, фазу, исход и длительность теста. `pytest_sessionfinish` записывает `collection_s`, `reports` и `fixture_setup_calls` в `phases.json`. Отдельный `execution.json` хранит длительность команды `elapsed_s` и происхождение запуска. Фазы call и teardown теста остаются измерениями теста.
- **Retention**: Срок хранения сырых артефактов должен соответствовать стандартной политике CI для артефактов телеметрии (90 дней, если не указано иное).

## 3. Изменения workflow (Отрицательные требования)
В рамках инструментирования **ЗАПРЕЩАЕТСЯ**:
- Изменять существующие `needs` или условия успеха (success criteria).
- Менять пороги качества (thresholds), тайм-ауты или baseline-файлы.
- Менять профиль покрытия тестами (coverage-profile).
- Менять членство тестов в суитах (test membership).
- Изменять код или логику самих тестов.

Разрешено **ТОЛЬКО** добавление новых шагов (сбора и публикации артефактов) с условием `if: always()`, чтобы профилирование выполнялось независимо от успеха/провала предыдущих шагов в джобе.

## 4. Проверка после внедрения
- **Сравнение полноты**. Для каждого последовательного запуска pytest сверять `elapsed_s` этой команды с суммой `collection_s + setup + call + teardown` из того же запуска. Остаток записывать отдельно как время, не отнесённое к измеренным фазам. Длительности setup отдельных фикстур уже входят в setup тестов и повторно не суммируются. Для параллельного исполнения суммарное время фаз по воркерам и прошедшее время команды показываются раздельно. Время всего workflow и очередь не входят в сверку.
- **Происхождение (Provenance)**: Каждый сгенерированный артефакт обязан фиксировать свое происхождение: `run_id`, `attempt`, `sha` (commit hash). Эта метаинформация должна быть валидна и не допускает зануления.

**Входные данные**: JSON-артефакты телеметрии из инструментированных workflow.

**Шаги эксперимента**:

## 6. Оценка Blast Radius
- **Workflow**: Добавление новых шагов с `if: always()` локализовано только в конфигурациях GitHub Actions для 3 указанных job'ов. Ожидается минимальное увеличение общего времени работы workflow (wall-time) из-за накладных расходов на генерацию и загрузку артефактов. Риск падения основного пайплайна отсутствует благодаря изоляции шагов и отсутствию изменений в логике.
- **Документация**: Добавляется только данный черновик спецификации и (в будущем) обновленные baseline-отчеты.
- **Кодовая база**: Без изменений. Ни один файл исходного кода или тестов не затронут.
