# RF-016 Final Plan

Date: 2026-03-17

## RF-016: Config Schema and Legacy Seam Convergence

RF-016 — это не “вторая попытка RF-008” и не общий cleanup всего `configs/` слоя. Это волна конвергенции между runtime reality, JSON schemas, Python schema models, CI invariants, golden snapshots и active documentation. Текущий pipeline/runtime слой уже значительно ближе к canonical-first модели, но основной хвост теперь сидит в другом месте: разные уровни системы по-разному отвечают на вопрос, что именно считается текущим canonical config path, а что уже должно считаться legacy seam или migration-only behavior.

Сейчас это особенно заметно по трём поддоменам:

- pipeline schema/runtime surface;
- source schema/runtime surface;
- composite schema хвост, где ещё остаются legacy shape references.

Текущий baseline:

- `configs/_schema/pipeline.json` всё ещё содержит `column_groups_file`, `schema_file`, `data_schema_file`, а также transitional `filter_batch_size` и `page_size_override`;
- `configs/_schema/composite.json` всё ещё содержит `column_groups_file`;
- `src/bioetl/infrastructure/schemas/source_config.py` всё ещё поддерживает legacy pagination promotion через:
  - `batch_size`
  - `page_size`
  - `max_url_length`
- `src/bioetl/infrastructure/schemas/source_config_pagination_helpers.py` напрямую реализует legacy promotion path;
- `configs/_schema/source.json` всё ещё рекламирует deprecated source pagination fields как часть schema surface;
- tests и snapshots всё ещё поддерживают equivalence между legacy and new source payloads.

Это означает, что RF-016 должен решать не только вопрос “что удалить”, но и вопрос “что ещё остаётся допустимым transition seam и как это честно описать”.

## 1. Scope Lock и декомпозиция на три поддомена

Первый шаг — зафиксировать scope. RF-016 не должен расползаться в broad config refactor и не должен трогать unrelated config semantics вроде DQ business rules, provider-specific extraction logic или merge semantics composites. Его правильный scope:

- `pipeline` schema/model/tests/docs convergence;
- `source` schema/model/tests/docs convergence;
- `composite` schema cleanup only where legacy shape is still advertised.

Это значит, что ключевые файлы задачи:

- `configs/_schema/pipeline.json`
- `configs/_schema/composite.json`
- `configs/_schema/source.json`
- `src/bioetl/infrastructure/schemas/pipeline_config.py`
- `src/bioetl/infrastructure/schemas/source_config.py`
- `src/bioetl/infrastructure/schemas/source_config_pagination_helpers.py`
- `src/bioetl/infrastructure/config_loader.py`
- `tests/architecture/test_config_ci_invariants.py`
- `tests/architecture/test_config_strict_keys.py`
- `tests/architecture/test_config_golden_master.py`
- `tests/unit/infrastructure/config/test_source_config_legacy_normalization.py`
- `tests/unit/infrastructure/config/test_source_normalizers.py`

Риски:

- задача превратится в “исправить все config-related проблемы”;
- broad churn сделает verify дорогим и неясным.

Минимизация:

- любые изменения вне этих зон считать новой задачей;
- особенно жёстко не лезть в unrelated provider business semantics.

Definition of Done:

- scope трёх поддоменов зафиксирован;
- нет расползания в unrelated config cleanup.

## 2. Классификация полей по статусу, а не механическое удаление

Главная ошибка в RF-016 была бы такой: увидеть в schema поле с пометкой deprecated и сразу удалить его. Это слишком грубо. Сначала для каждого legacy-looking поля нужно формально определить статус:

- `retire now`: поле больше не должно существовать ни в schema, ни в runtime, ни в active docs;
- `transitional but supported`: поле ещё поддерживается, но должно быть явно описано как legacy/migration-only;
- `canonical current contract`: поле остаётся, даже если пришло из migration wave.

На текущем baseline:

- к `retire now` почти наверняка относятся:
  - `schema_file`
  - `data_schema_file`
  - `column_groups_file`
  в pipeline schema;
- к `transitional but supported` сейчас, вероятно, относятся:
  - `filter_batch_size`
  - source pagination legacy aliases `batch_size`, `page_size`, `max_url_length` в provider config;
- к `canonical current contract` пока относится:
  - `page_size_override`

Это различие важно. Если смешать эти статусы, можно случайно удалить поддерживаемый путь или, наоборот, продолжить рекламировать уже retired field как обычную часть публичного контракта.

Риски:

- неправильная классификация сломает YAML corpus или tests;
- transitional field будет случайно задокументирован как canonical.

Минимизация:

- опираться на фактические Pydantic models, architecture tests и grep по configs;
- не принимать решение на уровне одной schema file изолированно.

Definition of Done:

- для каждого проблемного поля утверждён target status;
- дальнейшие изменения делаются уже не вслепую.

## 3. Привести pipeline JSON schema к фактическому runtime contract

Первый implementation cluster RF-016 — pipeline layer. В `configs/_schema/pipeline.json` сегодня остаются file-reference поля, которые выглядят как незавершённый legacy seam:

- `column_groups_file`
- `schema_file`
- `data_schema_file`

Если pipeline runtime уже не должен принимать или рекламировать эти fields как normal path, JSON schema не имеет права оставлять их как обычные supported properties. Это основной смысл RF-016: schema должна перестать врать о current contract.

При этом нужно аккуратно обращаться с:

- `filter_batch_size`
- `page_size_override`

Если `filter_batch_size` ещё остаётся supported transition field, schema должна явно показывать его как deprecated transition only, а не как равноправную часть active API. Если `page_size_override` — это текущая intentional часть дизайна, schema должна сохранять его как canonical current field и не смешивать с legacy.

Конкретные правки:

- убрать или переоформить `schema_file`, `data_schema_file`, `column_groups_file` из `pipeline.json`;
- проверить descriptions `filter_batch_size` и `page_size_override`;
- убедиться, что schema wording совпадает с policy decisions.

Риски:

- schema станет строже раньше, чем runtime/tests готовы;
- documentation drift сохранится, но уже в другую сторону.

Минимизация:

- править pipeline JSON schema только после classification matrix;
- сразу синхронизировать это с model/tests.

Definition of Done:

- `pipeline.json` больше не рекламирует retired file-reference fields как часть canonical model.

## 4. Синхронизировать `PipelineYamlConfig`, CI invariants и strict-keys tests

После изменения `pipeline.json` нельзя оставлять в старом виде:

- `src/bioetl/infrastructure/schemas/pipeline_config.py`
- `tests/architecture/test_config_ci_invariants.py`
- `tests/architecture/test_config_strict_keys.py`
- `tests/architecture/test_config_golden_master.py`

Сейчас `PIPELINE_ALLOWED_KEYS` уже не содержит retired file-reference fields, и это хороший сигнал. Но RF-016 должен добиться полной согласованности:

- JSON schema говорит одно;
- Pydantic model говорит то же самое;
- CI invariants и strict-keys tests enforce-ят тот же policy;
- golden master snapshots не держат старую shape silently.

Особенно важно не сломать intentional contract вокруг `page_size_override`, если он сохраняется, и не забыть про transitional `filter_batch_size`, если его ещё нельзя retire-ить в этой волне.

Риски:

- schema/model/tests останутся partially aligned;
- snapshots будут мешать convergence и давать ложное чувство стабильности.

Минимизация:

- каждое изменение в schema сопровождается синхронной правкой model/tests;
- snapshots review делать осмысленно, а не механически.

Definition of Done:

- pipeline JSON schema, `PipelineYamlConfig`, CI invariants и strict-keys tests согласованы между собой.

## 5. Принять policy-решение по source pagination legacy support

Это самый рискованный и самый важный подшаг RF-016. В source layer current code одновременно утверждает, что pagination — single source of truth, и при этом всё ещё принимает legacy aliases через:

- `src/bioetl/infrastructure/schemas/source_config.py`
- `src/bioetl/infrastructure/schemas/source_config_pagination_helpers.py`
- `configs/_schema/source.json`
- `tests/unit/infrastructure/config/test_source_config_legacy_normalization.py`
- `tests/unit/infrastructure/config/test_source_normalizers.py`

RF-016 должен сначала принять policy-решение:

1. либо legacy pagination support сохраняется ещё на один цикл как migration-only seam;
2. либо source `pagination` объявляется единственным supported canonical path и legacy promotion начинает retire-иться staged way.

Пока это решение не принято, нельзя корректно менять ни schema, ни model, ни docs.

Если support сохраняется:

- schema и docs должны честно назвать эти поля deprecated migration-only;
- tests должны подтверждать именно migration seam, а не равноправную dual-path model.

Если support retire-ится:

- изменения идут staged path и никогда не начинаются с удаления helpers.

Риски:

- удалить support слишком рано и сломать provider configs/tests;
- оставить support, но продолжить рекламировать его как normal API.

Минимизация:

- сначала policy decision, потом code/schema edits;
- перед decision смотреть реальный config corpus и current tests.

Definition of Done:

- source pagination policy больше не двусмысленен;
- schema/model/tests/docs знают один и тот же status каждого source field.

## 6. Если source legacy seam retire-ится, удалить promotion path поэтапно

Если на предыдущем шаге принято решение на retirement, то порядок должен быть строгим:

1. перевести provider configs и test fixtures на canonical `pagination`;
2. переписать tests, которые сейчас проверяют equivalence legacy/new payloads;
3. только потом чистить `source_config.py`;
4. затем сжимать или удалять `source_config_pagination_helpers.py`;
5. после этого синхронизировать `source.json`;
6. обновить docs.

Нельзя начинать с удаления `_promote_legacy_pagination()` и helper functions, потому что тогда сломается и runtime, и snapshot/test layer, а policy drift станет только сильнее.

Если же policy — сохранить seam ещё на цикл, этот шаг превращается в мягкую конвергенцию:

- helper path остаётся;
- schema/doc wording становится migration-only;
- tests отражают именно migration seam, а не normal public API.

Риски:

- half-migrated state: docs уже canonical-only, а runtime ещё silently promotes legacy keys;
- source schema/model расходятся сильнее после частичной чистки.

Минимизация:

- соблюдать fixed sequence `configs/tests -> model/helpers -> schema -> docs`;
- не менять docs раньше остального.

Definition of Done:

- source layer либо truly canonical-only, либо transitional-but-honestly-documented;
- никаких скрытых silent promotions, contradicting docs.

## 7. Закрыть composite schema хвост без открытия новой composite-wave

На текущем baseline в `configs/_schema/composite.json` найден по крайней мере один residual legacy field:

- `column_groups_file`

RF-016 должен закрыть этот хвост именно как schema convergence issue. Это не повод заново пересматривать composite merge architecture или enrichers contract. Scope здесь узкий:

- удалить или переоформить `column_groups_file` в composite schema согласно принятому policy;
- синхронизировать это с tests/docs, если они упоминают этот path.

Риски:

- broad composite refactor под видом schema cleanup;
- accidental change в merge/enricher semantics.

Минимизация:

- трогать только schema-layer representation legacy field;
- не менять composite business rules.

Definition of Done:

- composite schema больше не рекламирует legacy file-based column-group path как часть canonical contract, если он уже не должен быть supported.

## 8. Documentation sync только после schema/model/test convergence

RF-016 неизбежно имеет documentation tail, но он должен быть последним. После того как pipeline, source и composite subdomains договорились между собой, нужно обновить:

- `configs/README.md`
- active config reference docs
- architecture/config guidance, если там ещё описаны старые schema-file or legacy pagination paths

Здесь нельзя документировать “идеальное будущее”, если runtime ещё живёт в transitional mode. Если source legacy seam сохранён, docs должны прямо так и говорить: supported as migration-only, not canonical. Если file-based pipeline schema references retired, active docs не должны продолжать их рекламировать.

Риски:

- снова появится красивый, но ложный docs contract;
- docs уйдут вперёд относительно кода.

Минимизация:

- docs edits делать только после green targeted verification;
- каждый doc statement сверять с schema/model/tests.

Definition of Done:

- active docs, schema files и loader/model behavior говорят одно и то же.

## 9. Verify strategy и measurable closeout

RF-016 нельзя закрывать только на уровне ссылок или только на уровне одного `mypy`. Нужен целевой verify-set.

Обязательные проверки:

```bash
./.venv/Scripts/python.exe -m pytest tests/architecture/test_config_ci_invariants.py tests/architecture/test_config_strict_keys.py tests/architecture/test_config_golden_master.py -q
```

```bash
./.venv/Scripts/python.exe -m pytest tests/unit/infrastructure/config tests/unit/infrastructure/test_config_dynamic.py tests/unit/infrastructure/test_config.py -q
```

Если меняется source migration path:

```bash
./.venv/Scripts/python.exe -m pytest tests/unit/infrastructure/config/test_source_config_legacy_normalization.py tests/unit/infrastructure/config/test_source_normalizers.py -q
```

Параллельно после каждого батча:

```bash
./.venv/Scripts/python.exe scripts/docs/check_doc_links.py --configs
```

Дополнительно нужны scope-aware greps по retired fields в active runtime/docs:

- `schema_file`
- `data_schema_file`
- `column_groups_file`
- source pagination legacy fields where appropriate

Важно: greps должны быть domain-aware. Например, `primary_keys` как domain concept не равно pipeline YAML legacy key.

## 10. Критерии закрытия RF-016

RF-016 считается завершённым, если одновременно выполняются все условия:

1. `pipeline.json`, `PipelineYamlConfig`, CI invariants и strict-keys tests согласованы.
2. Source pagination policy однозначен и одинаково выражен в schema/model/tests/docs.
3. Composite schema не рекламирует legacy shape, если он уже не является canonical contract.
4. Active docs не противоречат runtime reality.
5. Architecture/config test gates остаются зелёными.
6. Legacy seams либо удалены, либо честно описаны как transitional and migration-only.

## Рекомендуемый порядок выполнения

1. Scope lock and field classification.
2. Pipeline schema cleanup.
3. Pipeline model/tests synchronization.
4. Source pagination policy decision.
5. Source migration cleanup or migration-only formalization.
6. Composite schema tail cleanup.
7. Docs sync.
8. Final verification.

## Финальный итог

RF-016 должен убрать не “строгость ради строгости”, а ложную многозначность из config layer. Сейчас основной долг не в том, что конфиги не работают, а в том, что schema, model, tests и docs не всегда одинаково отвечают на вопрос “что у нас canonical, а что legacy”. Правильный результат RF-016 — когда этот вопрос больше не вызывает разных ответов на разных уровнях системы.
