# RF-018 Final Plan

Date: 2026-03-17

## RF-018: Documentation and Compatibility Inventory Sync

RF-018 — это завершающая documentation/governance wave после технических рефакторингов. Это не задача “переписать docs покрасивее” и не задача на ещё одну архитектурную перестройку. Цель RF-018 — привести active documentation layer и compatibility inventory в строгое соответствие с фактическим кодом и действующими архитектурными решениями текущего цикла.

Это особенно важно, потому что у проекта уже есть сильный технический baseline:

- `src/` больше не содержит внешних private import leaks;
- imports из `bioetl.composition.entrypoints` в `interfaces` сведены к нулю;
- sanctioned public composition APIs уже существуют как:
  - `src/bioetl/composition/execution_api.py`
  - `src/bioetl/composition/services_api.py`
  - `src/bioetl/composition/resources_api.py`
- curated governance ledger уже существует как:
  - `docs/02-architecture/07-compatibility-facade-inventory.md`

Но именно поэтому RF-018 нельзя выполнять механически. Главный риск этой задачи — начать документировать “идеальное будущее состояние” вместо реально зелёного кода. Это быстро вернёт проект к documentation drift, который и должен быть устранён. Значит RF-018 должен идти только от фактов:

- от current compatibility inventory;
- от architecture tests;
- от active public seams в `src/`;
- от уже принятых retained-entrypoint решений.

## 1. Scope Freeze и Baseline Snapshot

Первый шаг RF-018 чисто организационный. Нужно зафиксировать, что задача не меняет production behavior и не подменяет техническую реализацию документацией. Любой documentation change здесь допускается только после того, как соответствующий code/test baseline уже зелёный. На старте нужно снять baseline со следующих источников истины:

- `docs/02-architecture/07-compatibility-facade-inventory.md`
- `src/bioetl/composition/entrypoints.py`
- `src/bioetl/composition/execution_api.py`
- `src/bioetl/composition/services_api.py`
- `src/bioetl/composition/resources_api.py`
- `tests/architecture/test_compatibility_facade_inventory.py`
- `tests/architecture/test_forbidden_imports.py`
- `tests/architecture/test_registry_contracts.py`
- `tests/architecture/test_adapter_contracts.py`
- `tests/architecture/test_retained_adapter_entrypoint_policy.py`

Также важно зафиксировать, что inventory сейчас содержит `10` curated rows и `10` measured tracked modules. Это не просто число ради отчёта — это measurable compatibility baseline. RF-018 не обязан уменьшить это число. Если технический слой не менялся, корректный outcome — сохранить то же количество rows, но сделать wording и cross-doc references точнее.

Риски:

- попытка “доказать прогресс” искусственным изменением inventory scope;
- подмена active guidance отчётами и planning docs.

Минимизация:

- считать reports/history docs evidence zones, а не canonical guidance;
- все правки в active docs обосновывать уже существующим зелёным кодом.

Definition of Done:

- baseline inventory snapshot зафиксирован;
- scope active-doc remediation утверждён;
- правило “docs only after green code” явно соблюдается.

## 2. Нормализовать compatibility inventory как governance-артефакт

`docs/02-architecture/07-compatibility-facade-inventory.md` уже выполняет роль curated inventory of module-level compatibility facades and shims. RF-018 должен сделать этот документ не просто полным, а внутренне консистентным и легко читаемым как policy artifact.

Сейчас в inventory уже есть несколько разных статусов:

- `retained-entrypoint`
- `compat-shim`
- `mixed-module`

И это правильно: проект действительно использует разные формы compatibility surfaces. Ошибка была бы пытаться выровнять всё под один статус. Напротив, задача — сделать так, чтобы каждое поле inventory читалось одинаково последовательно:

- `canonical target`
- `status`
- `allowed call sites`
- `migration path`
- `remove by / review date`
- `exit criteria`

Нужно отдельно проверить, что wording для retained-entrypoints не выглядит как скрытая депрекация, а wording для compat-shims and mixed-modules не выглядит как fully-clean canonical state. Иными словами, inventory должен говорить честно.

Риски:

- inventory превратится в каталог всех alias/helper modules;
- вместо governance-документа получится changelog текущей refactor-wave.

Минимизация:

- сохранять curated scope;
- включать только architecturally significant module-level facades;
- не добавлять helper modules без compatibility significance.

Definition of Done:

- inventory читается как policy ledger;
- разные status rows описаны единообразно;
- curated scope не размыт.

## 3. Синхронизировать Composition Public API Docs

Composition layer уже расколот на более узкие sanctioned public APIs:

- `src/bioetl/composition/execution_api.py`
- `src/bioetl/composition/services_api.py`
- `src/bioetl/composition/resources_api.py`

При этом:

- `src/bioetl/composition/entrypoints.py`

остаётся retained public seam и зафиксирован в inventory как `retained-entrypoint`, а не как deprecated surface. Это критически важно для RF-018. Active architecture docs не должны описывать `entrypoints.py` как “устаревающий монолит”, если текущий cycle decision — `retain`.

Что нужно сделать:

- проверить `docs/02-architecture/05-composition-layer.md`;
- проверить guide-материалы, где composition surface описан для interface-layer callers;
- убедиться, что docs различают:
  - canonical retained `entrypoints.py` как public stable seam;
  - narrower sanctioned APIs как preferred internal split for new helper families.

То есть правильная формулировка должна быть примерно такая: `entrypoints.py` retained as stable public seam; where narrower composition APIs already exist, new code should prefer them instead of growing the retained facade.

Риски:

- задокументировать `entrypoints.py` как deprecated, хотя inventory фиксирует `retain`;
- наоборот, продолжить описывать его как единственный универсальный internal path.

Минимизация:

- doc wording должен следовать inventory;
- никакая активная guide prose не должна противоречить retained-entrypoint decision.

Definition of Done:

- composition docs отражают coexistence retained public entrypoint и узких sanctioned APIs;
- active guidance не конфликтует с inventory.

## 4. Синхронизировать Registry и Config Mixed-Module Guidance

Inventory уже фиксирует два особенно важных mixed-module surfaces:

- `src/bioetl/composition/registry.py`
- `src/bioetl/infrastructure/config_loader.py`

Это не просто технические детали. Они отражают реальный governance state:

- registry module остаётся canonical instance-registry API, но внутри него ещё живёт transitional default-registry compatibility;
- config_loader остаётся public loader seam, но normalization concerns всё ещё partly bridge unified and legacy schema shapes.

RF-018 должен убедиться, что active docs говорят ровно это, а не что-то более оптимистичное или более расплывчатое. В частности, нужно перепроверить:

- `docs/03-guides/registry-pattern.md`
- architecture/config guidance, где ещё описывается registry usage;
- docs, где config loader path может быть показан как fully canonical-only, хотя inventory всё ещё считает его `mixed-module`.

Здесь особенно важно не скрывать transitional state. Mixed-module — это не shame label, а честное описание того, что public seam уже canonical, но compatibility debt ещё не полностью исчез.

Риски:

- docs могут преждевременно объявить registry/config surface “полностью очищенным”;
- mixed-module rows будут описаны слишком мягко и потеряют управленческую ценность.

Минимизация:

- использовать тот же vocabulary, что и inventory;
- не убирать слово `mixed-module`, если кодовый baseline его ещё оправдывает.

Definition of Done:

- registry/config docs синхронизированы с inventory;
- canonical path и compatibility debt описаны честно.

## 5. Синхронизировать Domain Retained-Entrypoint Guidance

В inventory уже зафиксированы retained-entrypoint rows для:

- `src/bioetl/domain/composite/config.py`
- `src/bioetl/domain/value_objects/activity_values.py`
- `src/bioetl/domain/value_objects/publication_field_groups.py`

Это означает, что public domain entrypoints являются санкционированными стабильными seams, а split internal modules — implementation detail owner package. RF-018 должен проверить, не осталось ли в active docs формулировок, которые:

- подталкивают к импортам split internals;
- описывают retained entrypoints как временные костыли, уже “на выход”.

Такой drift особенно опасен, потому что он влияет на то, как новые разработчики начинают импортировать domain types. Documentation layer должен поддерживать именно public façade path, а не создавать у читателя впечатление, что “настоящий путь” находится глубже.

Риски:

- docs будут слишком детализированы и начнут перечислять private internals;
- retained-entrypoint policy будет размыта.

Минимизация:

- в active docs упоминать только canonical public path;
- private split modules оставлять только inventory и dedicated tests.

Definition of Done:

- domain docs и inventory больше не расходятся;
- public domain façade paths явно закреплены как sanctioned imports.

## 6. Завершить Adapter Entrypoint Documentation Sync для PubMed и Semantic Scholar

Current cycle decision уже явно зафиксирован:

- `src/bioetl/infrastructure/adapters/pubmed/client.py` — `retain`
- `src/bioetl/infrastructure/adapters/semanticscholar/client.py` — `retain`

Это означает:

- новое first-party code использует provider package roots;
- retained `client.py` остаётся стабильным public seam;
- старые implementation-module paths `pubmed.pubmed_client` и `semanticscholar.adapter` не должны использоваться новым кодом.

RF-018 должен синхронизировать эту политику с active provider/adapter docs. Если документация где-то показывает импорт старых implementation-module paths или двусмысленно описывает retained `client.py` как deprecated, это нужно исправить. Но нельзя делать обратную ошибку — описывать retained `client.py` как обязательный путь для нового first-party code, если inventory уже говорит предпочитать provider package roots.

Риски:

- перепутать retained public seam с preferred first-party import path;
- случайно задокументировать депрекацию там, где её нет.

Минимизация:

- в docs явно различать package root preference и retained `client.py` stability surface;
- держаться wording inventory.

Definition of Done:

- adapter docs, inventory и policy tests говорят одно и то же про PubMed and Semantic Scholar.

## 7. Навести порядок между Canonical Docs и Evidence/History Zones

Это одна из самых важных дисциплинарных частей RF-018. В inventory уже зафиксировано правило:

- `docs/exports/**`, `docs/reports/**`, `docs/99-archive/**` — evidence/history zones;
- canonical guidance живёт в `docs/02-architecture/**`, `docs/03-guides/**`, `docs/04-reference/**`.

Но зафиксированное правило само по себе мало что значит, если active docs по-прежнему ссылаются на reports/archive как на источник текущей архитектурной истины. RF-018 должен сделать это правило реальным.

Что это означает practically:

- active architecture docs не должны ссылаться на planning/refactor reports как на canonical current-state documentation;
- свежие отчёты вроде:
  - `docs/reports/rf-014-final-2026-03-17.md`
  - `docs/reports/rf-015-final-2026-03-17.md`
  - `docs/reports/rf-017-final-2026-03-17.md`
  должны оставаться evidence, а не подменять active guidance;
- если active docs ссылаются на archive only for historical context, это должно быть явно обозначено.

Риски:

- useful traceability будет потеряна;
- команда снова начнёт читать reports как canonical source of truth.

Минимизация:

- не удалять reports или archive docs;
- только разорвать их роль как active guidance;
- при необходимости оставлять ссылки с пометкой `historical context`.

Definition of Done:

- canonical truth lives in canonical doc zones;
- reports remain evidence and history only.

## 8. Синхронизировать Tests, Measured Registry и Documentation

RF-018 не должен заканчиваться простым редактированием markdown. Поскольку compatibility inventory уже является measurable governance artifact, documentation sync нужно проверять against tests and measured state.

Ключевые checks:

- `tests/architecture/test_compatibility_facade_inventory.py`
- `tests/architecture/test_forbidden_imports.py`
- `tests/architecture/test_registry_contracts.py`
- `tests/architecture/test_adapter_contracts.py`
- `tests/architecture/test_retained_adapter_entrypoint_policy.py`

RF-018 должен гарантировать, что docs описывают именно тот policy baseline, который эти tests уже enforce-ят. Если wording tests и docs расходится, корректировать надо прежде всего docs, если только техническое решение не менялось в отдельной рефакторинг-волне.

Дополнительно стоит использовать diagnostic inventory checks по legacy implementation paths:

```bash
rg -n "bioetl\\.composition\\._pipeline_execution|bioetl\\.composition\\._resource_management|bioetl\\.composition\\._services|bioetl\\.infrastructure\\.adapters\\.pubmed\\.pubmed_client|bioetl\\.infrastructure\\.adapters\\.semanticscholar\\.adapter" src tests -g '*.py'
```

Риски:

- документация будет диктовать policy, а не отражать её;
- можно забыть про measurable side compatibility governance.

Минимизация:

- architecture policy tests считаются higher-signal baseline;
- docs only align to green code/tests.

Definition of Done:

- prose, tests and measured registry aligned;
- нет policy drift между documentation и enforce-слоем.

## 9. Финальное закрытие RF-018

RF-018 должен закрываться измеримо. Успешный результат выглядит так:

1. `07-compatibility-facade-inventory.md` остаётся curated, measured, internally consistent policy ledger.
2. Active docs ссылаются на canonical public seams, а не на internal implementation modules или reports.
3. Retained-entrypoint rows описаны именно как retained, а не accidentally deprecated.
4. Mixed-module rows честно описаны как mixed, без premature “fully cleaned” framing.
5. Reports/archive/exports перестают подменять canonical guidance.
6. Architecture policy tests остаются зелёными.
7. `scripts/docs/check_doc_links.py --configs` остаётся зелёным.

Важно: RF-018 не обязан уменьшить число inventory rows. Если technical state не изменился, но docs стали policy-consistent и перестали дрейфовать относительно кода, это уже правильный outcome.
