# RF-015 Final Plan

Date: 2026-03-17

## RF-015: CLI Thin-Command Finish for `run.py`

Цель этой задачи: довести CLI-команду `run` до состояния действительно тонкого интерфейсного entrypoint-модуля, не ломая текущий public contract и не открывая новую широкую архитектурную волну. Сейчас [run.py](/mnt/e/g-drive/05_AI/github/BioactivityDataAcquisition2/src/bioetl/interfaces/cli/commands/run.py) уже находится в значительно лучшем состоянии, чем раньше: он больше не зависит от `composition.entrypoints`, использует sanctioned composition APIs, часть policy-логики уже вынесена в [run_command_policy.py](/mnt/e/g-drive/05_AI/github/BioactivityDataAcquisition2/src/bioetl/interfaces/cli/commands/run_command_policy.py), а часть runtime-логики уже вынесена в [run_runtime_helpers.py](/mnt/e/g-drive/05_AI/github/BioactivityDataAcquisition2/src/bioetl/interfaces/cli/commands/run_runtime_helpers.py). Тем не менее сам файл всё ещё остаётся ровно `400 LOC`, содержит process-local service accessor, private async runtime path, result finalization glue и compatibility reexports для тестов. Это уже не критический архитектурный дефект, но это всё ещё не “тонкая команда” в строгом смысле.

Следовательно, RF-015 должен быть очень прагматичным. Это не задача на новый CLI framework и не задача на перенос orchestration в application или composition. Нельзя заново “изобретать” поток выполнения. Нужно лишь довести уже начатую декомпозицию до логического конца: сделать так, чтобы [run.py](/mnt/e/g-drive/05_AI/github/BioactivityDataAcquisition2/src/bioetl/interfaces/cli/commands/run.py) был местом, где живут click decorators, сбор входного payload, вызов канонического policy flow и сохранённые compat seams, а всё остальное было вынесено в private helpers рядом.

При этом нужно учитывать реальный blast radius. На текущую форму `run.py` опирается большой test surface:

- `tests/unit/interfaces/cli/test_cli_commands.py`
- `tests/unit/interfaces/cli/test_cli_commands_basic.py`
- `tests/unit/interfaces/cli/test_cli_helpers.py`
- `tests/unit/interfaces/cli/test_cli_main_module.py`
- `tests/unit/interfaces/cli/commands/test_run_command_policy.py`
- `tests/unit/interfaces/cli/commands/test_run_helpers.py`
- `tests/integration/interfaces/test_cli_run_incremental.py`
- `tests/integration/interfaces/test_cli_run_dry_run.py`
- `tests/integration/interfaces/test_cli_shutdown_integration.py`
- `tests/integration/interfaces/test_cli_exit_code_matrix.py`
- `tests/e2e/test_cli_safety.py`

Поэтому задача должна выполняться малыми батчами, с сохранением существующих patch seams до самого конца волны.

## 1. Freeze baseline и inventory реальных seams

Первый шаг нужен не для кода, а для дисциплины. Перед любым изменением необходимо письменно зафиксировать, какие seams в `run.py` являются каноническими, а какие уже стали de facto compatibility surface. На текущий момент файл делится на несколько функциональных зон:

- service accessor seam: `get_cli_run_orchestration_service()`
- command boundary helpers: `validate_options()`, `build_run_options()`, `execute_run()`
- CLI input normalization: `_build_run_command_input()`
- result/presentation glue: `_present_run_health_info()`, `_finalize_run_result()`
- runtime path: `_run_pipeline_async()`, `_run_prepared_request_async()`
- click callback: `run()`
- compatibility aliases: `_get_runner_logger`, `_handle_destructive_run_confirmation`, `_preview_cleanup`, `_validate_start_offset`

Нужно отдельно подтвердить, какие из этих symbols реально патчат tests. Это уже видно по текущему test surface: некоторые tests патчат `_run_pipeline_async`, другие опираются на `get_cli_run_orchestration_service()`, третьи импортируют compat helpers. Это означает, что даже если часть symbols уже не нужна production-коду, она может быть важной как compatibility seam.

Цель:

- получить карту активных и совместимых seams;
- не сломать tests “случайной чисткой”.

Риски:

- переоценить свободу рефакторинга;
- удалить symbol, который формально private, но фактически является test contract.

Минимизация:

- зафиксировать список patch targets и import targets из tests;
- не удалять ни один compatibility symbol в первой половине RF-015.

Definition of Done:

- есть явный inventory canonical seams и compatibility seams;
- список verify tests утверждён до первой правки.

## 2. Явное разделение canonical и compatibility surface

Сейчас `run.py` уже содержит compatibility reexports внизу файла, но они смешаны с активным command flow. Это создаёт cognitive noise: человеку, читающему модуль, неочевидно, что именно поддерживается как настоящее рабочее API команды, а что оставлено только ради обратной совместимости с тестами и старым internal import surface.

На этом шаге нужно не удалять compatibility aliases, а формально разделить их статус. То есть в модуле должна появиться явная зона active command flow и явная зона compatibility-only exports. Если это возможно без лишнего шума, стоит сопроводить compat aliases коротким поясняющим блоком-комментарием. Если в процессе станет ясно, что лучше вынести compat aliases в отдельный private helper module и re-export обратно, это допустимо, но не обязательно. Главное — сделать статус этих symbols прозрачным.

Конкретные правки:

- сохранить действующие alias-имена;
- явно отделить compat block внизу модуля;
- при необходимости скорректировать `__all__`, чтобы канонический public contract был явно отделён от обратной совместимости.

Риски:

- чрезмерная “чистка” может нарушить tests, даже если кажется, что aliases уже не используются;
- можно случайно сделать два равноправных API instead of one canonical plus compat.

Минимизация:

- не менять import names для compat surface в этой волне;
- любые re-exports считать временным переходным контрактом и явно это пометить.

Definition of Done:

- из структуры файла понятно, что относится к текущему command flow;
- compatibility seams отделены и больше не выглядят как обычная production-логика.

## 3. Вынести service accessor seam из `run.py`

Сейчас `run.py` держит process-local cached accessor:

- `_cli_run_orchestration_service`
- `get_cli_run_orchestration_service()`

Это уже лучше, чем старый module-level singleton instance, но сам факт хранения кеша непосредственно в command module делает `run.py` более stateful, чем нужно. Тонкий CLI модуль не должен одновременно быть и местом click wiring, и местом хранения service state.

На этом шаге стоит вынести accessor в отдельный private module, например:

- `src/bioetl/interfaces/cli/commands/run_service_access.py`

или, если это окажется полезнее для будущих команд:

- `src/bioetl/interfaces/cli/service_access.py`

При этом важно сохранить поведение один в один. `get_cli_run_orchestration_service()` должно остаться callable seam с тем же lazy caching behavior, чтобы tests и runtime semantics не изменились. В `run.py` можно оставить thin wrapper или прямой импорт/re-export, если так удобнее для compatibility.

Цель:

- убрать локальное состояние из command module;
- не менять semantics lazy initialization.

Риски:

- tests могут зависеть от identity accessor return value;
- можно незаметно поменять timing of initialization.

Минимизация:

- оставить ту же функцию и тот же behavior;
- менять только место хранения состояния, а не семантику.

Definition of Done:

- process-local service cache больше не живёт прямо в `run.py`;
- compatibility seam `get_cli_run_orchestration_service()` сохраняется.

## 4. Свести runtime execution path к одному private runtime seam

Сейчас runtime execution path уже частично декомпозирован, но ещё не доведён до конца. В [run_runtime_helpers.py](/mnt/e/g-drive/05_AI/github/BioactivityDataAcquisition2/src/bioetl/interfaces/cli/commands/run_runtime_helpers.py) уже живут:

- `build_run_command_input()`
- `run_pipeline_async()`
- `build_run_pipeline_callable()`

При этом в [run.py](/mnt/e/g-drive/05_AI/github/BioactivityDataAcquisition2/src/bioetl/interfaces/cli/commands/run.py) всё ещё остаются:

- `_run_pipeline_async()`
- `_run_prepared_request_async()`
- `execute_run()`

Это означает, что logical seam уже создан, но runtime path ещё дублируется между двумя модулями. RF-015 должен завершить этот переход. Правильный путь — сделать [run_runtime_helpers.py](/mnt/e/g-drive/05_AI/github/BioactivityDataAcquisition2/src/bioetl/interfaces/cli/commands/run_runtime_helpers.py) единственным местом, где живёт actual runtime helper logic, а в `run.py` оставить только thin wrappers или compat aliases, пока tests их используют.

Хороший сценарий:

- `execute_run()` остаётся в `run.py` как command-boundary seam;
- actual prepared-request async path строится через `build_run_pipeline_callable()`;
- `_run_pipeline_async()` и `_run_prepared_request_async()` либо становятся thin wrappers на runtime helpers, либо полностью делегируют туда.

Нельзя делать обратное и тянуть helper logic обратно в `run.py`.

Риски:

- unit tests сейчас патчат `_run_pipeline_async` прямо в `run.py`;
- integration tests тоже косвенно завязаны на текущий runtime path.

Минимизация:

- сохранить старые function names как wrappers, пока tests не мигрированы;
- только после этого убирать дублирование внутри.

Definition of Done:

- actual runtime helper logic живёт в одном private helper surface;
- `run.py` больше не содержит полноценную async execution pipeline.

## 5. Вынести result/presentation glue

В `run.py` до сих пор живут маленькие, но неуместные для thin entrypoint куски glue-логики:

- `_present_run_health_info()`
- `_map_status_to_exit_code()`
- `_finalize_run_result()`

Сами по себе они небольшие, но именно они поддерживают иллюзию, что command module должен знать слишком много о result finalization. Между тем presenter уже вынесен в [run_result_presenter.py](/mnt/e/g-drive/05_AI/github/BioactivityDataAcquisition2/src/bioetl/interfaces/cli/commands/run_result_presenter.py), а policy logic сидит в [run_command_policy.py](/mnt/e/g-drive/05_AI/github/BioactivityDataAcquisition2/src/bioetl/interfaces/cli/commands/run_command_policy.py). Значит `run.py` здесь выступает только как glue layer, который можно сделать тоньше.

Рекомендованный подход:

- вынести result finalization helpers в небольшой private helper module, если это действительно уменьшает шум;
- либо расширить уже существующий presenter/helper module, если это даёт более ясную структуру;
- оставить `_exit_with_code()` как typed sys.exit seam, потому что это полезный boundary helper.

Важно: tests уже патчат `_finalize_run_result`, так что alias-compatible surface должен сохраниться хотя бы до конца этой волны.

Риски:

- слишком агрессивный вынос сломает patch seams;
- result finalization может расползтись по нескольким файлам и стать менее discoverable.

Минимизация:

- максимум один новый helper module для result/presentation zone;
- compat wrapper names в `run.py` сохраняются, даже если реализация переносится.

Definition of Done:

- presentation/result glue больше не утяжеляет command file;
- tests продолжают работать через старые или явно задокументированные seams.

## 6. Финально сделать `run()` callback действительно тонким

В идеальной форме `run.py` должен содержать:

- click decorators;
- `run()` callback;
- thin command-boundary helpers вроде `execute_run()`;
- при необходимости compat wrappers.

Смысл RF-015 не в том, чтобы скрыть сложность “куда-то ещё”, а в том, чтобы у `run.py` осталось только то, что и должно жить в интерфейсном command module: сбор входных параметров и передача управления в канонический flow. На текущий момент [test_cli_commands.py](/mnt/e/g-drive/05_AI/github/BioactivityDataAcquisition2/tests/unit/interfaces/cli/test_cli_commands.py) уже проверяет этот сценарий: callback делегирует в `_build_run_command_input()` и `_run_command_with_cli_policy()`. Это нужно считать intentional architectural contract и после RF-015 закрепить окончательно.

Конкретные правки:

- после выноса service/runtime/result clusters свести тело `run.py` к thin command façade;
- убедиться, что в файле не осталось неочевидной orchestration logic;
- оставить только тот объём compat exports, который реально нужен.

Риски:

- complexity физически уйдёт из файла, но логически просто расползётся по многим helper files;
- thin command contract не будет формально зафиксирован.

Минимизация:

- ограничить число новых helper files;
- закрепить thin-entrypoint behavior существующими и при необходимости расширенными tests.

Definition of Done:

- `run.py` читается как entrypoint, а не как orchestration module;
- thin callback contract зафиксирован тестами.

## 8. Критерии закрытия RF-015

RF-015 считается завершённым только если одновременно выполняются все условия:

1. `run.py` становится заметно тоньше и опускается ниже текущих `400 LOC`.
2. В `run.py` больше не живёт локальное service cache state.
3. Runtime execution path и result/presentation glue вынесены в соседние private seams.
4. Public CLI behavior не изменился.
5. Backward-compat seams либо сохранены, либо аккуратно заменены без потери patchability.
6. `interfaces` не теряют текущую архитектурную чистоту и не возвращаются к `composition.entrypoints`.
7. Unit, integration и final architecture checks остаются зелёными.

## Рекомендуемый порядок реализации

1. Baseline и inventory seams.
2. Разделение canonical vs compatibility surface.
3. Вынос service accessor.
4. Consolidation runtime path.
5. Вынос result/presentation cluster.
6. Финальный cleanup `run.py`.
7. Full verification.

## Финальный итог

RF-015 не должен “спасти архитектуру” — она здесь уже в хорошем состоянии. Его задача более узкая и практичная: довести [run.py](/mnt/e/g-drive/05_AI/github/BioactivityDataAcquisition2/src/bioetl/interfaces/cli/commands/run.py) до консистентного thin-command состояния, чтобы дальнейшие изменения в CLI run flow были дешевле, безопаснее и локальнее. Это задача на снижение cognitive load и test fragility, а не на большой redesign. Если выполнить её аккуратно, получится cleaner command boundary без regressions и без возврата к старым god-module паттернам.
