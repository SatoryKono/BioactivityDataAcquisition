# RF-017 Final Plan

Date: 2026-03-17

## RF-017: Constructor Pressure Burn-down

Цель RF-017: снизить constructor pressure там, где он уже мешает понятности dependency graph и дальнейшему сопровождению, но не делать механический mass-refactor по всему проекту. Это принципиально важно. По текущему baseline [`check_constructor_args.py`](/mnt/e/g-drive/05_AI/github/BioactivityDataAcquisition2/src/tools/scripts/check_constructor_args.py) даёт **17 нарушений**, и они лежат в очень разных кластерах: application/composite, transformer stack, application core, composition factory, domain aggregate, infrastructure adapters. Эти случаи нельзя лечить одним шаблоном.

Следовательно, RF-017 должен идти не по принципу “уменьшить число аргументов любой ценой”, а по принципу “применить bundle/context только там, где это уже подтверждено архитектурным паттерном и реально улучшает локальную читаемость”. Всё остальное либо выносится в отдельные волны, либо сознательно остаётся за пределами первой фазы.

То есть часть архитектурной работы уже сделана, но миграция не доведена до конца. Именно этот pattern должен стать главным рычагом RF-017.

## 1. Scope Lock и разбиение нарушений на группы

Первый шаг — не код, а правильная декомпозиция задачи. Нужно формально разбить `17` нарушений на три группы:

1. Pattern-driven cluster, где bundle/context уже существует и его надо довести до канонического состояния.
2. Local application/composition services, где bundle может быть полезен, но только локально.
3. Residual domain/infrastructure cases, которые не входят в первую волну RF-017.

В первую группу входят:

- `BaseTransformer`
- `BaseChemblTransformer`
- provider transformers для CrossRef/OpenAlex/PubChem/PubMed/SemanticScholar/UniProt
- `PublicationTransformer`

Во вторую группу:

- `JoinPlannerService`
- `BatchProcessingService`

В третью группу:

- `CompositeSupportServicesFactory`
- `QuarantineEntry`
- `PubChemAdapter`
- `PubChemFetchStrategies`
- `UniProtAdapter`

Такой split нужен, чтобы задача не обещала нереалистичный результат. Реалистичная цель первой волны — не убрать все `17` нарушений, а снизить их примерно до диапазона `8–10`, закрыв те случаи, где уже есть архитектурный фундамент.

Риски:

- попытка уместить все 17 кейсов в одну волну приведёт к broad churn;
- bundle-изация начнёт использоваться механически.

Минимизация:

- жёстко ограничить первую волну первыми двумя группами;
- третью группу считать explicit out-of-scope.

Definition of Done:

- есть утверждённый список in-scope и out-of-scope нарушений;
- для первой волны понятна реалистичная целевая метрика.

## 2. Сделать `TransformerDependencyContext` каноническим путём для transformer stack

В [`types.py`](/mnt/e/g-drive/05_AI/github/BioactivityDataAcquisition2/src/bioetl/application/core/base_transformer/types.py) уже существует [`TransformerDependencyContext`](/mnt/e/g-drive/05_AI/github/BioactivityDataAcquisition2/src/bioetl/application/core/base_transformer/types.py), который агрегирует:

- `tracer`
- `metrics`
- `identity_service`
- `pii_hasher`
- `data_normalizer`
- `contract_policy`

Это именно тот тип bundle, который нужен проекту: он выражает один чёткий контекст — технические transformer collaborators. Проблема в том, что [BaseTransformer](/mnt/e/g-drive/05_AI/github/BioactivityDataAcquisition2/src/bioetl/application/core/base_transformer/base.py) всё ещё принимает и `dependencies`, и параллельный длинный flat list. То есть архитектурный паттерн уже есть, но осталась transitional compatibility.

RF-017 должен довести этот паттерн до состояния “dependencies-first”. Это значит:

- composition собирает `TransformerDependencyContext`;
- provider transformer constructors воспринимают `dependencies` как primary path;
- flat args остаются только на переходный период, если они ещё нужны для совместимости;
- defaults не строятся внутри application.

Критически важно не уронить DI discipline. Контекст должен оставаться explicit collaborator bundle, а не неявным контейнером, из которого класс сам начинает “доставать всё подряд” по мере надобности.

Риски:

- `BaseTransformer` превратится в merger нескольких dependency sources, слишком похожий на service locator;
- composition и tests могут продолжить использовать старые flat args и никакого фактического упрощения не произойдёт.

Минимизация:

- сначала перевести composition и tests на `dependencies`;
- только потом сужать flat сигнатуры.

Definition of Done:

- `TransformerDependencyContext` становится canonical wiring path;
- transformer callsites в composition и tests используют его по умолчанию.

## 3. Мигрировать transformer family по шаблону, а не вручную

Следующий шаг — не редактировать каждый transformer как уникальный случай. У provider transformer family уже виден повторяемый паттерн: constructors принимают provider/entity labels, observability collaborators, normalization collaborators, filters и иногда provider-specific dependencies. Значит миграция должна идти по семействам.

Базовая последовательность:

1. Обновить base transformer layer.
2. Обновить `BaseChemblTransformer`.
3. Обновить publication transformer families.
4. Обновить remaining provider transformers.

Здесь особенно важен [PubMedPublicationTransformer](/mnt/e/g-drive/05_AI/github/BioactivityDataAcquisition2/src/bioetl/application/pipelines/pubmed/transformer.py), потому что кроме общего transformer context он принимает ещё `author_extractor` и `date_extractor`. Это не повод расширять `TransformerDependencyContext`, потому что эти зависимости не являются общими для всех transformer-ов. Значит нужен второй, локальный context, например узкий `PubMedExtractionDependencies` или аналог, который описывает только provider-specific extractors.

Тот же принцип применим и к другим transformer families: один bundle должен означать один usage context. Нельзя собирать в один object и общие pipeline collaborators, и provider-specific extractors, и scalar config labels только ради метрики constructor width.

Риски:

- bundle превратится в “мешок всего”;
- разные provider-specific зависимости попадут в общий context и размоют его смысл.

Минимизация:

- общий bundle только для shared transformer collaborators;
- provider-specific collaborators собирать в отдельные узкие bundles или оставлять явными, если их мало.

Definition of Done:

- transformer migration идёт по повторяемому pattern;
- один и тот же приём можно применить к нескольким transformer families без ad hoc решений.

## 4. Сузить `BaseTransformer`, не превращая его в service locator

[BaseTransformer](/mnt/e/g-drive/05_AI/github/BioactivityDataAcquisition2/src/bioetl/application/core/base_transformer/base.py) уже содержит `_resolve_dependency_context()`, `_merge_dependency_context()` и `_build_explicit_dependency_context()`. Это полезно как transitional seam, но в долгую этот код может стать слишком многорежимным и потерять прозрачность.

Конечная форма должна быть такой:

- явные semantic params: `provider`, `entity_type`, `silver_filters`, `gold_filters`;
- один `dependencies: TransformerDependencyContext`;
- возможно, узкий compatibility path на переходный период;
- отсутствие локального конструирования default collaborators.

Очень важно не прятать semantic values внутрь dependency bundle. `provider` и `entity_type` — не сервисы, а часть модели transformer-а. Если затолкать их в bundle только ради уменьшения числа аргументов, код станет менее понятным.

Риски:

- попытка “добить метрику” приведёт к bundle-изации scalar params;
- сохранится слишком много transitional logic и выигрыша по читаемости не будет.

Минимизация:

- bundle использовать только для сервисных collaborators;
- compatibility path удалить или сузить только после миграции callsites.

Definition of Done:

- `BaseTransformer` стал проще как DI boundary;
- смысловой баланс между scalar params и collaborator bundle сохранён.

## 5. Отдельно пройти `BaseChemblTransformer` и publication base stack

[BaseChemblTransformer](/mnt/e/g-drive/05_AI/github/BioactivityDataAcquisition2/src/bioetl/application/pipelines/chembl/base_chembl_transformer.py) сейчас почти полностью повторяет flat dependency surface `BaseTransformer`, плюс собственную логику derived `entity_type`. Это хороший кандидат для явного сокращения сигнатуры после stabilizing `BaseTransformer`.

Параллельно нужно аккуратно посмотреть на publication stack, особенно:

- [BasePublicationTransformer](/mnt/e/g-drive/05_AI/github/BioactivityDataAcquisition2/src/bioetl/application/pipelines/common/base_publication_transformer.py)
- [PublicationTransformer](/mnt/e/g-drive/05_AI/github/BioactivityDataAcquisition2/src/bioetl/application/pipelines/chembl/publication_transformer.py)
- [PubMedPublicationTransformer](/mnt/e/g-drive/05_AI/github/BioactivityDataAcquisition2/src/bioetl/application/pipelines/pubmed/transformer.py)

Идея та же: общие collaborators должны идти через общий transformer context; publication-specific extras — отдельно. Здесь RF-017 должен работать в сцепке с уже существующими template-method patterns, а не ломать их.

Риски:

- publication transformers начнут расходиться по собственным bundle patterns;
- derived `entity_type` behavior может тихо измениться.

Минимизация:

- держать один migration pattern на весь publication stack;
- проверять не только constructor width, но и semantic parity.

Definition of Done:

- base transformer stack и publication stack используют согласованный DI pattern.

## 6. Локально обработать `JoinPlannerService`

[JoinPlannerService](/mnt/e/g-drive/05_AI/github/BioactivityDataAcquisition2/src/bioetl/application/composite/join_planner.py) уже был частично упрощён в RF-013, поэтому RF-017 не должен заново открывать merge-архитектуру. Но конструктор всё ещё широкий и это остаётся legitimate hotspot.

Здесь полезен только узкий bundle. По текущей сигнатуре видны естественные зоны:

- core state: `merge_config`, `logger`
- preparation collaborators: `deduplicator`, `aggregator`, `renamer`, `conflict_resolver`
- execution collaborators: `join_key_resolver`, `join_executor`, `dependency_joiner`, `field_alias_resolver`

RF-017 должен проверить, действительно ли grouping этих зависимостей улучшает читаемость. Если да, можно вводить один `JoinPlannerCollaborators` или два маленьких bundles по preparation/execution. Если нет, лучше оставить явную сигнатуру и не делать искусственный object only for metric reduction.

Риски:

- появится “magic bundle”, в котором сложно понять, что реально нужно сервису;
- текущая читаемость после RF-013 ухудшится.

Минимизация:

- bundle вводить только если он отражает естественный collaborator context;
- не смешивать `merge_config` и logger с service-collaborator bundle.

Definition of Done:

- `JoinPlannerService` либо реально упрощён, либо осознанно исключён из первой implementation wave с documented rationale.

## 7. Локально обработать `BatchProcessingService`

[BatchProcessingService](/mnt/e/g-drive/05_AI/github/BioactivityDataAcquisition2/src/bioetl/application/core/batch_processing_service.py) сейчас принимает смесь execution context и технических collaborators:

- `services`
- `context`
- `config`
- `logger`
- `batch_metrics`
- `transformer`
- `writer`
- `tracing_manager`
- `batch_id_factory`

Здесь bundle имеет смысл только если он не замажет границу между execution state и инструментами обработки. Рациональный путь:

- оставить `services`, `context`, `config` явными как execution context;
- сгруппировать processing collaborators в узкий `BatchProcessingCollaborators`;
- отдельно решить, входит ли `logger` в этот bundle или остаётся явным shared service.

Это даст выигрыш и по constructor width, и по читаемости.

Риски:

- слишком большой bundle скроет важные operational collaborators;
- execution context и service graph сольются в один “мешок”.

Минимизация:

- не bundle-ить execution state;
- выделять только технологический collaborator cluster.

Definition of Done:

- `BatchProcessingService` стал понятнее как unit of work orchestration;
- сигнатура отражает реальную границу между context и collaborators.

## 8. Что явно не входит в первую волну RF-017

Следующие кейсы не должны входить в первую wave:

- `QuarantineEntry`
- `CompositeSupportServicesFactory`
- `PubChemAdapter`
- `PubChemFetchStrategies`
- `UniProtAdapter`

Причины разные:

- доменный aggregate может legitimately иметь широкую state-constructor сигнатуру;
- composition factory может быть широким по роли, а не по smell;
- infrastructure adapters требуют отдельной client/resilience-wave, а не смешивания с application DI cleanup.

Это не значит, что их никогда не нужно трогать. Это означает, что их нельзя смешивать с transformer/core/composite pattern wave без потери управляемости.

Definition of Done:

- out-of-scope cases явно зафиксированы;
- RF-017 не расползается в unrelated layers.

## 10. Критерии закрытия RF-017

RF-017 можно считать завершённым, если:

1. constructor violations снижаются с `17` до реалистично меньшего диапазона, целевой ориентир `8–10`;
2. transformer stack переходит на canonical `TransformerDependencyContext` path;
3. `JoinPlannerService` и `BatchProcessingService` либо становятся реально проще, либо получают documented rationale, почему bundle здесь не улучшает дизайн;
4. architecture gates не ухудшаются;
5. `mypy --strict` остаётся зелёным;
6. нет regressions в targeted unit/integration suites.

## Финальный итог

RF-017 не должен быть косметической попыткой “спрятать аргументы”. Его правильная цель — уменьшить constructor pressure там, где уже есть зрелый DI pattern и где bundle/context реально повышает читаемость dependency graph. Самый сильный рычаг здесь — transformer stack с уже существующим [`TransformerDependencyContext`](/mnt/e/g-drive/05_AI/github/BioactivityDataAcquisition2/src/bioetl/application/core/base_transformer/types.py). Если довести именно этот pattern до канонической формы и дополнительно локально пройти `JoinPlannerService` и `BatchProcessingService`, проект получит заметное улучшение maintainability без broad churn и без искусственного нагромождения новых abstractions.
