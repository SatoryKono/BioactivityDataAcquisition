## 3. Этап 2: Качественный Анализ

### Основные Проблемы

1.  **Дублирование логики оркестрации в пайплайнах:**
    - **Проблема:** Файлы `application/pipelines/chembl_activity.py`, `pubchem_compound.py`, `uniprot_protein.py` содержат очень похожий код для основного цикла ETL: захват блокировки, получение чекпоинта, итерация по данным, обработка ошибок, сохранение чекпоинта, освобождение блокировки.
    - **Последствия:** Добавление нового пайплайна требует копирования и адаптации большого объема кода. Изменение логики оркестрации (например, добавление нового шага) нужно будет вносить в каждый файл отдельно.

2.  **Неявная конфигурация пайплайна:**
    - **Проблема:** Часть логики пайплайна определяется не в конфигурационном файле (`.yaml`), а непосредственно в Python-коде. Например, какие именно трансформации применять или как именно обрабатывать ошибки.
    - **Последствия:** Чтобы понять, как работает пайплайн, недостаточно посмотреть в его `.yaml` файл, нужно читать Python-код, что снижает прозрачность.

3.  **Отсутствие базового класса для пайплайнов:**
    - **Проблема:** Нет общего абстрактного класса, который бы определял скелет алгоритма пайплайна и оставлял для реализации только специфичные для источника детали.
    - **Последствия:** Это является первопричиной дублирования кода (проблема №1).

## 4. Этап 3: План Рефакторинга

### Приоритетные Направления

1.  **Выделение общего кода пайплайнов:** Создать базовый класс или "движок" (Pipeline Engine), который инкапсулирует общую логику оркестрации.
2.  **Декларативное описание трансформаций:** Перенести описание шагов трансформации из Python-кода в конфигурационные `.yaml` файлы.

### Детальный План Задач

#### Задача REF-01: Создать базовый класс для пайплайнов

- **Проблема:** Дублирование кода оркестрации.
- **Цель:** Инкапсулировать общий алгоритм ETL в одном месте, оставив в дочерних классах только специфичную логику.
- **Конкретные шаги:**
    1.  Создать `src/bioetl/application/core/base_pipeline.py` с абстрактным классом `BasePipeline`.
    2.  `BasePipeline` будет принимать в конструкторе все необходимые порты (`LockPort`, `StoragePort`, `CheckpointPort` и т.д.).
    3.  Реализовать в `BasePipeline` основной метод `run()`, который будет содержать общую логику:
        - `acquire_lock()`
        - `load_checkpoint()`
        - Цикл `for record in self._extract()`:
            - `transformed = self._transform(record)`
            - `self._load(transformed)`
        - `save_checkpoint()`
        - `release_lock()`
    4.  Определить в `BasePipeline` абстрактные методы `_extract()`, `_transform()`, `_load()`, которые должны будут реализовать дочерние классы.
- **Риски:** Неправильное проектирование базового класса может сделать его слишком жестким и неподходящим для некоторых пайплайнов.
- **Критерий готовности:** Класс `BasePipeline` создан. Пайплайны `chembl_activity`, `pubchem_compound` и `uniprot_protein` унаследованы от него, их код значительно сократился и не содержит дублирующейся логики оркестрации. Все тесты проходят.

#### Задача REF-02: Создать фабрику трансформаций

- **Проблема:** Шаги трансформации жестко закодированы в Python.
- **Цель:** Сделать пайплайны управляемыми через конфигурацию.
- **Конкретные шаги:**
    1.  Создать `src/bioetl/domain/transformations.py`, где каждая трансформация будет представлена в виде чистой функции (например, `normalize_units(record: dict) -> dict`).
    2.  Создать `src/bioetl/infrastructure/factories/transformation_factory.py`. Эта фабрика будет иметь метод `get_transformation(name: str) -> Callable`.
    3.  В `pipeline_config.py` добавить поле `transform_steps: list[str]` в модель конфигурации.
    4.  В `BasePipeline` (из REF-01) метод `_transform` будет читать `transform_steps` из конфига, получать функции из фабрики и применять их последовательно к записи.
- **Риски:** Усложнение отладки, так как последовательность вызовов определяется во время выполнения.
- **Критерий готовности:** Конфигурации `.yaml` для пайплайнов содержат секцию `transform_steps`. Код пайплайнов больше не содержит явных вызовов функций трансформации.
