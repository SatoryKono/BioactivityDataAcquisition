# Руководство по Архитектурному Обзору Проекта BioETL

**Версия:** 1.0
**Дата:** 2024-07-26

## 1. Введение

Цель этого документа — определить стандартизированный процесс для проведения архитектурного обзора (Architectural Review) проекта BioETL. Этот процесс предназначен для регулярной оценки состояния кодовой базы, выявления технического долга и формирования действенного плана по улучшению архитектуры.

Обзор должен проводиться периодически (например, раз в квартал или перед началом работы над крупным новым функционалом) ведущим инженером проекта.

## 2. Процесс Обзора

Обзор состоит из трех основных этапов:
1.  **Оценка состояния проекта:** Количественная оценка по 10 ключевым категориям.
2.  **Качественный анализ:** Глубокое исследование кода на предмет архитектурных нарушений и "болевых точек".
3.  **Формирование плана рефакторинга:** Создание приоритизированного списка задач по улучшению кода.

---

### 3.2. Процедура Оценки

1.  Для каждой категории провести анализ согласно колонке "Что и где смотреть".
2.  Выставить оценку по 10-балльной шкале (1 – очень плохо, 10 – отлично) с кратким обоснованием.
3.  Рассчитать взвешенный балл: `Взвешенный балл = Вес * Оценка`.
4.  Просуммировать взвешенные баллы для получения итоговой оценки проекта.

### 3.3. Интерпретация Балла

- **8.0 – 10.0 (Отлично):** Проект в прекрасном состоянии. Требуются минимальные улучшения.
- **5.0 – 7.9 (Хорошо):** Проект стабилен, но есть технический долг, который следует устранить в плановом порядке.
- **0.0 – 4.9 (Требует внимания):** Проект имеет серьёзные архитектурные проблемы, которые мешают его развитию. Требуется срочный рефакторинг.

## 4. Этап 2: Качественный Анализ

На этом этапе проводится глубокий анализ кода с целью выявления конкретных проблем.

### Что искать:
- **Нарушение границ слоёв:**
  - **Где:** `src/bioetl/domain/`, `src/bioetl/application/`.
  - **Признаки:** Импорты `httpx`, `redis`, `boto3` или других I/O библиотек. Прямое открытие файлов, работа с сокетами.
- **"Божественные объекты" (God Objects):**
  - **Где:** Везде, но особенно в `application/pipelines` и `infrastructure/adapters`.
  - **Признаки:** Классы с тысячами строк кода, множеством ответственностей (например, пайплайн, который сам ходит в API, сам пишет в 5 таблиц и сам считает аналитику).
- **Утечки абстракций:**
  - **Где:** В сигнатурах методов портов (`domain/ports.py`).
  - **Признаки:** Метод порта принимает аргументы, специфичные для конкретной реализации (например, `def fetch(self, chembl_specific_param: str)` вместо `def fetch(self, query: Query)`).
- **Дублирование кода:**
  - **Где:** Особенно между пайплайнами (`application/pipelines`) или адаптерами (`infrastructure/adapters`).
  - **Признаки:** Похожие блоки кода для логирования, обработки ошибок, получения данных.
- **Смешение ответственности:**
  - **Где:** `interfaces/bootstrap.py`, `interfaces/cli.py`.
  - **Признаки:** `bootstrap.py` содержит бизнес-логику. `cli.py` сам создаёт адаптеры вместо того, чтобы получать их из `bootstrap`.

## 5. Этап 3: Формирование Плана Рефакторинга

На основе количественной оценки и качественного анализа составляется документ с планом рефакторинга.

### Структура Плана

1.  **Сводка:** Краткое изложение результатов обзора и итоговый балл.
2.  **Приоритетные направления:** 2-3 ключевые области, требующие улучшения в первую очередь (например, "Устранение нарушений слоёв", "Выделение общего кода из пайплайнов").
3.  **Детальный план задач:**
    - Каждая задача должна быть сформулирована в виде конкретного, измеримого действия.
    - Для каждой задачи указывается:
        - **ID и Название:** `REF-01: Вынести HTTP-логику из пайплайна X`.
        - **Проблема:** Краткое описание, почему это проблема.
        - **Цель:** Что должно получиться в итоге.
        - **Конкретные шаги:**
            1. Создать новый адаптер в `infrastructure/adapters/`.
            2. Перенести код, связанный с `httpx`, из `application/pipelines/X.py` в новый адаптер.
            3. Заменить прямой вызов `httpx` в пайплайне на вызов метода адаптера через порт.
        - **Риски:** "Может затронуть смежные пайплайны Y и Z".
        - **Критерий готовности:** "Пайплайн X больше не импортирует `httpx`. Тесты для пайплайна X проходят".

### Пример Задачи

- **ID:** `REF-01: Вынести логику кэширования из адаптера ChEMBL.`
- **Проблема:** Адаптер ChEMBL реализует собственное in-memory кэширование, что дублирует функциональность и нарушает принцип единственной ответственности.
- **Цель:** Создать универсальный декоратор или прокси-класс для кэширования, который можно будет применять к любому адаптеру.
- **Шаги:**
    1. Создать `infrastructure/caching/proxy.py` с классом `CachingProxy(DataSourcePort)`.
    2. `CachingProxy` в конструкторе принимает другой `DataSourcePort` и `CachePort`.
    3. В методе `fetch` `CachingProxy` сначала проверяет кэш, и только потом вызывает `fetch` у вложенного адаптера.
    4. В `bootstrap.py` обернуть `ChemblAdapter` в `CachingProxy`.
- **Риски:** Неправильная инвалидация кэша может привести к поставке устаревших данных.
- **Критерий готовности:** Логика кэширования удалена из `ChemblAdapter`. Интеграционные тесты показывают, что при повторном запросе не происходит реального HTTP-вызова.

## 6. Контроль Качества

- **Метрики:** После рефакторинга необходимо заново провести оценку и убедиться, что балл по затронутым категориям вырос.
- **Автоматизация:** Настроить CI-джобы для автоматического контроля:
    - `import-linter` для проверки архитектуры слоёв.
    - `radon` для контроля цикломатической сложности.
    - `pytest --cov` для отслеживания покрытия тестами.
- **Регресс:** Убедиться, что все существующие тесты проходят после рефакторинга.
