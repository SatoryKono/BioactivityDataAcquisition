# D-04 Data Model, IDs & Lineage Specification

Руководство по модели данных Medallion, правилам построения идентификаторов (Entity ID / Content Hash), canonical JSON и lineage/metadata sidecars, а также обязательным проверкам и миграционным требованиям.

## Область действия

- **Model layers**: Bronze/Silver/Gold и системные поля (entity_id, content_hash, `_run_id`, `_source_batch_id`, `_metadata`).  
- **Identifiers**: canonical Entity ID (preferred provider ID) + Content Hash (Version ID) + optional surrogate/composite keys.  
- **Lineage**: `_source_batch_id` на строку + `BaseOutputMetadata` sidecar (run info, bronze_paths, source_batch_ids, transform stats).  
- **History**: SCD Type 2 flows rely on content_hash for dedup/backfill and track dual-write windows.  
- **Compliance**: PII policy, canonical serialization, ADR-driven breaking changes.

## Key principles

| Principle | Description |
| --- | --- |
| **Entity ID first** | Use provider native ID (DOI, PMID, UniProt, ChEMBL, PubChem CID, OpenAlex ID, Semantic Scholar paperId) when available. Fallback: business key normalization (provider:id). |
| **Content Hash** | `sha256(provider + canonical_json(normalized_record))`, excludes `_` prefixed meta fields. Deterministic serialization: sorted keys, compact separators, ASCII, orjson when available. |
| **Normalization** | Float rounding (10 digits), datetime → ISO string, str → `strip()`, NaN/Inf → null, recursive normalization for lists/dicts. |
| **Metadata sidecar** | `BaseOutputMetadata` (record_count, total_bytes, content_hash, timestamps) + extensions per layer (e.g., Bronze: `bronze_paths`, API request details; Silver/Gold: `source_tables`, `transform_steps`). |
| **Lineage trace** | `_source_batch_id` references Bronze batch; sidecar stores mapping to bronze paths + transform version/steps. Storing full Bronze paths per record forbidden. |
| **Dual-service guard** | Breaking normalization changes require ADR, migration plan, dual service (14 days or 2 releases) + adoption >90% + parity + 0 critical DQ before cutover. |
| **PII handling** | Salted hashing in Silver, aggregation/removal in Gold; no PII leaks via logs. |

## Identifier taxonomy

| ID | Purpose | Status |
| --- | --- | --- |
| `entity_id` | Business entity key (provider native ID or normalized provider:id) | MUST for Silver/Gold |
| `content_hash` | Version ID (SHA-256) for dedup/SCD2 | MUST stable + deterministic |
| `surrogate_key` | Internal UUID/auto increment | Avoid as primary identity (non-reproducible) |
| `composite_key` | Business-field set (e.g., provider + external_id) | Controlled merge key only |

### Content hash rules

- Exclude `_`-prefixed meta fields and `META_FIELDS` set (e.g., `_run_id`, `_dq_*`, `_source`).  
- Normalize via centralized hashing API (`hashing.normalize_record()`).  
- Algorithm: `hashlib.sha256(...).hexdigest()` (NIST FIPS 180-4 reference).  
- Any change to canonical JSON/normalization is breaking → requires ADR + migration plan (see D-03).  
- Conflict note: RULES request empty collections normalized to NULL, while hash normalization currently preserves `[]/{}`; ensure transformation code validates pre-hash stage.

## Lineage & metadata

1. **Bronze batch metadata**: Writers emit `.meta.json` with `ingestion_ts`, `run_id`, `run_type`, `batch_id`, `bronze_paths`, `source` info.  
2. **BaseOutputMetadata** (ADR-029): common record_count, total_bytes, content_hash, timestamps; layer-specific extensions (Bronze: API request details, Silver: delta metrics, Gold: partition counts).  
3. **Lineage metadata fields**: `_metadata.source_batch_ids`, `_metadata.bronze_paths`, `_metadata.transform_version`, `_metadata.steps`, `_metadata.source_tables`.  
4. **Run provenance**: `run_id` flows from orchestration boundary to metadata and sidecars (ADR-012 prohibits regenerating run_id locally).  
5. **External models**: aligns with W3C PROV-DM (Entity/Activity/Agent mapping) and OpenLineage facets (`run.runId`, job namespace, dataset dependencies).

## Validation & compliance

- `uv run python -m scripts.schema generate_schema_artifacts --check` (includes canonical JSON + hashing check).  
- `uv run python -m pytest tests/contract/` + `monthly contract-tests` workflow (canonical repo ensures contract coverage for key providers).  
- `scripts/schema/check_contract_parity.py` or equivalent parity diff artifact must run and publish results.  
- Schema drift policy: Info/Critical statuses a) assign owner, b) SLA 48h for Critical, c) unresolved Critical drift blocks release.  
- Breaking contract/identity normalization changes require `breaking-change` label + notification channel (e.g., `#platform-governance`).

## Migration & dual-service policy

1. **Migration steps for PK rename/breaking normalization**: add new canonical PK column → backfill → dual-write window → drop old column only in major release.  
2. **Dual-service window** = `max(14 calendar days, 2 releases)` per ADR-036.  
3. **Cutover criteria**: adoption > 90%, parity checks green, zero critical DQ alerts for 7 days, rollback plan documented.  
4. **Contract change artifacts**: ADR (decision + migration plan + rollback), CHANGELOG entry mapping old→new, automation diff artifact, notifications to consumers (channel defined per release).  
5. **Lineage trace enforcement**: ensure `_metadata.bronze_paths` is populated via sidecar metadata and accessible through lineage tooling.
