# Промты для рефакторинга BioETL

*Документ содержит готовые к использованию промты для проведения рефакторинга кодовой базы BioETL. Каждый промт оптимизирован для работы с AI-ассистентами и содержит достаточный контекст для качественного анализа. Минимальный объём каждого промта — 250 слов для обеспечения полноты инструкций.*

---

## 4.1 Аудит структуры пакетов

**Промт:**

> Проведи глубокий и комплексный аудит текущей структуры каталогов `src/bioetl`. Твоя задача — выявить все структурные проблемы, которые увеличивают когнитивную нагрузку на разработчиков и затрудняют навигацию по кодовой базе. Помни, что каждый лишний файл или папка — это дополнительная точка принятия решений для разработчика, который пытается найти нужный код.
>
> **Этап 1: Поиск дублирующих модулей.**
> Проанализируй все модули и определи, есть ли файлы с идентичной или почти идентичной функциональностью. Обрати особое внимание на модули, которые могут иметь разные имена, но выполнять одинаковые задачи — например, `utils.py` и `helpers.py`, или `parsers.py` и `extractors.py`. Проверь наличие копипасты между модулями: сравни функции с похожими сигнатурами, найди одинаковые регулярные выражения, идентичные алгоритмы обработки. Для каждой пары дубликатов укажи: какой модуль является основным и должен остаться, какой можно безопасно удалить, какие зависимости придётся обновить после удаления, какие тесты затронет это изменение. Составь карту дублирования в формате таблицы: модуль-источник, модуль-дубликат, процент совпадения кода, рекомендуемое действие.
>
> **Этап 2: Выявление файлов с пересекающейся ответственностью.**
> Найди модули, которые нарушают принцип единственной ответственности (SRP — Single Responsibility Principle). Это файлы, которые одновременно занимаются несколькими несвязанными задачами — например, и валидацией данных, и форматированием вывода, и логированием, и бизнес-логикой. Особенно внимательно проверь так называемые «god-модули» размером более 500 строк, которые часто становятся свалкой для разнородного кода. Для каждого такого файла составь список всех обязанностей, которые он выполняет, и предложи, как разделить его на несколько модулей с чёткой ответственностью, или как перенести лишнюю функциональность в более подходящее место. Укажи конкретные диапазоны строк для каждой ответственности.
>
> **Этап 3: Идентификация слишком мелких файлов.**
> Выяви все файлы размером менее 40–60 строк кода (без учёта комментариев, docstrings и импортов). Мелкие файлы создают навигационный шум и заставляют разработчика открывать множество вкладок для понимания простой логики. Для каждого такого файла определи: является ли он осмысленной единицей абстракции (например, содержит важный публичный API), или его содержимое логичнее разместить в родственном модуле. Учитывай, что мелкие файлы оправданы только если они: экспортируют критически важные публичные интерфейсы, являются точками входа в подсистему, содержат изолированную конфигурацию, определяют исключения или константы для всего пакета. Во всех остальных случаях предложи слияние с соседними модулями.
>
> **Этап 4: Анализ разделения слоёв.**
> Проверь, соблюдается ли разделение на слои согласно архитектуре проекта: domain, application, infrastructure, composition, interfaces. Найди все нарушения архитектурных границ, когда: модуль из domain импортирует что-либо из infrastructure (нарушение dependency rule), модуль application содержит детали реализации вместо оркестрации, слой interfaces содержит бизнес-логику вместо делегирования, composition содержит логику вместо чистой сборки зависимостей. Используй статический анализ импортов для построения графа зависимостей между слоями. Для каждого нарушения укажи: файл и строку с проблемным импортом, почему это нарушение архитектуры, как исправить (переместить код, создать интерфейс, инвертировать зависимость).
>
> **Ожидаемый результат:**
> Сформируй итоговый отчёт с конкретными предложениями по укрупнению структуры. Укажи, какие папки можно полностью удалить, какие модули объединить, какие переименовать для лучшей консистентности с naming-policy проекта. Предложи целевую структуру каталогов в виде дерева с обоснованием каждого решения. Оцени трудоёмкость миграции в человеко-часах с разбивкой по этапам. Определи приоритеты: что рефакторить в первую очередь (quick wins), что требует глубокого редизайна.

## 4.2 Рефакторинг пайплайнов

**Промт:**

> Выполни детальный анализ всех пайплайнов в директории `src/bioetl/pipelines/**` и связанных модулей в `application/transformers`, `application/services`. Твоя цель — радикально упростить структуру пайплайнов, сократив количество файлов, классов и этапов обработки данных. Текущая архитектура может содержать избыточную декомпозицию, которая усложняет понимание потока данных, затрудняет отладку и замедляет добавление новых пайплайнов. Помни правило: если для понимания одного пайплайна нужно открыть более 5-7 файлов, структура переусложнена.
>
> **Анализ текущего состояния.**
> Для каждого пайплайна (ChEMBL compound, ChEMBL activity, PubChem, UniProt и т.д.) построй полный граф зависимостей между модулями: какие файлы импортируют друг друга, как данные передаются между стадиями, где происходят трансформации. Визуализируй путь одной записи от входа (raw API response) до выхода (Gold-слой Parquet). Подсчитай: сколько файлов и классов задействовано в обработке, сколько промежуточных структур данных создаётся, сколько раз данные сериализуются и десериализуются. Выяви «мёртвый код» — функции и классы, которые определены, но никогда не вызываются в production-потоке, или вызываются только из тестов. Для каждого мёртвого фрагмента укажи: можно ли безопасно удалить, или он нужен для будущей функциональности.
>
> **Объединение стадий transform, validate, normalize.**
> Проанализируй целесообразность слияния этих трёх стадий в единый модуль `process` или `transform`. Текущее разделение может быть избыточным, если: валидация не требует отдельного шага и может быть встроена в трансформацию через Pandera-аннотации, нормализация — это просто часть трансформации без собственной логики, между стадиями нет возможности подключения альтернативных реализаций. Определи: какие интерфейсы и контракты придётся изменить при слиянии, какие тесты потребуют переписывания, как изменится трассировка ошибок (сохранится ли понимание, на каком этапе произошла проблема). Предложи унифицированный интерфейс обработки данных — например, единый метод `process(df: DataFrame) -> DataFrame` с декларативной конфигурацией шагов, который заменит три отдельных контракта.
>
> **Вынесение вспомогательного кода в утилиты.**
> Проведи grep-анализ повторяющегося кода между разными пайплайнами. Типичные кандидаты на выделение: функции парсинга дат в разных форматах (ISO, Unix timestamp, human-readable), нормализации строк (trim, lowercase, удаление спецсимволов), валидации идентификаторов (SMILES, InChI, UniProt ID, ChEMBL ID), форматирования чисел (научная нотация, округление, обработка NaN/Inf), работы с отсутствующими данными (fillna-стратегии, default values). Для каждого паттерна укажи: в каких пайплайнах он встречается (список файлов со строками), сколько раз дублируется, какова степень идентичности (100% копипаста или вариации). Предложи структуру общего модуля утилит: разделение на категории (string_utils, date_utils, validation_utils, format_utils, null_utils), публичный API каждой категории, примеры использования.
>
> **Оптимизация схем и конфигов.**
> Проанализируй все YAML/JSON конфигурации пайплайнов в `configs/pipelines/` и все Pydantic/Pandera схемы. Определи: какие конфиг-файлы дублируют друг друга (например, DQ-правила для разных сущностей одного провайдера), какие поля повторяются во всех схемах и могут быть вынесены в базовую схему, какие конфиги можно объединить через параметризацию вместо дублирования. Особо обрати внимание на explosion схем Bronze/Silver/Gold — часто Silver-схема отличается от Bronze только добавлением служебных полей, а Gold — только фильтрацией колонок. Предложи декларативный способ описания этих различий вместо полного дублирования определений.
>
> **Ожидаемый результат:**
> Создай целевой шаблон пайплайна (в виде кода или псевдокода), показывающий оптимальную структуру файлов и классов для одного провайдера/сущности. Шаблон должен содержать не более 3-4 файлов на пайплайн. Составь пошаговый миграционный план с указанием: порядка рефакторинга (начиная с самого простого пайплайна как пилота), точек отката после каждого этапа, критериев успешности (тесты проходят, метрики производительности не деградировали). Оцени потенциальное сокращение: количества файлов в процентах, общего LOC, времени на создание нового пайплайна.

## 4.3 Унификация клиентов

**Промт:**

> Проведи всесторонний анализ директории `src/bioetl/infrastructure/adapters/http` (или `clients`) с целью унификации архитектуры HTTP-клиентов для внешних источников данных. Текущая реализация может содержать значительное дублирование кода между клиентами ChEMBL, PubChem, UniProt, CrossRef, SemanticScholar и другими провайдерами, что затрудняет добавление новых источников, увеличивает поверхность для багов и замедляет поддержку существующих интеграций. Каждый новый провайдер не должен требовать написания сотен строк boilerplate-кода — большая часть логики должна переиспользоваться.
>
> **Инвентаризация повторяющихся паттернов.**
> Для каждого существующего клиента (адаптера) детально проанализируй и задокументируй реализацию следующих паттернов: логика повторных попыток (retry) — используемые backoff-стратегии, максимальное количество попыток, какие ошибки считаются retriable; обработка HTTP-ошибок (4xx, 5xx) — какие коды обрабатываются специально, какие пробрасываются как исключения; парсинг ответов — JSON, XML, другие форматы, обработка вложенных структур; пагинация — offset/limit, cursor-based, link headers, специфичные для API механизмы; rate limiting — token bucket, fixed window, соблюдение заголовков X-RateLimit, Retry-After; логирование — что логируется (URL, timing, payload размер), на каком уровне; таймауты — connect timeout, read timeout, total timeout. Создай матрицу «клиент × паттерн», показывающую, какие клиенты реализуют какие паттерны и насколько их реализации похожи (процент совпадения кода). Выдели паттерны, которые реализованы во всех клиентах идентично или почти идентично — это первоочередные кандидаты на вынос в базовый класс.
>
> **Проектирование BaseClient.**
> Предложи детальную архитектуру базового класса `BaseHttpAdapter` (или `BaseClient`), который инкапсулирует всю общую функциональность. Проработай структуру класса: какие методы должны быть абстрактными (обязательны для реализации в каждом подклассе — например, `_parse_response`, `_build_url`), какие — конкретными с общей логикой (например, `_make_request_with_retry`, `_handle_rate_limit`), какие — хуками для опционального переопределения (например, `_on_request_start`, `_on_request_complete`). Разработай контракт конфигурирования клиента через dataclass или Pydantic-модель: base_url, default_headers, timeout_config (connect, read, total), retry_config (max_attempts, backoff_factor, retriable_statuses), rate_limit_config (requests_per_second, burst_capacity). Предусмотри расширяемость через dependency injection: возможность подключения кастомного HTTP-backend (httpx, aiohttp, requests), кастомного сериализатора/десериализатора, кастомного rate limiter.
>
> **Унификация парсеров ответов.**
> Проанализируй, как разные клиенты парсят ответы API. Выяви общие паттерны: извлечение данных из вложенных структур (data.items, response.results), обработка пагинации (next_page_url, total_count, has_more), нормализация полей (camelCase → snake_case, вложенные объекты → плоские). Предложи механизм декларативного описания маппинга ответа на внутреннюю модель данных — например, через JSONPath-выражения или Pydantic-модели с field aliases. Это позволит минимизировать boilerplate-код парсинга в каждом клиенте и сконцентрировать всю логику маппинга в конфигурации.
>
> **Сокращение количества классов и файлов.**
> Определи, какие клиенты настолько похожи, что их можно реализовать как параметризованные экземпляры одного класса, а не как отдельные подклассы. Например, если два клиента отличаются только базовым URL, структурой ответа и названием поля пагинации, их можно заменить на единый GenericRestClient с конфигурацией. Предложи целевое количество файлов и классов с обоснованием. Оптимальный вариант: один BaseHttpAdapter, 2-3 специализированных миксина (PaginatedMixin, RateLimitedMixin), и минимальные subclass-ы только для провайдеров с уникальной логикой.
>
> **Ожидаемый результат:**
> Разработай полный архитектурный шаблон клиента с примером кода BaseHttpAdapter (минимум 100 строк показательного кода). Составь план миграции существующих клиентов на новую архитектуру с указанием: приоритетов (какие клиенты мигрировать первыми — обычно самые простые для валидации подхода), рисков (где наиболее вероятны регрессии — обычно клиенты с нестандартной пагинацией или аутентификацией), метрик успеха (LOC на клиент, время добавления нового провайдера, количество багов в интеграциях). Оцени ожидаемое сокращение LOC в процентах для всей директории клиентов.

## 4.4 Упрощение схем

**Промт:**

> Выполни комплексный анализ всех схем данных в проекте: Pydantic-модели в `domain/entities`, `application/dto`, DTO-классы, Pandera DataFrameSchemas в `application/transformers/schemas`, TypedDict и dataclass-определения. Цель — минимизировать количество схем, устранить дублирование полей и создать автоматизируемую систему генерации схем из единого источника истины (Single Source of Truth). Каждая дублирующаяся схема — это потенциальное расхождение при изменениях и дополнительная нагрузка на поддержку.
>
> **Инвентаризация существующих схем.**
> Составь полный каталог всех схем в проекте. Для каждой схемы зафиксируй: полное имя класса, модуль/файл где определена, тип (Pydantic BaseModel, Pandera DataFrameModel, TypedDict, dataclass, NamedTuple, Protocol), количество полей, количество импортов этой схемы в других модулях (популярность), слой архитектуры (domain/application/infrastructure). Представь результат в виде таблицы, отсортированной по количеству использований — схемы с нулевым использованием это «orphan»-схемы, кандидаты на удаление. Для orphan-схем проверь: возможно они используются только в тестах (тогда переместить в tests/), возможно это deprecated-код (тогда удалить), возможно это planned-but-not-implemented (тогда документировать или удалить).
>
> **Анализ дублирования полей.**
> Построй матрицу «поле × схема», показывающую, в каких схемах встречаются какие поля. Для каждого поля укажи: имя, тип, значение по умолчанию (если есть), в скольких схемах встречается. Выяви группы схем с высоким пересечением полей (>70% общих полей) — это кандидаты на объединение через наследование или композицию. Определи «универсальные» поля, которые присутствуют почти везде: id-поля (molecule_id, assay_id), временные метки (created_at, updated_at, _ingested_at), служебные поля (_source, _run_id, _batch_id). Предложи механизм их централизованного определения: базовый класс TimestampMixin, IdentifiableMixin, SourceTrackingMixin, от которых наследуются конкретные схемы. Это сократит дублирование и обеспечит консистентность.
>
> **Выявление одноразовых схем.**
> Найди схемы, которые используются ровно в одном месте и не экспортируются из модуля через `__all__`. Для каждой такой схемы оцени: оправдано ли её существование как отдельного типа, или её можно инлайнить прямо в коде. Критерии для инлайнинга: схема используется только для валидации в одном методе, схема не переиспользуется и не планируется к переиспользованию, схема не является частью публичного API. Для инлайн-кандидатов предложи замену: TypedDict для простых структур, Literal для перечислений, простой dict с комментарием для внутренних структур. Исключение: схемы для сериализации/десериализации JSON всегда должны быть явными для читаемости.
>
> **Унификация Bronze/Silver/Gold схем.**
> Проанализируй схемы Medallion-архитектуры для каждой сущности (compound, activity, assay, target и т.д.). Определи, какие преобразования происходят между слоями: какие поля добавляются в Silver (обычно _source, _ingested_at, normalized-версии), какие удаляются или переименовываются, какие поля добавляются в Gold (агрегаты, computed-поля), какие фильтруются (удаление служебных полей). Предложи механизм автоматической генерации Silver-схемы из Bronze и Gold из Silver. Варианты реализации: декоратор `@silver_from(BronzeSchema, add_fields=[...], remove_fields=[...])`, функция-генератор `generate_silver_schema(bronze_cls, transformations)`, наследование с переопределением `class SilverCompound(BronzeCompound, SilverMixin)`. Это устранит необходимость вручную синхронизировать три копии почти идентичных схем.
>
> **Ожидаемый результат:**
> Предложи минимальный набор «корневых» моделей (root schemas), из которых все остальные схемы генерируются или наследуются. Примерная структура: 5-7 базовых entity-схем в domain, автогенерируемые Bronze/Silver/Gold варианты, 2-3 миксина для служебных полей. Разработай логику генерации схем: какой инструмент использовать (datamodel-codegen для API-схем, кастомный генератор для Medallion-слоёв), как встроить генерацию в CI (pre-commit hook или отдельный скрипт), как валидировать консистентность схем после генерации (schema diff check). Оцени итоговое сокращение: количества schema-классов в процентах, строк кода в schema-модулях.

## 4.5 Переработка naming-policy

**Промт:**

> Проведи критический анализ документа с политикой именования (`docs/00-project/governance/02-naming-policy.md` или аналогичного) с целью радикального упрощения правил. Текущая политика может содержать избыточные требования, которые создают трение при разработке, усложняют code review субъективными замечаниями по стилю, увеличивают время onboarding новых разработчиков и не приносят ощутимой пользы для качества и читаемости кода. Хорошая naming policy должна быть короткой, запоминающейся и автоматически проверяемой.
>
> **Аудит существующих правил.**
> Составь полный перечень всех правил именования из документа. Для каждого правила зафиксируй: формулировку правила, категорию (именование модулей, классов, функций, переменных, констант, файлов), обязательность (MUST, SHOULD, MAY). Затем для каждого правила определи: какую конкретную проблему оно решает — приведи реальные примеры багов, путаницы или maintenance-проблем, которые правило предотвращает; сколько раз правило реально нарушалось за историю проекта — проанализируй git history, PR comments, issues; насколько сложно правило запомнить и последовательно применять для нового разработчика, пришедшего из другого проекта с другими конвенциями; автоматизируемо ли правило — можно ли написать linter-проверку, или требуется субъективное человеческое суждение.
>
> **Выявление чрезмерных правил.**
> Определи правила, которые попадают в одну или несколько категорий проблемных: правила для редких случаев — регулируют ситуации, возникающие менее чем в 5% кода (например, правила для метаклассов или декораторов верхнего уровня); дублирование PEP — повторяют стандартные Python-конвенции из PEP8, PEP257, PEP484 (нет смысла дублировать то, что и так проверяется стандартными линтерами); противоречивые правила — требуют исключений для определённых случаев, что создаёт неопределённость; правила с высокой когнитивной нагрузкой — требуют запоминания сложных паттернов (например, «методы для X используют префикс foo_, а для Y — суффикс _bar»). Для каждого проблемного правила предложи: удалить полностью (если пользы нет), упростить и обобщить (объединить несколько частных правил в одно общее), понизить до рекомендации (SHOULD вместо MUST), заменить автоматической проверкой (линтер вместо ручного review).
>
> **Анализ реального применения.**
> Проверь кодовую базу на соответствие каждому правилу документа. Используй grep, ast-анализ, custom scripts для количественной оценки. Для каждого правила определи: процент соответствия (сколько именований в коде следуют правилу), количество нарушений (с конкретными примерами), наличие «blessed exceptions» — случаев, когда нарушение очевидно допустимо. Выяви три категории правил: правила, которые никогда не нарушались — возможно, они слишком очевидны и могут быть удалены как избыточные (все и так знают, что классы в PascalCase); правила, которые постоянно нарушаются — возможно, они нереалистичны, и их нужно ослабить или удалить; правила, которые требуют ручной проверки — это узкое место, их нужно автоматизировать или упростить.
>
> **Оценка влияния на CI и DX (Developer Experience).**
> Определи, какие правила уже проверяются автоматически в CI (через flake8, pylint, ruff, mypy, custom linters), какие требуют ручного review, какие вообще никак не проверяются (существуют только в документе). Для автоматизируемых правил оцени: сколько времени они добавляют к CI pipeline, сколько ложных срабатываний генерируют (false positives, которые приходится подавлять через # noqa), сколько времени разработчики тратят на исправление warning-ов. Для ручных правил оцени: сколько PR-комментариев в среднем посвящено naming issues, сколько раз naming-дискуссии блокировали merge. Предложи оптимальный баланс между строгостью проверок, скоростью CI и удобством разработки.
>
> **Ожидаемый результат:**
> Создай упрощённую версию naming-policy, сократив количество правил минимум вдвое. Целевой объём документа — не более 1-2 страниц (текущие многостраничные guidelines никто не читает полностью). Для каждого оставшегося правила предложи: формулировку в одно-два предложения (чем короче, тем лучше запоминается), пример правильного и неправильного кода (наглядность важнее объяснений), способ автоматической проверки (конкретный linter и конфигурация). Опиши изменения в CI-конфигурации, необходимые для поддержки новой политики: какие правила добавить в ruff/flake8, какие убрать, какие custom-проверки написать.

## 4.6 Оптимизация слоёв проекта

**Промт:**

> Выполни фундаментальный анализ архитектурных слоёв проекта BioETL: domain, application, infrastructure, composition, interfaces. Цель — критически оценить необходимость пятислойной архитектуры и предложить консолидацию там, где разделение создаёт больше накладных расходов, чем пользы. Каждый слой должен зарабатывать своё существование — приносить ощутимую пользу в виде изоляции, тестируемости или переиспользуемости. Слои, которые существуют «для чистоты архитектуры», но усложняют навигацию и увеличивают количество файлов, должны быть пересмотрены или объединены.
>
> **Анализ текущей архитектуры по метрикам.**
> Для каждого слоя собери количественные метрики: количество файлов и модулей, количество классов (включая abstract/concrete разбивку), общий LOC, средний размер класса в строках. Оцени связность внутри слоя (cohesion) — насколько модули внутри слоя связаны друг с другом логически и по импортам. Оцени связанность с другими слоями (coupling) — сколько импортов направлено в другие слои и из других слоёв. Построй матрицу зависимостей между слоями: для каждой пары (layer_from, layer_to) подсчитай количество import-statements. Визуализируй результат как heatmap или dependency graph. Выяви нарушения: циклические зависимости между слоями (A→B→C→A), импорты из «нижних» слоёв в «верхние» (infrastructure→application, composition→domain), «обходные пути» через третий слой.
>
> **Кандидаты на удаление: классы и модули.**
> Систематически проанализируй каждый класс и модуль на предмет необходимости существования. Кандидаты на удаление или инлайнинг: классы менее 50 строк без учёта docstrings — если логика тривиальна, возможно её можно инлайнить в вызывающий код; thin wrappers — классы, которые просто делегируют вызовы другому классу без добавления логики; дублирование stdlib/external — классы, которые реинвентируют функциональность из стандартной библиотеки или зависимостей (например, кастомный Result вместо returns.Result, кастомный retry вместо tenacity); single-use classes — классы, которые инстанциируются ровно в одном месте и могут быть заменены функцией. Для каждого кандидата укажи: где используется, какой код изменится после удаления, есть ли риски (потеря расширяемости, ухудшение тестируемости).
>
> **Возможности слияния слоёв.**
> Оцени конкретные варианты консолидации архитектуры. Вариант 1: трёхслойная архитектура (presentation/business/data) — объединение domain+application в business, infrastructure остаётся data, interfaces становится presentation, composition распределяется. Вариант 2: двухслойная архитектура (application/infrastructure) — domain поглощается application (доменные сущности становятся просто моделями), interfaces поглощается application (CLI/API просто точки входа), composition инлайнится в bootstrap. Вариант 3: hybrid — сохранение только слоёв с доказанной пользой. Для каждого варианта определи: какие конкретно модули куда переезжают, как изменится структура каталогов (новое дерево папок), какие импорты придётся массово переписать, как изменятся имена модулей (application.services.x → business.x). Оцени трудоёмкость каждого варианта.
>
> **Сокращение интерфейсов и абстракций.**
> Проанализируй все абстрактные классы (ABC), Protocol-определения и интерфейсы в проекте. Для каждого определи: сколько реализаций существует, используется ли полиморфизм (подстановка разных реализаций в runtime), нужен ли интерфейс для тестирования (подмена моками). Выяви проблемные абстракции: интерфейсы с единственной реализацией — если нет и не планируется альтернативных реализаций, интерфейс — преждевременная абстракция; интерфейсы с избыточными методами — не все методы интерфейса используются вызывающим кодом (нарушение Interface Segregation); дублирующие интерфейсы — несколько Protocol с похожими сигнатурами (например, Reader и Fetcher с идентичным `read()` методом). Предложи минимальный набор интерфейсов, необходимых для: инверсии зависимостей между слоями, подмены реализаций в тестах (мокирование), конфигурируемости (выбор storage backend). Все остальные интерфейсы — кандидаты на удаление или инлайнинг в конкретные классы.
>
> **Ожидаемый результат:**
> Разработай целевую архитектуру с чётким обоснованием количества слоёв. Документ должен содержать: сравнительную таблицу текущей и предлагаемой архитектуры (метрики «было/стало»), диаграмму зависимостей «до» и «после» (можно в Mermaid или PlantUML), детальный маппинг модулей (откуда и куда переезжает каждый файл). Составь миграционный план с: порядком изменений (какие модули рефакторить первыми — рекомендуется начинать с leaf-модулей без зависимых), контрольными точками (как валидировать корректность после каждого этапа — запуск тестов, проверка импортов), оценкой трудоёмкости по этапам. Определи метрики успеха: целевое количество файлов, целевое количество слоёв, целевое количество интерфейсов, максимально допустимый coupling между слоями.

## 5. Итог

**Стратегия упрощения:** меньше файлов, меньше абстракций, меньше этапов пайплайна, меньше схем, меньше правил.

**Принципы применения промтов:**

1. **Инкрементальность** — применяй промты по одному, завершая полный цикл «анализ → план → реализация → валидация» перед переходом к следующему. Не пытайся провести глобальный рефакторинг всего проекта за один раз.

2. **Измеримость** — перед началом зафиксируй метрики: общий LOC, количество файлов, количество классов, время CI, время на создание нового пайплайна. После завершения сравни с исходными и убедись, что показатели улучшились.

3. **Обратимость** — создавай точки отката (git tags или branches) перед каждым крупным изменением. Это позволит вернуться к рабочему состоянию, если рефакторинг создаст неожиданные проблемы.

4. **Верификация** — после каждого этапа рефакторинга запускай полный набор тестов (`pytest --cov`), проверяй coverage (не должен упасть), проверяй type-check (`mypy`), запускай линтеры.

5. **Документирование** — для каждого крупного изменения создавай ADR (Architecture Decision Record) с обоснованием принятого решения.

**Порядок применения промтов (рекомендуемый):**

1. Начни с **4.1 Аудит структуры** — это даст общую картину проблем.
2. Затем **4.4 Упрощение схем** — сокращение схем влияет на все пайплайны.
3. После этого **4.2 Рефакторинг пайплайнов** — с упрощёнными схемами будет легче.
4. Параллельно **4.3 Унификация клиентов** — относительно изолированная задача.
5. После кодовых изменений **4.5 Naming-policy** — адаптация правил к новой структуре.
6. В конце **4.6 Оптимизация слоёв** — это самое масштабное изменение, его лучше делать на «очищенной» кодовой базе.

Для полноценного аудита требуется доступ к распакованному дереву `src/`, `configs/`, `tests/`.
