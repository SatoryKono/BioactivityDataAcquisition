# План отрицательных сценариев защиты слияния (0.5)

**Исполнитель:** Владелец репозитория (требует записи в репозиторий)
**Цель:** Снятие статуса UNAVAILABLE 0.5 (предпосылка миграции агрегатора 1.1)

## Ограничения и условия (Границы)
- Не ослаблять ruleset ради сценариев.
- Не отключать обязательные проверки.
- Единственный блокер доступа аудитора (403 на rule-suites) обходится через наблюдение поведения `merge` вместо чтения истории.
- Сценарии не изменяют пороги, baseline и исходные доказательства.
- После фиксации результатов необходимо восстановить исходное состояние (тестовые PR закрыть).

## Сценарии проверки

### Сценарий A — отказ обязательного контекста
- **Точные действия:** Создать тестовый PR, который гарантированно вызывает отказ (failure) в обязательной проверке `class-lane`. Попытаться выполнить merge (наблюдение поведения вместо чтения истории).
- **Ожидание:** Запрет merge для всех классов акторов.
- **Способ фиксации:** Записать ответ API попытки merge (ожидаемый отказ) и статус агрегатора.
- **Границы (что не проверяется):** Не проверяется история применения правил, только фактическое поведение merge.

### Сценарий B — отмена прогона
- **Точные действия:** Создать тестовый PR, запустить прогон и выполнить cancel (отмену) прогона PR до его завершения (`force-cancel` не используется). Попытаться выполнить merge.
- **Ожидание:** Отсутствие валидного success → запрет merge.
- **Способ фиксации:** Записать статус прогона и дословный ответ API попытки merge.
- **Границы (что не проверяется):** Поведение при `force-cancel` не проверяется.

### Сценарий C — отсутствующий обязательный контекст
- **Точные действия:** В отдельном тестовом PR изменить только job-level `if` у `class-lane` в `.github/workflows/pr-required.yml` на `${{ false }}` как контролируемую инъекцию отказа. Classifier, его outputs/decision matrix, сборщик результатов и агрегатор оставить без изменений. Изменение самого workflow должно дать хотя бы одно решение `required`, принадлежащее `class-lane`; до попытки merge проверить это по сохранённому output classifier. Если такого решения нет, сценарий не выполнен: штатный skip при всех `not_applicable` относится к D. Не переносить тестовый workflow в main. Попытаться выполнить merge тестового PR.
- **Ожидание:** Запрет merge. Пропущенный job может сообщать "Success", но агрегатор обязан упасть (проверяются обе стороны).
- **Способ фиксации:** Сохранить точный head SHA, diff инъекции, полный decision matrix и имя required gate/owner, статус пропущенного job, сформированный lane-results JSON, статус агрегатора (упал) и дословный ответ API попытки merge. Решение `required` и результаты должны относиться к одному SHA/run/attempt.
- **Границы (что не проверяется):** Изменение конфигурации ruleset не производится.

### Сценарий D — разрешённый not_applicable
- **Точные действия:** Создать тестовый PR, где решение classifier'а выдает проверяемое основание для статуса `not_applicable`. Попытаться выполнить merge.
- **Ожидание:** Разрешение merge.
- **Способ фиксации:** Записать решение classifier'а с проверяемым основанием и дословный ответ API попытки merge.
- **Границы (что не проверяется):** Не изменяются пороги/baseline.

## Критерий снятия UNAVAILABLE
Все четыре сценария должны быть зафиксированы по форме акта, и фактический результат каждого должен совпасть с ожидаемым: A–C запрещают merge, D разрешает merge и завершается успешным merge отдельного безопасного тестового PR. У D должны отсутствовать другие блокеры (review, конфликт, ограничения актора); иначе положительный контроль не выполнен.
Любое несовпадение, включая отказ в D, либо недостаточность доказательств сохраняет UNAVAILABLE с указанием причины. Повторная попытка без изменения условий не снимает статус. Исполнение и успешное слияние положительного контроля требуют отдельного разрешения владельца; настоящий PR содержит только план и не выполняет эти действия.
