## 3) Архитектурные инварианты (MUST)

### 3.1 Слои

- `domain/` — чистая бизнес-логика, порты (Protocols), **без I/O**.
- `application/` — orchestration/use-cases.
- `composition/` — composition root, DI, factories.
- `infrastructure/` — адаптеры, реализация портов.
- `interfaces/` — CLI и точки входа.

### 3.2 Импорты

- Нельзя ломать границы слоёв: любой запрещённый импорт — blocker.
- Порты импортировать через фасад `bioetl.domain.ports`.
- Допустимы cross-layer импорты только в `TYPE_CHECKING`, где это явно разрешено правилами.

### 3.3 DI и состояние

- Внедрение зависимостей через конструктор.
- Нельзя создавать внешние зависимости внутри бизнес-классов.
- Нельзя использовать Service Locator.

### 3.4 Запреты в коде

- Нет `print()` в production-коде; использовать структурированное логирование.
- Нет hardcoded secrets.
- Нет sentinel-значений (`-1`, `"N/A"`) вместо `None`.
- Нет блокирующего I/O в async-коде.

## 4) Data/ETL инварианты (MUST)

- **Bronze**: JSONL + zstd, append-only.
- **Silver**: только **Delta Lake** (raw parquet для Silver запрещён).
- **Gold**: строгая валидация и согласованная стратегия загрузки.

Дополнительно:

- Детерминизм пайплайна (порядок, UTC, воспроизводимость).
- DQ-thresholds: >5% warning, >20% fail batch.
- Hashing: `sha256(provider + canonical_json_dumps(record))` с нормализацией и исключением служебных полей.

## 5) Deployment/operations контекст

## 6) Протокол верификации (обязателен перед выводами)

Перед любым архитектурным утверждением:

1. Найти фактический файл и строки.
1. Прочитать реализацию, а не только сигнатуры.
1. Проверить делегирование (большой файл ≠ god object).
1. Проверить импорты по факту.
1. Сверить покрытие/тесты рядом с изменяемым модулем.

Рекомендуемые команды:

```bash
wc -l <file>
rg "^from|^import" <file>
rg "self\._.*\." <file>
rg "ClassName|function_name" tests/
uv run python -m pytest tests/architecture/ -v
uv run python -m mypy --strict src/bioetl/
```

## 7) Оркестрация подзадач (для сложных изменений)

Используй безопасный порядок:

1. Baseline audit.
1. План (`RF-*`).
1. Baseline tests.
1. Реализация (`src/` + `configs/`).
1. Final tests (`lint`, `test`, architecture).
1. Обновление документации.
1. Final audit.

Если артефакты задачи сохраняются, класть в:
`docs/99-archive/reports/<task-id>/`.

## 8) Формат архитектурного аудита

Для каждого finding:

- Severity: MUST/SHOULD/MAY.
- Location: `path:line-line`.
- Rule violated: ссылка на правило.
- Evidence: минимальный код-фрагмент.
- Impact.
- Recommendation.
- Verification command.

Если доказательств недостаточно — не маркируй как нарушение.

## 9) Definition of Done для Codex

Задача считается завершённой, когда:

1. Изменения соответствуют слоевой архитектуре и DI.
1. Типизация/линтеры/тесты пройдены или явно объяснены ограничения среды.
1. Обновлена документация (если изменилось поведение/контракты).
1. В отчёте нет недоказанных утверждений.
