  Ты — технический аудитор файловой структуры проекта BioETL.
                                                                                                                                                                                                                      
  Задача                                                                                                                                                                                                            

  Провести 2 независимых аудита файловой структуры проекта, консолидировать результаты и предложить план рефакторинга.

  Этап 1: Два независимых аудита

  Запусти параллельно двух агентов-аудиторов. Каждый работает изолированно, без доступа к результатам другого.

  Аудитор A — Структурный аудит (top-down)

  Анализ организации директорий и модулей:

  1. Глубина вложенности: директории глубже 5 уровней от src/bioetl/
  2. Раздутые пакеты: директории с >15 .py файлами на одном уровне
  3. Одинокие модули: пакеты с единственным файлом (кроме __init__.py)
  4. Пустые/формальные __init__.py: только __all__ или пусто — нужен ли пакет?
  5. Симметрия слоёв: каждый provider в infrastructure/adapters/ должен иметь зеркальную структуру (client.py, transformer.py, exceptions.py)
  6. Test-to-source mapping: для каждого src/bioetl/{layer}/{module}.py существует tests/unit/{layer}/test_{module}.py?
  7. Orphaned files: файлы, не импортируемые ни одним другим модулем

  Формат вывода:
  findings:
    - id: SA-001
      category: structure|symmetry|orphan|depth|bloat
      severity: CRITICAL|HIGH|MEDIUM|LOW
      location: path/to/dir/
      description: "..."
      evidence: "команда → результат"
      recommendation: "..."

  Аудитор B — Семантический аудит (bottom-up)

  Анализ содержимого и именования:

  1. Нарушение SRP: файлы, содержащие >3 публичных классов или >2 несвязанных ответственности
  2. Naming drift: имя файла не отражает содержимое (например, utils.py с бизнес-логикой)
  3. Дублирование логики: одинаковые/похожие функции в разных модулях (>70% similarity)
  4. Misplaced modules: файл в неправильном слое по содержимому (например, domain-логика в infrastructure)
  5. Circular dependency clusters: группы модулей с циклическими импортами
  6. Config sprawl: конфиги разбросаны по нескольким местам вместо единой точки
  7. God modules: файлы >500 LOC без делегирования (проверить через self._component.method() count)

  Формат вывода: аналогичный, с prefix SB-XXX.

  Этап 2: Консолидация

  Объедини находки обоих аудиторов:

  1. Пересечения: проблемы, найденные обоими (повысить confidence)
  2. Уникальные: проблемы, найденные только одним (проверить валидность)
  3. Конфликты: противоречащие выводы (разрешить с обоснованием)

  Итоговая таблица:

  ┌─────┬──────────┬──────┬───────────┬──────────┬─────────────────┐
  │ ID  │ Severity │ Оба? │ Категория │ Описание │ Файл/директория │
  ├─────┼──────────┼──────┼───────────┼──────────┼─────────────────┤
  └─────┴──────────┴──────┴───────────┴──────────┴─────────────────┘

  Этап 3: План рефакторинга

  На основе консолидированных результатов:

  1. Приоритет 1 (CRITICAL/HIGH): блокеры архитектуры
  2. Приоритет 2 (MEDIUM): улучшения структуры
  3. Приоритет 3 (LOW): косметика и оптимизация

  Для каждой задачи:
  RF-FS-XXX: [Название]
    Severity: ...
    Находки: [ссылки на ID из консолидации]
    Действие: конкретные шаги (move/merge/split/rename/delete)
    Риск: LOW|MEDIUM|HIGH (вероятность регрессии)
    Тесты: какие тесты затронуты

  Ограничения

  - НЕ менять код — только анализ и план
  - Учитывать .claude/rules/ai-selfreview-rules.md (ARCH-001..008, NAME-001..009)
  - Исключения из EXC-001..015 НЕ флагить как проблемы
  - tests/ и docs/ — анализировать только на mapping к source, не на внутреннюю структуру
