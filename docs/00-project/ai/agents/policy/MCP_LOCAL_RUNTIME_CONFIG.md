# MCP_LOCAL_RUNTIME_CONFIG.md

*Status: internal-published (AI runtime config strategy)*

## Purpose

Document how BioETL treats MCP/runtime config files, including the distinction
between portable tracked workspace manifests and generated machine-local
runtime surfaces.

## Scope

This policy applies to:

- `.mcp.json`
- `scripts/ai/.mcp.json`
- `.zed/mcp.json`
- `.codex/settings.json`
- `.gemini/settings.json`
- `.codex/config.toml`
- `~/.codex/config.toml`
- `.codex/config-headless.toml`
- `.gemini/config.toml`
- `.devin/config.json`
- `.devin/mcp_config.json`
- `.devin/mcp_config.local.json`
- `.kimi-code/mcp.json`
- `.kimi-code/local.toml`

## Strategy

1. Apply tracked `.codex/config.toml` only in a trusted checkout. It owns
   portable project behavior such as agent concurrency and MUST NOT duplicate
   the generated MCP block in `~/.codex/config.toml`.
1. Treat `.mcp.json` as a retained exact-root workspace entrypoint, not as a
   machine-local runtime file. It, `scripts/ai/.mcp.json`, and `.zed/mcp.json`
   MUST use repo-relative paths.
1. Treat generated Codex/Gemini/editor runtime mirrors as local-only runtime
   surfaces when ignored by `.gitignore`; these may contain machine-local
   absolute paths when the consuming tool requires them.
1. Codex runtime npm/uv caches MUST use the native user cache directory
   (`$XDG_CACHE_HOME/bioetl-mcp` or `~/.cache/bioetl-mcp`) instead of a
   Windows-mounted workspace path. Tracked portable MCP projections continue
   to use repo-relative `.cache/**` paths.
1. Treat `.devin/config.json` as portable tracked Devin project settings and
   `.devin/mcp_config.json` as the portable tracked Devin MCP projection. The
   setup generator preserves only project keys supported by current Devin CLI
   and writes the sanctioned mixed-transport inventory to the dedicated MCP
   file. The local overlay preserves scoped stdio routes while applying
   daily-mode settings to optional servers.
1. Devin starts repository work in its cloned workspace and root environment
   commands from the repository root. Relative MCP filesystem, cache, memory,
   and wrapper arguments therefore use that repository root as their execution
   precondition. A runtime that changes this working-directory contract must
   materialize a local-only absolute projection instead of committing it.
1. Contributor docs MUST say whether a config is portable/repo-relative or
   depends on machine-local absolute paths. `.devin/config.json` and
   `.devin/mcp_config.json` are part of the portable tracked set;
   `.devin/mcp_config.local.json` is machine-local and gitignored.
1. Tracked `.agents/skills/*/SKILL.md` un-ignore in `.gitignore` is last-match
   SSOT. Do not add a later blanket `.agents/` ignore that would hide those
   skills.
1. Do not silently rewrite checked-in runtime paths during unrelated work.
1. If broader portability work is required, introduce an explicit
   template/strategy change instead of implying that all current runtime
   surfaces are portable.
1. Codex launchers MUST treat MCP synchronization as an idempotent ensure
   operation: verify persisted workspace projections and the managed
   `~/.codex/config.toml` block first, regenerate only missing or stale state,
   and reserve force-refresh for an explicit setup command.

## Materialization profiles (least privilege)

The tracked portable inventory remains the full sanctioned server set
(currently 21 servers). Local materialization may use a **profile** so high-
privilege servers are not always-on:

| Profile | Membership intent | Default for daily coding? |
| --- | --- | --- |
| `stable` | host/HTTP MCP only; Ref remains available, credentialed DeepWiki is excluded | **yes — daily default for local IDE projections** |
| `shared` | full sanctioned local set over shared HTTP plus opt-in remote HTTP MCP, including DeepWiki | explicit multi-client heavy plane (`--profile shared`) |
| `core` | `stable` + pinned Mermaid MCP | explicit legacy/local profile |
| `ops` | `core` + prometheus, grafana, github-actions | observability / dashboard work; `github-actions` is ops-only |
| `graph` | `ops` + neo4j-*, brave-search, mutmut, mcp-code-interpreter, docker | research / graph / mutation work |
| `full` | entire sanctioned inventory (same as tracked portable set) | only when explicitly needed |

Shared Streamable HTTP plane (multi-client, localhost): see
[`MCP_SHARED_RUNTIME.md`](./MCP_SHARED_RUNTIME.md). Tracked portable inventory
stays stdio; only **local** projections may emit `http://127.0.0.1:…/mcp` when
`--transport-mode shared` is set.

Live readiness is profile-aware. `stable` is the daily required set. `shared`
materializes the larger inventory but keeps Mermaid, Neo4j, monitoring, and
other heavy additions optional. `core` requires Mermaid, `ops` requires its
operations endpoints, `graph` requires Neo4j, and `full` requires its explicit
entire selection. Static CI validates the matrix without starting services:

```bash
python3 scripts/ai/codex/doctor.py static --no-write
python3 scripts/ai/codex/setup_mcp.py --check
python3 scripts/ai/codex/setup_mcp.py --check-local
```

`--check` owns the tracked full portable/Devin contract. `--check-local` owns
the generated profile-filtered surfaces: workspace Codex, VS Code, Cursor,
Qodo, optional Gemini, and (through `mcp-static`) the managed Codex user block.
When profile flags are omitted, `--check-local` reads the persisted
`.codex/mcp-profile.json`; if that file is absent, it uses the daily
`stable/shared` defaults. The check is read-only, starts no process, reports
bounded `missing`, `extra`, `transport_drift`, and `server_drift` names, and
ignores custom non-BioETL Gemini servers.

The legacy bounded transport probe never starts Docker Compose or a monitoring
stack and does not establish MCP protocol/tool readiness:

```bash
python scripts/ai/codex/doctor.py transport --profile stable \
  --timeout 1 --overall-timeout 10 --no-write
```

The live doctor is read-only by default. A persisted report requires an
explicit `.json` target under `reports/quality`; implicit writes to `logs/` are
not part of the runtime contract.

### Why Docker MCP multiplies containers

Stdio MCP transport starts **one process/container per client session**. Each
AI host (Grok, Cursor, WSL gateway, etc.) that loads docker-backed servers
(`brave-search`, `docker`, `grafana`, `prometheus`, …) can leave
orphans with random names (`elastic_*`, labels `docker-mcp=true`). On 32 GiB
hosts this thrash is a primary Docker Desktop failure mode — not a BioETL
compose bug.

### Generator

```bash
# Daily local state: ten selected entries, nine localhost endpoints + Ref.
python3 scripts/ai/codex/setup_mcp.py \
  --profile stable --transport-mode shared \
  --persist-local-profile --skip-codex-validation

# Full local enablement:
python3 scripts/ai/codex/setup_mcp.py \
  --profile full --transport-mode shared \
  --persist-local-profile --skip-codex-validation
```

Direct `setup_mcp.py` calls change the generated projection for that call only.
They change future launcher behavior only with `--persist-local-profile`.
Generation updates all local editor projections, including Gemini when that
surface is present, while preserving custom Gemini servers. Restart clients
that cache MCP configuration after materialization.

Canonical recovery and verification does not create or modify `.env`:

```bash
python3 scripts/ai/codex/setup_mcp.py \
  --profile stable --transport-mode shared \
  --persist-local-profile --skip-codex-validation
bash scripts/ai/codex/run-codex.sh mcp-setup

# Restart Codex/Cursor/VS Code/Qodo/Gemini, then verify.
bash scripts/ai/codex/run-codex.sh mcp-static
python3 scripts/ai/codex/setup_mcp.py --check
python3 scripts/ai/codex/setup_mcp.py --check-local
python scripts/ai/codex/doctor.py transport --profile stable \
  --timeout 1 --overall-timeout 10 --no-write
codex mcp list
```

One-shot host apply (profile + orphan cleanup + ensure-stable):

```powershell
.\scripts\ops\runtime\docker\apply-docker-stable-mcp.ps1 -Profile stable -WithNeo4j
# orphans only:
.\scripts\ops\runtime\docker\cleanup-mcp-orphans.ps1 -IncludeGatewayHint
```

Rules:

1. Tracked `.mcp.json` / `scripts/ai/.mcp.json` / `.zed/mcp.json` remain the
   portable **full** inventory SSOT unless a separate reviewed change says
   otherwise. They MUST stay loadable by the Muse strict project-file loader
   (fail-closed on the first required entry that mismatches): the generator
   applies the tracked-JSON compat projection (`_apply_tracked_json_compat`)
   and `--check` enforces it byte-exact.
2. Tracked `.devin/mcp_config.json` keeps the **full** sanctioned set (shared
   HTTP). `.devin/mcp_config.local.json` may disable optional servers for daily
   use. Profiles filter **local IDE** projections (`.cursor/mcp.json`,
   `.vscode/mcp.json`, `.qodo/mcp.json`, workspace `.codex/settings.json`, and
   optional `.gemini/settings.json`). Generator defaults are **`stable`**
   profile and **`shared`** transport.
3. Retired servers in `REMOVED_MCP_SERVER_NAMES` must never reappear.
4. Do not increase tech-debt budgets to paper over privilege sprawl.
5. Prefer **one** AI client with a heavy **stdio**/Docker MCP profile at a time;
   after reconnects run `cleanup-mcp-orphans.ps1` or `ensure-stable.ps1`.
   Alternatively run the **shared HTTP plane** (`start-shared.ps1` +
   `--profile shared --transport-mode shared`) so multiple clients share one
   process per migrated server — see `MCP_SHARED_RUNTIME.md`.

## Token Configuration

MCP tokens are local runtime inputs, not portable workspace configuration. The
tracked `.mcp.json` and `scripts/ai/.mcp.json` files must route token-bearing
servers through `scripts/ai/mcp/*wrapper*` scripts rather than embedding token
values.

The repo env loaders are:

- `scripts/ops/support/load_repo_env.sh`
- `scripts/ai/mcp/support/load_repo_env.ps1`

For Grok on Windows, the documented compatibility helper
`scripts/ai/mcp/export_mcp_env_from_dotenv.ps1` can export already configured
local values to process scope, or to user scope with `-UserScope`. It MUST NOT
write secret values into tracked MCP configuration.

They load local env files when present and normalize common aliases such as:

- GitHub one-way into `GITHUB_PERSONAL_ACCESS_TOKEN` when unset, in loader
  order: `GITHUB_TOKEN`, then `GH_TOKEN` (bash only), then
  `GITHUB_CDX_PERSONAL_ACCESS_TOKEN`, then `GITHUB_ANY_PERSONAL_ACCESS_TOKEN`
  (compat; do not add `ANY` to new `.env` files). Wrappers then try
  `gh auth token`. **Do not** copy PAT into `GITHUB_TOKEN` or write
  `GH_TOKEN` (#10298). `GITHUB_TOKEN_02` is not an alias (#10301).
- `BRAVE_SEARCH_API_KEY` / `BRAVE_API_KEY1` -> `BRAVE_API_KEY`
- `GRAFANA_TOKEN` / `GRAFANA_API_KEY` -> `GRAFANA_SERVICE_ACCOUNT_TOKEN`
- `DOCKERHUB_PAT` / `DOCKERHUB_TOKEN` -> `HUB_PAT_TOKEN`

### Grok GitHub overlay vs shared HTTP `:8820`

**XOR (#10299):** one live GitHub MCP endpoint per session — shared HTTP
`http://127.0.0.1:8820/mcp` **or** stdio `github-mcp-stdio.cmd`, never both.

- Daily canon is **B**: `start-shared` raises github `:8820`; Grok
  `[mcp_servers.github]` uses `url` (no `command`) when the plane is up.
- Stdio overlay is single-client **fallback** (`--transport-mode stdio` or
  plane down). Do not start github on `:8820` in parallel with stdio.
- Tracked `.mcp.json` / `scripts/ai/.mcp.json` stay portable **stdio wrappers**.
- Overlay must not call `Import-BioetlRepoEnv` into the parent `gh` process.
- Do not run `github-actions` HTTP on `:8831` in a daily Grok session
  (catalog `daily: false`); use `github` `actions_*` tools instead.

Token-bearing wrappers must also use:

- `scripts/ai/mcp/support/token_validation.sh`
- `scripts/ai/mcp/support/token_validation.ps1`

Validation must check missing required tokens, minimum length, and known token
prefixes where a provider has stable prefixes. Optional service tokens should
warn and continue with local-default or unauthenticated behavior.

CI/CD stance: default CI may run static config checks and stub/local MCP smoke
tests. CI must not require personal MCP tokens or third-party service tokens
unless a separate security design approves the secret source, scopes, rotation,
and fork/PR exposure model. Document any approved CI secret usage in
[`../../mcp-token-configuration.md`](../../mcp-token-configuration.md).

Remote MCP servers that support OAuth, including Ref Tools at
`https://api.ref.tools/mcp`, must use the key-free base URL in tracked and
generated config. Ref authentication may use interactive OAuth or the local
Codex-only `env_http_headers` mapping from `x-ref-api-key` to
`REF_TOOL_API_KEY`. Only the environment variable name may appear in generated
config; API key values must not be embedded in URLs or committed config.

## Native Codex route evidence

Use the installed native Codex resolver to inspect effective MCP configuration:

```powershell
python scripts/ai/codex/doctor.py routes --profile stable --json --no-write
```

If `codex` is absent from PATH, pass `--codex-executable` with the installed
native executable. This mode starts its own bounded diagnostic app-server,
performs `initialize` followed by `config/read` with `includeLayers`, and closes
only that process. It starts no thread, model turn, MCP backend, or tool call.
Initialization and configuration reads each have a 30-second observation limit;
timeouts cause no automatic retry, replay, or backend restart. Native startup may
create its ordinary service logs or cache. No target user data is changed.

The native effective configuration is the authority; the Python code does not
reimplement configuration precedence. `expected` is the selected project profile
inventory, while `effective`, `missing`, `additional`, and `disabled` describe
native resolution separately. Missing entries are diagnostic findings and are
never enabled automatically. Per-field origins and layer declarations explain
overrides. Adapter profile references remain distinct from the expected project
profile. Different server names, authorization references, or profiles are never
deduplicated by this diagnostic.

The stable selection fingerprint covers the resolver contract/native version,
physical workspace, expected project profile, server identity, projected
transport and scope settings, per-field origins, sanitized layer declarations,
and an optional authorization identity reference. It excludes secret values,
their hashes, native layer revision tokens, and current process identity.
Unknown arguments and opaque URL components are omitted and
`projection_complete=false` explicitly limits comparison. Private native inputs
can be compared in memory with `changed_routes` to detect credential rotation
without publishing a credential digest. A matching projected fingerprint alone
does not prove equal authorization or the correct backend.

`runtime_instance` is separate from selection: PID plus process creation time,
generation, and owner/gateway/backend observations may change after recovery.
These fields are evidence supplied by an observer, not verified by config/read.
Local backend acceptance requires owner registration and process/profile binding;
remote acceptance requires the expected service address, confirmed authorization,
and resource identity. Unavailable internal details remain unverified.

Gateway/backend identity and session tool readiness remain `NOT_TESTED`. This is
a diagnostic process using the ordinary configuration home, not evidence that an
existing or newly opened user session exposes these tools. A separate SDK call
or isolated Codex home does not replace ordinary-session acceptance. Full memory
graphs, raw native configuration, headers, credentials, and native revision
tokens must not be copied into diagnostic logs. Persist only the projected
report through an explicit `--output reports/quality/<name>.json` path.

## Protocol and control-call doctor

`doctor.py mcp` now uses the native effective-route capture. Without an explicit
control plan it starts no MCP adapters and reports `NOT_TESTED`. The former
fixed localhost catalog/socket diagnostic remains available as
`doctor.py transport`; its OK/FAIL/WARN transport results do not attest MCP
readiness. The legacy `--timeout` and `--overall-timeout` options belong to that
transport diagnostic. Native route resolution still has its own observation
limit; it must not be confused with backend initialization limits.

To opt into the already approved adapters, provide both `--probe-plan` and
`--start-approved-adapters`. A plan is a JSON object keyed by effective server
name. Each control declares a tool, arguments, and nonempty `contains_all`
expectations evaluated locally against actual result content. For example:

```json
{
  "filesystem": {
    "tool": "read_file",
    "arguments": {"path": "README.md"},
    "contains_all": ["BioETL"]
  }
}
```

Select arguments and expected sources for the actual route before executing;
this example is a schema illustration, not a claim that a server accepts a
relative file path. External controls must check library/document identity and
origin rather than freeze volatile result IDs. List-roots and token-count
controls cover only those functions, not ADR analysis or other analyzer tools.
Do not place secrets or full graph/dialogue contents into a control plan.

The diagnostic announces ordinary network, cache/log and approved-backend
startup effects before invoking a control. It installs nothing, registers no
workspace, does not enable missing routes, and never restarts a shared owner.
Only declared reading tools are eligible. Unbounded `read_graph`, memory writes
and Deja `remember` are deliberately ineligible; prefer a bounded reading query.
Explicit root `.env` references are read locally, never copied or changed.

The report distinguishes client startup, actual transport response, MCP
initialize, bounded/paginated tools/list, and semantic tool control. The native
route's startup timeout covers startup plus initialize; its tool timeout covers
catalog enumeration and separately the control call. Each phase reports elapsed
time and the limit source. If a native timeout/default cannot be established,
the control remains `NOT_TESTED`; no universal backend timeout is invented.
Responses and process stderr stay private and bounded. Neither response content,
raw server exception text nor credential hashes are persisted by the report.

Statuses are `PASS` for a verified phase, `FAIL` for a confirmed failed check,
`DISABLED` for native intentional disable, `NOT_TESTED` for missing evidence,
`DENIED_AS_EXPECTED` only for the exact structured reason
`WORKSPACE_POLICY_DENIED`, and `STALE` when the final native capture differs or
cannot be obtained. HTTP 401/403, a dead process, or a generic exception cannot
qualify as expected workspace isolation. An uncertain request outcome is an
additional flag and never triggers an automatic retry, replay, or restart.

Semantic control success does not prove local owner/process identity. Until the
independent backend/access binding is verified, backend identity and overall
readiness remain `NOT_TESTED` and the command exits nonzero. Obligatory disabled,
missing or untested routes are not silently waived. Diagnostic tools/list may
advertise memory writes even when all diagnostic calls are reads; the report
records this distinction without executing a write or claiming technical
read-only enforcement.

A final native config capture detects affected-route drift, including private
credential rotation in memory. It does not automatically replay old controls.
Instance recovery must be verified separately without treating a new PID or
generation as a policy change. This direct diagnostic is not a new ordinary
user session and cannot close ordinary-session acceptance. If the actual user
session cannot invoke a tool, retain `NOT_TESTED` for that acceptance item.

The launcher latency baseline now measures static MCP configuration ensure.
It does not label missing semantic controls as successful live readiness.
Installer/container launchers and unreviewed interpreter prefixes remain
`NOT_TESTED`; the direct diagnostic accepts an existing script adapter with a
supported interpreter prefix and never invokes npx/uv/pip installation paths.
An unsupported valid protocol version is a client capability gap, reported
`NOT_TESTED`, rather than evidence that the server is broken.

Probe plans must be repository-relative JSON files under
`reports/quality/mcp-controls/`. Absolute paths, parent traversal and resolved
symlink/junction escapes are rejected before any adapter starts. Reading a plan
is bounded to 1 MiB; arbitrary files are not accepted as control plans.

The stdio probe uses the native effective `cwd` for both relative script
resolution and process startup. An explicit task `BIOETL_AI_MEMORY_MODE` is
preserved over route/dotenv values without inheriting unrelated secrets.
Legacy `mcp_*_wrapper.sh` / `.ps1` fallbacks remain `NOT_TESTED` because an
existing wrapper file cannot prove a no-install backend; select a verified
existing adapter route instead. Policy denial on initialize/catalog is a phase
failure, not a successful negative tool control. `control_status` stays
`NOT_TESTED` until the actual control is attempted.

HTTP response headers, JSON and SSE bodies share the request's monotonic
deadline. Each body read receives the remaining socket timeout; a watchdog
interrupts only the diagnostic's owned socket at the deadline. Initialize's
notification shares its remaining budget. No request is replayed on timeout.

Stdio requests use nonblocking pipe writes; sending and waiting for the reply
share one monotonic request deadline. If the platform cannot support this, the
probe remains `NOT_TESTED`. An unresponsive owned adapter is terminated on
timeout; shared owners are never terminated or automatically restarted.

The JSONL reader uses interruptible nonblocking reads and a bounded join during
cleanup. An inherited stdout held by a backend cannot block diagnostic shutdown;
that backend is not terminated. `--no-write` controls report output; it does not
cancel the separately acknowledged adapter cache/log/startup effects.

Readiness controls honor native `enabled_tools` and `disabled_tools` before
starting a diagnostic session. An excluded control is reported with
`control_status: DISABLED` and overall readiness remains `NOT_TESTED`.
Raw and effective catalogue sizes remain separate; client filters cannot prove
server-side prohibition of writes. Explicit route env values are preserved.
Only explicitly declared environment references may inherit process values
when the repository environment has no value; unrelated credentials stay excluded.

HTTP name resolution, address attempts and TLS setup share the same absolute
request deadline. A timed-out connection worker cannot send a protocol request;
late DNS results are discarded before socket creation, and late owned sockets
are closed by their worker. A platform resolver already running may finish in
a daemon thread; its completion does not delay the diagnostic report.

Invalid or unreadable probe plans produce a structured `NOT_TESTED` result
before adapter startup. Credential-bearing HTTP controls are limited to
loopback hosts; remote credential-bearing controls require HTTPS.
