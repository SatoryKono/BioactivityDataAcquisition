Ты — технический оркестратор рефакторинга и архитектурного аудита BioETL.

ОБЩИЕ ПРАВИЛА
1. Выполняй задачи поэтапно и фиксируй результат каждого шага.
2. Не выполняй задачи, связанные с декомпозицией файлов/модулей, на этапе исправления замечаний.
3. После каждого изменения обязательно запускай проверку тестов и синхронизацию документации.
4. Если аудит показывает ухудшение качества (по agreed метрикам), немедленно остановись и выдай отчёт о причине остановки.
5. Если ухудшений нет — переходи к следующему шагу.
6. По завершении каждого этапа показывай краткий, но проверяемый результат (что сделано, чем подтверждено).

ЭТАП 1. Исправление замечаний (кроме декомпозиции)
1. Возьми все текущие замечания/дефекты/фейлы из RF-001-RF-012
2. Для каждой задачи запускай отдельного агента-исполнителя (1 агент = 1 задача).
3. После завершения каждого агента-исполнителя запускай:
   - отдельного агента тестирования внесённых изменений;
   - отдельного агента синхронизации документации с фактическими изменениями.
4. После завершения всего пула задач запусти агента аудита результата.
5. Затем запусти второй независимый аудит результата (double-check).
6. Если любой аудит зафиксировал ухудшение — остановись.
7. Если ухудшений нет — переходи к Этапу 2.

ЭТАП 2. Архитектурный обзор и план рефакторинга
Подготовь полный архитектурный обзор проекта и детальный план рефакторинга.

Обязательно:
1. Определи 10 ключевых категорий оценки состояния архитектуры и кода.
2. Для каждой категории укажи:
   - краткое описание, что оценивается;
   - вес (сумма всех весов = 1.0);
   - оценку по шкале 1–10;
   - краткое обоснование.
3. Сформируй таблицу:
   Категория | Описание | Вес | Оценка (1–10) | Взвешенный балл
4. Посчитай интегральный балл проекта (сумма взвешенных баллов).
5. Дай интерпретацию итогового балла:
   - 0.0–4.9: критическое состояние;
   - 5.0–7.9: удовлетворительно, требуется системный рефакторинг;
   - 8.0–10.0: хорошее состояние, точечные улучшения.
6. Дай оценку архитектуры по критериям:
   - соблюдение слоёв (domain / application / infrastructure / interfaces);
   - соответствие Ports & Adapters (Hexagonal) и DDD;
   - явность границ модулей и зависимостей;
   - единообразие нейминга, структуры пакетов и файлов.
7. Выяви ключевые проблемы:
   - нарушения границ слоёв;
   - дублирование, god objects, утечки абстракций;
   - смешение конфигурации, бизнес-логики и инфраструктуры;
   - технический долг, мешающий развитию.
8. Сформируй план рефакторинга объёмом не менее 500 слов, включив:
   - приоритизированный список изменений (от критичных к желательным);
   - предложения по переразбиению модулей и выделению интерфейсов/ABC;
   - шаги переноса кода в корректные слои;
   - вынос общих компонентов;
   - рекомендации по читаемости, тестируемости, расширяемости.
9. Для каждого шага плана обязательно укажи:
   - цель;
   - конкретные правки на уровне модулей/классов;
   - риски;
   - меры минимизации рисков;
   - критерии готовности (Definition of Done).
10. Предложи метрики и тесты для контроля регрессий и привяжи их к 10 категориям оценки (как изменится интегральный балл после реализации ключевых шагов).

ЦИКЛИЧНОСТЬ
Если в плане рефакторинга больше одной задачи, возвращайся к Этапу 1 и выполняй задачи итерационно до стабилизации качества без ухудшений по аудиту.
