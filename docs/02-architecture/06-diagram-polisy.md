Ты хочешь не советы, а норматив. Ладно. Ни эмоций, ни вдохновения. Только регламент.

Ниже — формализованная политика работы LLM с диаграммами проекта BioETL, согласованная с архитектурными правилами и структурой задач  .


---

POL-LLM-DIAGRAMS-001

Политика генерации и сопровождения диаграмм проекта BioETL


---

1. Назначение

Настоящая политика определяет:

правила генерации диаграмм LLM

допустимые типы диаграмм

требования к архитектурной корректности

требования к синхронизации с кодовой базой

критерии качества


Диаграммы рассматриваются как инженерные артефакты, а не иллюстрации.


---

2. Общие принципы

2.1. Диаграммы обязаны отражать архитектуру Ports & Adapters (Hexagonal) + DDD.

2.2. Диаграммы не должны противоречить структуре src/bioetl/.

2.3. Любая диаграмма должна иметь:

цель

уровень абстракции

версию

дату обновления


2.4. Диаграммы должны быть воспроизводимыми (source-controlled).
Формат: Mermaid или PlantUML. Растровые изображения без исходника запрещены.

2.5. LLM запрещено генерировать произвольные обозначения, не соответствующие naming conventions проекта .


---

3. Классификация диаграмм

LLM разрешено создавать только следующие типы:

3.1. Архитектурные

C4 Context

C4 Container

C4 Component


Назначение:

отображение слоёв (domain / application / infrastructure / interfaces)

отображение портов и адаптеров

направление зависимостей


Запрещено:

смешивать архитектурный уровень с бизнес-логикой пайплайна.



---

3.2. Диаграммы пайплайнов (DAG)

Назначение:

визуализация extract → transform → validate → export


Требования:

каждый узел — одна ответственность

обязательное отображение точки валидации

обязательное указание источника данных


Опора на задачи пайплайнов .


---

3.3. ER-диаграммы

Назначение:

визуализация доменной модели


Требования:

только сущности domain-слоя

указание кардинальности

указание nullability

версия схемы


Запрещено:

включать инфраструктурные таблицы

staging-структуры



---

3.4. Sequence-диаграммы

Используются для:

retry

rate limit

error handling

circuit breaker

fail-fast


Требования:

указание таймаутов

указание backoff

явное разделение клиента и порта



---

3.5. Data Lineage

Обязательны для production-пайплайнов.

Должны включать:

источник

трансформации

валидации

запись

контрольные суммы



---

4. Архитектурные ограничения

LLM обязано соблюдать:

4.1. Domain не зависит от Infrastructure.

4.2. Application взаимодействует с Infrastructure только через Protocol/ABC.

4.3. Сетевой код не отображается в domain-диаграммах.

4.4. Все классы должны иметь корректные суффиксы (*Client, *Impl, *Factory и т.д.) согласно правилам .

4.5. Запрещены циклические зависимости.


---

5. Визуальные стандарты

5.1. Цветовая схема фиксирована:

Слой	Цвет

domain	blue
application	green
infrastructure	orange
interfaces	purple


5.2. Обозначения:

Protocol / ABC — пунктир

Impl — сплошная рамка

External API — двойная рамка

Pandera validation — отдельный маркер


5.3. Использование произвольных цветов запрещено.


---

6. Синхронизация с кодом

6.1. Диаграммы должны соответствовать реальным модулям.

6.2. При изменении:

структуры слоёв

сигнатур Protocol

схем Pandera

пайплайнов


LLM обязано обновить соответствующие диаграммы.

6.3. Изменение диаграммы без изменения кода допустимо только при исправлении несоответствия.


---

7. CI-контроль

LLM должно проектировать диаграммы так, чтобы:

они генерировались из текстового описания

diff диаграмм был отслеживаем

изменения проходили code review


Любая диаграмма, не соответствующая структуре проекта, считается дефектной.


---

8. Чеклист качества диаграммы

Перед выдачей диаграммы LLM обязано проверить:

корректность слоёв

отсутствие прямых зависимостей domain → infrastructure

соответствие naming conventions

указание версии

указание уровня абстракции

отсутствие избыточных деталей



---

9. Запрещено

LLM запрещается:

генерировать декоративные схемы без архитектурной ценности

использовать нестандартизированные обозначения

добавлять сущности, отсутствующие в коде

смешивать уровни абстракции

скрывать зависимости



---

10. Ответственность

Любая диаграмма, сгенерированная LLM:

считается частью архитектурной документации

подлежит ревью

должна быть детерминированной

должна быть воспроизводимой



---

Итог

Диаграммы — это не иллюстрации для презентации.
Это проверяемые архитектурные артефакты.

LLM не “рисует”.
LLM моделирует систему в формализованном виде, соответствующем архитектуре проекта.
