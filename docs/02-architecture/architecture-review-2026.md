# Архитектурный обзор проекта BioETL (2026)

**Дата проведения:** 4 февраля 2026 г.  
**Версия проекта:** 5.9.0  
**Статус:** Завершен

---

## Аннотация

Проведен комплексный архитектурный обзор проекта **BioETL** — фреймворка для сбора и обработки данных о биологической активности из публичных репозиториев (ChEMBL, PubChem, UniProt, PubMed и др.). 

Проект демонстрирует высокий уровень архитектурной дисциплины с применением **Hexagonal Architecture** (Порты и Адаптеры), **Domain-Driven Design** и **Medallion Architecture** для организации данных. Документировано **32 архитектурных решения (ADR)**, покрытие тестами превышает **80%**, строго контролируются границы слоев.

## 1. Архитектурный стиль и паттерны

### 1.1 Гексагональная архитектура (Hexagonal Architecture)

Проект реализует классическую гексагональную архитектуру с четким разделением:

```
┌─────────────────────────────────────────────────────────────┐
│                  ИНТЕРФЕЙСЫ (CLI)                           │
│              Внешние точки входа                            │
├─────────────────────────────────────────────────────────────┤
│                  КОМПОЗИЦИЯ (DI)                            │
│         bootstrap_pipeline() → Фабрики                      │
├─────────────────────────────────────────────────────────────┤
│                  ПРИЛОЖЕНИЕ                                 │
│         PipelineRunner → Executor → BaseTransformer         │
├─────────────────────────────────────────────────────────────┤
│                  ДОМЕН (DDD)                                │
│  Порты │ Агрегаты │ Объекты-значения │ Сущности │ Схемы   │
├─────────────────────────────────────────────────────────────┤
│                  ИНФРАСТРУКТУРА                             │
│  Адаптеры │ Хранилище │ HTTP-клиент │ Наблюдаемость        │
└─────────────────────────────────────────────────────────────┘
```

**Ключевые принципы:**
- **Инверсия зависимостей:** Все внешние зависимости абстрагированы через интерфейсы `Protocol` в `domain/ports/`
- **Композиционный корень:** Централизован в `composition/bootstrap.py` и `composition/factories/`
- **Изоляция слоев:** Матрица импортов контролируется через `import-linter` (нарушения блокируют PR)
- **Чистый домен:** Бизнес-логика полностью независима от инфраструктуры

### 1.2 Medallion Architecture (Bronze → Silver → Gold)

Трехуровневая архитектура данных с четкими границами ответственности:

| Слой | Формат | Валидация | Назначение |
|------|--------|-----------|-----------|
| **Bronze** | JSONL + zstd | Отсутствует | Сырые данные из API (неизменяемый архив) |
| **Silver** | Delta Lake | Pandera (мягкая) | Нормализованные данные (можно пересчитать из Bronze) |
| **Gold** | Delta/Parquet | Pandera (строгая) | Бизнес-готовые агрегаты (оптимизированы для аналитики) |

**Поток данных:**
```
Внешний API → Bronze (архив) → Silver (нормализация) → Gold (аналитика)
                                    ↓
                               Quarantine (DQ failures)
```

## 2. Структура слоев

### 2.1 Слой домена (`src/bioetl/domain/`)

**Назначение:** Чистая бизнес-логика, независимая от инфраструктуры.

**Компоненты:**

| Компонент | Содержание | Назначение |
|-----------|-----------|-----------|
| **ports/** | 12 интерфейсов Protocol | Контракты для инверсии зависимостей |
| **aggregates/** | DDD-агрегаты | Защита инвариантов (Batch, PipelineRun, QuarantineEntry) |
| **entities/** | Доменные модели | Модели по провайдерам (ChEMBL, PubChem, UniProt и т.д.) |
| **value_objects/** | Неизменяемые примитивы | RunID, EntityType, FilterID |
| **schemas/** | Pydantic/Pandera модели | Валидация данных на всех слоях |
| **filtering/** | Динамические фильтры | Экстернализация DQ-правил |

**Ключевые порты (12 интерфейсов):**
1. `DataSourcePort` — абстракция REST API с поддержкой пагинации
2. `FilterableDataSourcePort` — расширение с серверной фильтрацией
3. `StoragePort` — мультислойное хранилище (Bronze/Silver/Gold)
4. `LockPort` — механизм распределенных блокировок
5. `CheckpointPort` — управление состоянием конвейера
6. `QuarantinePort` — очередь отказов для DQ-проблем
7. `MetricsPort`, `TracingPort`, `LoggerPort`, `DQMonitorPort` — наблюдаемость
8. `GoldValidatorPort` — валидация схем для Gold-слоя
9. `InputFilterPort` — загрузка динамических фильтров

**Архитектурное правило:** Все импорты из `domain/ports/` должны идти через фасад `__init__.py`.

### 2.2 Слой приложения (`src/bioetl/application/`)

**Назначение:** Оркестрация use case (конвейеры) с использованием доменной логики.

**Компоненты:**

| Компонент | Ответственность |
|-----------|-----------------|
| **pipelines/** | ETL-оркестрация для каждого провайдера |
| **core/base.py** | Управление жизненным циклом: блокировка → чекпоинт → извлечение → трансформация → запись → разблокировка |
| **core/base_transformer.py** | Шаблонный метод для преобразований Bronze → Silver |
| **core/runner.py** | Обертка вокруг BasePipeline с обработкой ошибок и метриками |
| **core/executor.py** | Координация потока данных (extract → transform → load) |
| **services/** | Сервисы приложения (lifecycle, vacuum, cleanup) |
| **composite/** | Многоисточниковый конвейер обогащения (seed → enrich → merge) |

**Жизненный цикл конвейера:**
1. Захват блокировки (предотвращение параллельных запусков)
2. Загрузка чекпоинта (точка возобновления)
3. Извлечение данных из API источника
4. Трансформация Bronze → Silver
5. Валидация и трансформация Silver → Gold
6. Обновление чекпоинта
7. Освобождение блокировки

**Трансформеры (12+ реализаций):**
- **ChEMBL:** Activity, Assay, Molecule, Target, Publication и др.
- **PubChem:** Compound
- **UniProt:** Protein
- **PubMed, CrossRef, OpenAlex, Semantic Scholar:** Варианты публикаций

### 2.3 Слой инфраструктуры (`src/bioetl/infrastructure/`)

**Назначение:** Конкретные реализации портов домена.

**Компоненты:**

| Компонент | Ответственность |
|-----------|-----------------|
| **adapters/** | 7 адаптеров для провайдеров (ChEMBL, PubChem, UniProt и др.) |
| **http_client/** | Единый `UnifiedHTTPClient` с rate limiting, circuit breaker, retries |
| **storage/** | Адаптеры Delta Lake (Silver/Gold) и JSONL+zstd (Bronze) |
| **locking/** | In-memory `MemoryLock` (только локальное развертывание) |
| **checkpoint/** | Управление состоянием на основе локальных файлов |
| **quarantine/** | Реализация очереди отказов (dead-letter queue) |
| **observability/** | Метрики Prometheus, структурированное логирование (structlog), OpenTelemetry |
| **config.py** | Загрузка конфигурации на основе Pydantic из YAML |

**Архитектура HTTP-адаптеров:**
```
DataSourcePort (Protocol)
├── BaseHttpAdapter (async, UnifiedHTTPClient)
│   ├── ChemblAdapter
│   ├── UniProtAdapter
│   ├── PubMedAdapter
│   ├── CrossRefAdapter
│   ├── OpenAlexAdapter
│   └── SemanticScholarAdapter
└── BaseSyncAdapter (ThreadPoolExecutor)
    └── PubChemAdapter (pubchempy + legacy support)
```

**Rate Limiting & Устойчивость:**

| Провайдер | Rate Limit | Circuit Breaker | Стратегия повторов |
|-----------|------------|-----------------|-------------------|
| ChEMBL | Нет | Да | экспоненциальная задержка |
| PubChem | 5 req/sec | Да | экспоненциальная задержка |
| UniProt | 100 req/sec | Да | экспоненциальная задержка |
| PubMed | 3 req/sec | Да | экспоненциальная задержка |
| CrossRef | Polite pool | Да | экспоненциальная задержка |
| OpenAlex | 10 req/sec | Да | экспоненциальная задержка |
| Semantic Scholar | 100 req/5min | Да | экспоненциальная задержка |

### 2.4 Слой композиции (`src/bioetl/composition/`)

**Назначение:** Dependency Injection и сборка объектов (Composition Root).

**Компоненты:**

| Компонент | Ответственность |
|-----------|-----------------|
| **bootstrap.py** | Главная точка входа для инициализации конвейеров |
| **GenericPipelineFactory** | Декларативная фабрика конвейеров с DI трансформеров |
| **HttpClientFactory** | Создание настроенных экземпляров UnifiedHTTPClient |
| **StorageFactory** | Сборка мультислойного адаптера хранилища |
| **DataSourceFactory** | Создание источников данных для конкретных провайдеров |
| **ProviderRegistry** | Центральный реестр 7 поддерживаемых провайдеров |
| **PipelineRegistry** | Динамическое обнаружение доступных конвейеров |

**Ключевой паттерн:** Фабрики позволяют декларативную регистрацию конвейеров без шаблонного кода.

### 2.5 Слой интерфейсов (`src/bioetl/interfaces/`)

**Назначение:** Точки входа для внешнего взаимодействия.

**Компоненты:**

| Компонент | Тип | Команды |
|-----------|-----|---------|
| **cli/** | Click-интерфейс | `run`, `run_all`, `export`, `quarantine`, `health` |
| **orchestration/** | Обработчики сигналов ОС | Graceful shutdown на SIGTERM/SIGINT |

**Примеры использования CLI:**
```bash
bioetl run --pipeline chembl_activity --limit 100
bioetl run_all --provider chembl
bioetl export --table gold_chembl_activity --format parquet
bioetl health --provider chembl
```

## 3. Ключевые архитектурные решения (ADR)

Проект документирует архитектурные решения через **32 Architecture Decision Records**. Ключевые решения:

| ADR # | Решение | Обоснование |
|-------|---------|------------|
| **ADR-001** | Delta Lake vs Parquet | ACID-транзакции, эволюция схем, time travel для Silver/Gold |
| **ADR-002** | Medallion Architecture | Слои качества данных: Bronze (сырые) → Silver (нормализованные) → Gold (кураторские) |
| **ADR-003** | In-Memory Locking | Проще распределенных блокировок; обосновано локальным развертыванием |
| **ADR-004** | Pydantic vs Dataclasses | Pydantic для валидации; кастомные TypeAdapters для пользовательских типов |
| **ADR-005** | Композиция как отдельный слой | Единая ответственность: композиция знает обо всех слоях |
| **ADR-007** | Реализация Circuit Breaker | Предотвращение каскадных сбоев API; экспоненциальные задержки |
| **ADR-010** | Локальное развертывание | Автономность; не требуется внешних сервисов (S3, Kubernetes) |
| **ADR-014** | Детерминированные записи | Запрет `random` в слое хранения для воспроизводимой обработки данных |
| **ADR-017** | Архитектура наблюдаемости | Метрики, трассировка, логирование как приоритетные концепции (порты) |
| **ADR-018** | Строгая валидация Gold | Схемы Pandera обеспечивают качество данных на аналитическом слое |
| **ADR-021** | DDD-агрегаты | Batch, PipelineRun, QuarantineEntry с защищенными инвариантами |
| **ADR-026** | Паттерн композитного конвейера | Обогащение из нескольких источников: seed → enrich (fan-out) → merge |
| **ADR-031** | Формализация стратегий загрузки | Полное сканирование vs инкрементальная загрузка с чекпоинтами |
| **ADR-032** | Единый HTTP-клиент | Стандартизированный rate limiting, circuit breaker, телеметрия |

## 5. Стратегия тестирования

### 5.1 Пирамида тестирования

```
                    ▲
                   ╱ ╲
                  ╱   ╲  E2E (tests/e2e/)
                 ╱─────╲ ~20 тестов, 5мин
                ╱       ╲
               ╱─────────╲ Integration (tests/integration/)
              ╱           ╲ ~150 тестов, VCR
             ╱─────────────╲
            ╱               ╲ Unit (tests/unit/)
           ╱─────────────────╲ ~500 тестов, <1мин
          ╱___________________╲
```

### 5.2 Категории тестов

| Категория | Фреймворк | Маркеры | Покрытие | Время выполнения |
|-----------|-----------|---------|----------|------------------|
| **Unit** | pytest | `@pytest.mark.unit` | Доменная логика, трансформеры | <1 сек/тест |
| **Integration** | pytest+VCR | `@pytest.mark.integration` | Адаптеры, хранилище, HTTP | 1-5 сек/тест |
| **E2E** | pytest | `@pytest.mark.e2e` | Полный цикл конвейера | 10+ сек/тест |
| **Architecture** | import-linter | `@pytest.mark.architecture` | Границы слоев, правила | <1 сек |
| **Security** | pytest | `@pytest.mark.security` | Сканирование секретов, PII | <1 сек |

### 5.3 Метрики качества

| Метрика | Целевое значение | Применение | Инструмент |
|---------|-----------------|-----------|-----------|
| **Покрытие строк** | >80% (общее), >90% (домен) | CI падает при нарушении | pytest-cov |
| **Покрытие ветвлений** | >80% | CI падает при нарушении | pytest-cov |
| **Проверка типов** | Строгий режим | Блокировка PR | mypy |
| **Цикломатическая сложность** | A (avg ≤5), B (max ≤10) | Предупреждение CI | xenon |
| **Нарушения архитектуры** | 0 | Блокировка PR | import-linter |
| **Проблемы безопасности** | HIGH=0 | Блокировка PR | bandit |

## 6. Организация кода и модульность

### 6.1 Структура директорий

```
src/bioetl/
├── domain/                          # Чистая бизнес-логика
│   ├── ports/                       # Интерфейсы Protocol (12 контрактов)

│   ├── entities/                    # Доменные модели по провайдерам
│   ├── value_objects/               # Неизменяемые примитивы

│
├── application/                     # Use cases и оркестрация
│   ├── pipelines/                   # ETL-конвейеры по провайдерам
│   ├── core/                        # Движок выполнения
│   ├── composite/                   # Обогащение из нескольких источников
│   └── services/                    # Сервисы приложения

│   ├── adapters/                    # Адаптеры API провайдеров (7)
│   ├── storage/                     # Записывающие модули Bronze/Silver/Gold
│   ├── http_client/                 # UnifiedHTTPClient + устойчивость
│   ├── observability/               # Prometheus, логирование, трассировка
│   └── config.py                    # Загрузка конфигурации

├── composition/                     # Dependency Injection
│   ├── bootstrap.py                 # Главная точка входа

│   └── registry.py                  # Обнаружение конвейеров
│
└── interfaces/                      # Внешние адаптеры
    ├── cli/                         # CLI на основе Click

tests/
├── unit/                            # Изолированная бизнес-логика
├── integration/                     # Тесты адаптеров и хранилища
├── e2e/                             # Полные циклы конвейеров
├── architecture/                    # Изоляция слоев, правила

```

### 6.2 Принципы модульности

| Принцип | Реализация | Контроль |
|---------|------------|----------|
| **Единая ответственность** | Каждый модуль имеет одну причину для изменения | Code reviews |
| **Инверсия зависимостей** | Зависимость от абстракций (Ports), а не конкретных реализаций | import-linter |
| **DRY** | Общая логика извлечена в базовые классы | Обнаружение дубликатов (pylint) |
| **Композиция вместо наследования** | Предпочтение mixin-композиции для сквозных задач | Архитектурные ревью |
| **Неизменяемость** | Объекты-значения, агрегаты заморожены после создания | Type hints, frozen dataclasses |
| **Четкие границы** | Импорты слоев строго контролируются | import-linter (блокировка PR) |

## 7. Сильные стороны архитектуры

✅ **Отличное разделение ответственности** — Доменный слой полностью изолирован от инфраструктуры  
✅ **Комплексная стратегия тестирования** — Многоуровневое тестирование с VCR.py для записи HTTP  
✅ **Строгая типобезопасность** — mypy в строгом режиме на всех слоях  
✅ **Хорошо документированные решения** — 32 ADR с объяснением архитектурных выборов  
✅ **Контроль архитектурных правил** — Границы слоев через import-linter  
✅ **Детерминированное выполнение** — Запрет случайных функций в слое хранения  
✅ **Локальное развертывание** — Нет зависимостей от внешних сервисов  
✅ **Отличная наблюдаемость** — Метрики, логирование, трассировка как первоклассные порты  
✅ **Расширяемость провайдеров** — Четкие паттерны для добавления новых источников данных

### 8.3 Долгосрочные стратегические вопросы
