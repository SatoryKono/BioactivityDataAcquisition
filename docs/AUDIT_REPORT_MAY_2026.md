## 2. Архитектурный обзор

### Сильные стороны
1.  **Строгий Hexagonal Layering:** Соблюдение границ слоев (`domain` -> `application` -> `infrastructure`) принудительно контролируется CI-тестами (`tests/architecture/test_layer_dependencies.py`).
2.  **Composition Root:** Внедрение зависимостей централизовано в `src/bioetl/composition`, что исключает скрытые связи.
3.  **Medallion Architecture:** Четкое разделение данных на Bronze (Raw/JSONL), Silver (Clean/Delta) и Gold (Aggregated). Реализована защита от Schema Drift.
4.  **Детерминизм:** Внедрен `PipelineContext.started_at` как единый источник времени (Single Source of Time), что решило проблемы с воспроизводимостью тестов и данных.

### Выявленные проблемы и точки роста
1.  **Производительность сериализации (Performance):** В критических путях записи (`BronzeWriter`, `DeltaWriter`) используется стандартная библиотека `json`. Отсутствие `orjson` (хотя он заявлен в зависимостях `performance`) создает лишние накладные расходы на CPU при обработке больших батчей.
2.  **Полнота Observability:** Инфраструктура для Tracing (`TracingPort`) заложена, но не внедрена повсеместно в `PipelineExecutor`. Это затрудняет отладку распределенных проблем (latency breakdown).
3.  **Governance автоматизация:** Правила, описанные в `RULES.md` (например, запрет `random`), проверяются тестами, но не все аспекты (например, именование метрик) автоматизированы.

## 3. Детальный план рефакторинга (Phase 5: Optimization & Hardening)

План направлен на устранение выявленных точек роста без нарушения стабильности системы.

### Приоритет 1: Производительность (High)
**Цель:** Снизить CPU overhead при сериализации данных на 30-50%.

*   **Шаг 1.1: Миграция на `orjson` в BronzeWriter**
    *   **Файл:** `src/bioetl/infrastructure/storage/bronze_writer.py`
    *   **Изменение:** Заменить `json.dumps` на `orjson.dumps`.
    *   **Детали:** Использовать опцию `orjson.OPT_SORT_KEYS` для сохранения детерминизма (канонический JSON). Учесть, что `orjson` возвращает `bytes`, что исключает лишний этап кодирования в UTF-8.
    *   **Риски:** `orjson` не поддерживает некоторые кастомные типы по умолчанию (например, `decimal`). Требуется `default` хендлер, если такие типы есть в сырых данных.
    *   **Критерии:** Тесты проходят, бенчмарк показывает ускорение записи.

*   **Шаг 1.2: Миграция на `orjson` в DeltaWriter (Silver)**
    *   **Файл:** `src/bioetl/infrastructure/storage/delta_writer.py`
    *   **Изменение:** Использовать `orjson` для сериализации сложных структур перед конвертацией в Arrow (если применимо) или для логирования.

### Приоритет 2: Наблюдаемость (Medium)
**Цель:** Получить детальную разбивку времени выполнения этапов (Fetch vs Transform vs Write).

*   **Шаг 2.1: Внедрение Tracing в PipelineExecutor**
    *   **Файл:** `src/bioetl/application/core/executor.py` (или `runner.py`, где происходит вызов этапов).
    *   **Изменение:** Обернуть вызовы `fetch`, `transform`, `write` в spans через инжектированный `tracer`.
    *   **Детали:** Добавить атрибуты к спанам: `batch_id`, `record_count`, `retry_attempt`.
    *   **Критерии:** В логах/экспортере видны вложенные спаны выполнения батча.

### Приоритет 3: Укрепление контрактов (Medium)
**Цель:** Гарантировать отсутствие регрессий в детерминизме.

*   **Шаг 3.1: Расширение архитектурных тестов**
    *   **Файл:** `tests/architecture/test_performance.py` (новый).
    *   **Изменение:** Добавить тест, запрещающий импорт `json` в модулях хранения (`infrastructure/storage`), требуя использование `orjson`.
    *   **Критерии:** CI падает при попытке использовать медленный `json` в hot paths.

## 4. Метрики успеха

После реализации плана ожидается:
1.  **Интегральный балл:** Рост с **9.20** до **9.50** (за счет категорий "Производительность" и "Наблюдаемость").
2.  **Latency:** Снижение времени обработки батча (process time) на ~10-15% за счет ускорения сериализации.
3.  **Observability:** Наличие полной трассировки выполнения батча (Trace coverage > 90% logic).
