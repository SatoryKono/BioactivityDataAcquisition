## Часть 2. Оценка по 10 категориям

Для каждой категории:
1. Укажи конкретные нарушения со ссылками на файлы/строки
2. Приведи примеры кода (если релевантно)
3. Оцени по шкале с чёткими критериями

### Категории и критерии оценки

#### 1. Соблюдение слоистой архитектуры (вес: 15%)
**Что проверяется**: §1.1 RULES.md — domain не импортирует infrastructure/application; application не импортирует interfaces.

| Балл | Критерий |
|------|----------|
| 9-10 | 0 нарушений границ слоёв |
| 7-8 | 1-3 нарушения, все в некритичных модулях |
| 5-6 | 4-10 нарушений или 1-2 в критичных модулях |
| 3-4 | >10 нарушений, границы размыты |
| 1-2 | Архитектура слоёв не прослеживается |

**Проверка**:
```bash
# Domain не должен импортировать infrastructure
grep -r "from bioetl.infrastructure" src/bioetl/domain/
grep -r "from bioetl.application" src/bioetl/domain/
```

#### 2. Контракты и Ports (вес: 12%)
**Что проверяется**: §1.1.1 — использование Protocol в domain/ports.py; реализации в infrastructure.

| Балл | Критерий |
|------|----------|
| 9-10 | Все внешние зависимости абстрагированы через Protocol |
| 7-8 | >80% зависимостей через Protocol, остальные с TODO |
| 5-6 | 50-80% через Protocol |
| 3-4 | <50%, прямые вызовы библиотек в application |
| 1-2 | Protocol не используются |

#### 3. Medallion Architecture (вес: 12%)
**Что проверяется**: §2.1 — Bronze (JSONL+zstd), Silver (Delta Lake, merge), Gold (strict validation).

| Балл | Критерий |
|------|----------|
| 9-10 | Полное соответствие: форматы, пути, retention, VACUUM |
| 7-8 | Структура соблюдена, minor отклонения в путях/retention |
| 5-6 | 2 из 3 слоёв реализованы корректно |
| 3-4 | Только Bronze реализован, Silver/Gold отсутствуют или raw Parquet |
| 1-2 | Medallion не реализован |

#### 4. Обработка ошибок и Circuit Breaker (вес: 10%)
**Что проверяется**: §3.1 — классификация ошибок (Critical/Recoverable/DQ), §3.1.4 — Circuit Breaker.

| Балл | Критерий |
|------|----------|
| 9-10 | Все 3 типа ошибок обрабатываются, CB реализован с метриками |
| 7-8 | Классификация есть, CB реализован без метрик |
| 5-6 | Retry есть, CB отсутствует |
| 3-4 | Только базовый try/except |
| 1-2 | Ошибки не обрабатываются или глушатся |

#### 5. Блокировки и конкурентность (вес: 10%)
**Что проверяется**: §3.3 — Redis SETNX, TTL 60s, Heartbeat 20s, Fencing Token, Safety Guard.

| Балл | Критерий |
|------|----------|
| 9-10 | Полная реализация: lock + heartbeat + fencing + safety guard |
| 7-8 | Lock + heartbeat, без safety guard |
| 5-6 | Только базовый lock без heartbeat |
| 3-4 | Lock реализован некорректно (race conditions) |
| 1-2 | Блокировки отсутствуют |

#### 6. Валидация и DQ (вес: 10%)
**Что проверяется**: §2.6 — Pandera schemas, Quarantine, thresholds (5%/20%), §2.8.1 — Content Hash.

| Балл | Критерий |
|------|----------|
| 9-10 | Pandera для всех сущностей, Quarantine, Content Hash, DQ metrics |
| 7-8 | Pandera есть, Quarantine реализован, без метрик |
| 5-6 | Базовая валидация, без Quarantine |
| 3-4 | Частичная валидация, sentinel values присутствуют |
| 1-2 | Валидация отсутствует |

#### 7. Логирование и наблюдаемость (вес: 8%)
**Что проверяется**: §3.2 — UnifiedLogger, JSON-логи, run_id во всех логах, §3.4 — Prometheus metrics.

| Балл | Критерий |
|------|----------|
| 9-10 | UnifiedLogger везде, run_id в логах, Prometheus metrics |
| 7-8 | UnifiedLogger везде, run_id есть, без metrics |
| 5-6 | Смешанное логирование (UnifiedLogger + logging) |
| 3-4 | print() в коде, логи не структурированы |
| 1-2 | Логирование отсутствует или хаотичное |

#### 8. Тестирование (вес: 8%)
**Что проверяется**: §4.2 — coverage ≥85%, VCR.py для integration, golden tests.

| Балл | Критерий |
|------|----------|
| 9-10 | Coverage ≥85%, VCR cassettes, golden tests, contract tests |
| 7-8 | Coverage 70-84%, VCR есть, golden частично |
| 5-6 | Coverage 50-69%, unit tests есть |
| 3-4 | Coverage <50%, тесты фрагментарны |
| 1-2 | Тесты отсутствуют или не запускаются |

#### 9. Безопасность и секреты (вес: 8%)
**Что проверяется**: §5.2 — секреты через env, §5.4 — PII hashing с salt.

| Балл | Критерий |
|------|----------|
| 9-10 | Секреты только через env, PII salted, .env не в git |
| 7-8 | Секреты через env, без salt rotation |
| 5-6 | Секреты через env, но есть утечки в логах |
| 3-4 | Частичный hardcode или секреты в конфигах |
| 1-2 | Hardcoded secrets в коде |

#### 10. Документация и сопровождаемость (вес: 7%)
**Что проверяется**: §6, §7 — Data Contracts, ADR, docstrings, CHANGELOG.

| Балл | Критерий |
|------|----------|
| 9-10 | Gold contracts, ADR для решений, docstrings везде, CHANGELOG актуален |
| 7-8 | Contracts частично, ADR есть, docstrings >70% |
| 5-6 | README актуален, docstrings <70% |
| 3-4 | Документация устарела |
| 1-2 | Документация отсутствует |

### 3.2. Интерпретация общего балла
- **8.0-10.0**: Production-ready, minor improvements
- **6.0-7.9**: Требуется рефакторинг, но система работоспособна
- **4.0-5.9**: Значительный технический долг, риски при масштабировании
- **<4.0**: Критическое состояние, требуется существенная переработка

### 3.3. План рефакторинга

Для каждого пункта плана указать:
```
### [P1/P2/P3] Название изменения

**Категория**: какую категорию улучшает
**Текущий балл → Целевой балл**: X → Y
**Влияние на общий балл**: +Z

**Проблема**: конкретное описание со ссылками на код
**Решение**: что именно изменить
**Файлы**: список затрагиваемых модулей
**Риски**: что может сломаться
**Критерий готовности**: как проверить успех
**Трудозатраты**: S/M/L (часы/дни/недели)
```

Приоритеты:
- **P1**: Блокеры production, нарушения MUST требований
- **P2**: Нарушения SHOULD, значительный tech debt
- **P3**: Улучшения, MAY требования

### 3.4. Roadmap

Сгруппируй изменения в фазы:
- **Фаза 1** (неделя 1-2): P1 изменения, стабилизация
- **Фаза 2** (неделя 3-4): P2 изменения, улучшение архитектуры
- **Фаза 3** (неделя 5+): P3 изменения, оптимизация

Для каждой фазы укажи ожидаемое изменение общего балла.
