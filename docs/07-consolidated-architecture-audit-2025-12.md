## Часть 2. Верификация Утверждений

### 2.1. ❌ ЛОЖНЫЕ УТВЕРЖДЕНИЯ (Выявлены при верификации)

| Утверждение | Планы | Верификация | Почему ложно |
|-------------|-------|-------------|--------------|
| **"Требуется Redis для распределённых блокировок"** | 2, 3 | `CLAUDE.md` §5 | **Проект явно использует локальные блокировки по дизайну**: "Для локального развертывания используется in-memory блокировка. Распределённые блокировки не требуются, так как пайплайны запускаются локально." |
| **"DQ метрики не экспортируются"** | 2, 3 | `postrun_service.py:122-163` | **УЖЕ РЕАЛИЗОВАНО**: `_check_hard_threshold()`, `_check_soft_threshold()`. Эмитятся метрики `dq_soft_threshold_exceeded` (counter), `dq_check_duration_ms` (histogram). |
| **"MemoryMonitor возвращает захардкоженные значения/нули"** | 1 | `memory_monitor.py:170-180` | **Graceful degradation, НЕ баг**: Возвращает консервативные оценки (50% использования памяти), не нули. Это безопасный fallback при недоступности psutil. |
| **"Email в config требует хэширования как PII"** | 1, 3 | `CLAUDE.md` §2.3 | **НЕ PII**: `default_email` — технический идентификатор для NCBI API, не персональные данные. NCBI требует email для идентификации инструмента. |
| **"TTL по умолчанию 3600s несоответствует требованиям"** | 1 | `domain/config.py:291-293` | **Неточно**: `effective_lock_ttl = lock_ttl or heartbeat_interval * 3` = 90s по умолчанию. `LockContext.is_valid(ttl_seconds=3600)` — проверка backward-compat, не фактический TTL. |
| **"protocols.py пустой/нулевое покрытие"** | 3 | `application/core/protocols.py` | **НЕ пустой**: Содержит 4 Protocol: `TransformCallback`, `GoldFilterCallback`, `GoldTransformCallback`, `TransformerPort`. |
| **"Нет DQ thresholds в мониторинге"** | 2, 3 | `domain/config.py:28-40` | **УЖЕ РЕАЛИЗОВАНО**: `DQConfig` с `soft_fail_threshold=0.05`, `hard_fail_threshold=0.20`, плюс `DataQualityThresholdError` в exceptions. |

### 2.2. ⚠️ ЧАСТИЧНО ВЕРНЫЕ УТВЕРЖДЕНИЯ

| Утверждение | Планы | Верификация | Уточнение |
|-------------|-------|-------------|-----------|
| **"MemoryMonitor обходит порт"** | 1 | `memory_monitor.py:116-128` | Использует psutil напрямую, но это **infrastructure concern**. Класс находится в `application/core/` — можно улучшить, но не критично. |
| **"Нет safety guard при записи"** | Все | `domain/locking.py:14-39` | `LockNotHeldError` определён, `LockContext` существует. **Требуется**: проверка вызова `validate_lock_for_write` в writers. |
| **"Tracing покрытие низкое"** | 3 | `observability/tracing.py` | Трассировка реализована, но интеграция с exporters может быть улучшена. |

## Часть 4. Консолидированный План Рефакторинга

### 4.1. ❌ ОТКЛОНЁННЫЕ ПРЕДЛОЖЕНИЯ

| Предложение | Причина отклонения |
|-------------|-------------------|
| **P1: Redis distributed locks** | Противоречит архитектурному решению (CLAUDE.md §5). Локальные блокировки достаточны. |
| **P2: Экспорт DQ метрик** | Уже реализовано в `postrun_service.py:158-163`. |
| **P2: MemoryStatsPort** | Over-engineering. Graceful degradation — валидный паттерн. |
| **P2: PII salt/hashing** | `default_email` — не PII, а технический идентификатор. |
| **P1: TTL 60s/heartbeat 20s** | Текущие значения (90s effective TTL) достаточны для локального запуска. |

### 4.2. ✅ ПРИНЯТЫЕ ПРЕДЛОЖЕНИЯ

#### P2: Усилить Safety Guard при записи
**Категория:** Блокировки и конкурентность
**Влияние:** Защита от split-brain при конкурентных записях

| Параметр | Значение |
|----------|----------|
| Текущее состояние | `LockContext` и `LockNotHeldError` определены, но вызов проверки в writers опционален |
| Целевое состояние | Writers обязательно проверяют владельца блокировки перед записью |
| Файлы | `delta_writer.py`, `gold_writer.py`, `bronze_writer.py` |
| Риски | Ложные отказы при некорректном wiring |
| Трудозатраты | S-M (1-2 дня) |
| Критерий готовности | Тест: запись без lock_context → `LockNotHeldError` |

#### P3: Документация контрактов данных
**Категория:** Документация
**Влияние:** Упрощение интеграции и понимания схем

| Параметр | Значение |
|----------|----------|
| Текущее состояние | Pandera схемы в коде, но нет человекочитаемых контрактов |
| Целевое состояние | `docs/contracts/` с описанием Silver/Gold схем |
| Файлы | `docs/contracts/*.md` (новые) |
| Трудозатраты | S (0.5-1 день) |
| Критерий готовности | Контракты синхронизированы с Pandera схемами |

#### P3: Увеличить покрытие bootstrap/factory
**Категория:** Тестирование
**Влияние:** Уверенность в composition layer

| Параметр | Значение |
|----------|----------|
| Текущее состояние | Некоторые фабрики имеют покрытие <50% |
| Целевое состояние | Покрытие composition layer ≥80% |
| Файлы | `tests/unit/composition/` |
| Трудозатраты | M (2-3 дня) |
| Критерий готовности | `pytest --cov=src/bioetl/composition --cov-fail-under=80` |
